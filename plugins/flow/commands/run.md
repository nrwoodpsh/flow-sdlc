# /flow:run — 파이프라인 오케스트레이션

국면을 **순서대로 자동 실행**해 매번 손으로 호출하는 수고를 없앤다.
단계를 넘길 때마다 **게이트 에이전트가 직전 산출물을 검증**하고, 통과해야 진행한다.

> 자동화하는 건 *국면 사이의 호출*이지 *게이트*가 아니다 — 게이트는 오히려 강해진다.
> 커밋 직전엔 **반드시 멈춘다**. 기본(하나씩 호출)을 대체하지 않는다.

## 연결

- **에이전트**: 국면별(`explorer`·`builder`⇄`verifier`·`reviewer`) + **`gatekeeper`**(작업자와 분리된 단계 게이트)
- **스킬**: `traceability`(게이트 기준 = 요구 ID 충족 · 되돌아갈 범위 계산) · `doc-verify`(게이트가 산출 문서를 템플릿과 대조) · **`code-review`**(`review → sync` 게이트가 **회차 누적** critical을 본다 — `회차가 쌓일 때`) · `drift-check`(커밋 직전) · `default-reference`
- **템플릿**: 없음 — 각 국면이 자기 템플릿을 쓴다
- 각 국면은 자기 커맨드의 절차·가드레일·기본 참조를 그대로 상속

## 입력 (`$ARGUMENTS`)

**세 칸을 조합한다.** 성격이 달라 서로 섞이지 않는다. 순서는 상관없다.

| 칸 | 값 | 무엇을 정하나 |
|:--|:--|:--|
| **체인** | `full` · `fix` · `design` · `build` | 어느 국면까지 도나 |
| **범위** | (비움)=대상 하나 · `project` · `{도메인}` · `{유닛}` | 대상이 몇 개인가 |
| **모드** | (비움)=멈춤 · `auto` | 설계가 잘못됐을 때 멈추나 고치나 |

**체인**

| 값 | 국면 |
|:--|:--|
| `full` | (spike) → prd → design → spec → build → verify unit → review → *(project면 verify project)* → sync **⏸** |
| **`fix`** | **design → spec → build → verify unit → review → sync ⏸** — 버그·변경 요청 |
| `design` | (spike) → prd → design → spec |
| `build` | build → verify unit → review → sync **⏸** |
| (비움) | **파일을 세어 어디까지 됐나 계산**하고(`traceability`) 이어갈 체인을 제안·확인 |

**`fix`에 `prd`가 없는 이유** — `/flow:design`이 요구를 **자동 발급**한다(재현 조건 → 기대 결과를 완료 기준으로). 버그는 "무엇이 필요한가"를 새로 묻는 게 아니라 **왜 안 되나**를 찾는 것이라 요구 인터뷰가 성립하지 않는다.

| 상황 | 체인 |
|:--|:--|
| 안 되던 것을 고친다 | **`fix`** |
| 동작을 바꾼다 (예: 잠금 3회 → 5회) | **`fix`** — `/flow:design`이 변경 요청으로 요구를 발급한다 |
| 없던 기능을 만든다 | `full` |
| 설계는 끝났고 구현만 | `build` |

- **`fix`는 유닛이 이미 있어야 한다.** 없으면 `full`이다 — 고칠 대상이 없다.
- **`fix`에 `full`을 쓰지 않는다.** `prd` 국면이 이미 있는 요구에 무엇을 할지 정해지지 않는다.

- `(spike)`는 앞단이 불확실할 때만. 사람이 판단해 켠다.
- **`verify project`는 `project` 범위에서만** 체인에 들어간다 — 유닛 하나를 도는데 전체 통합테스트를 돌릴 이유가 없다.

**자주 쓰는 조합**

| 명령 | 뜻 |
|:--|:--|
| `/flow:run full` | 유닛 하나를 끝까지. 문제 생기면 멈춘다 |
| `/flow:run full user/00.login` | 그 유닛만 |
| **`/flow:run fix user/00.login`** | **그 유닛의 버그를 설계부터 동기화까지** |
| **`/flow:run fix user/00.login auto`** | 같음 + **막히면 스스로 고쳐가며** |
| `/flow:run full project` | 제품 전체를 펼쳐서. 층마다 승인받는다 |
| `/flow:run full project auto` | 전체 + **설계가 틀리면 고치고 계속** |
| `/flow:run build project auto` | 설계는 끝났고 **구현만** 자율로 |

**레벨에 따라 체인이 짧아진다.** 시스템·도메인 요구는 `/flow:design`에서 끝나고 `/flow:spec`은 기능 레벨 전용이라 거부한다.

| 레벨 | `full` · `design` 체인 |
|:--|:--|
| `sys` · `domain` | (spike) → prd → design **에서 종료**. `spec` 이후를 실행하지 않는다 |
| `func` | 표 그대로 |

- **`fix`는 기능 레벨 전용**이다. 시스템·도메인 요구를 고치는 것은 정책 변경이라 `/flow:prd`로 간다.

- 대상 레벨은 첫 국면 전에 `traceability`로 판별한다. 판별 못 하면 **묻고 멈춘다** — 잘못된 체인을 돌리면 중간에 거부당한다.

**체인에 없는 커맨드** — 국면이 아니라서 빠진다.

| 커맨드 | 무엇인가 |
|:--|:--|
| `/flow:ask` | 라우터 — 어느 체인을 돌지 정해 준다 |
| `/flow:publish` | 발행 — 끝난 산출물을 밖으로 옮긴다 |
| `/flow:theme` | FE 테마 설정 — 화면 설계(`design`)와 별개다 |

- **`/flow:theme`은 `setup` 이후 언제든** 프로젝트당 1회. **FE가 있는 프로젝트만** — 없으면 안 돈다.
- **적용할 FE 코드가 있어야 한다.** `setup`이 원형을 복제했으면 바로, 빈 프로젝트면 FE 골격이 생긴 뒤.

## 절차

**대상 선언**

```
[/flow:run] 체인: {full|fix|design|build}   범위: {하나|project|도메인|유닛}   모드: {멈춤|auto}
       레벨: {sys|domain|func}   대상: {경로 또는 "1층에서 정해짐"}
       실행할 국면: {레벨을 반영한 실제 목록}
       게이트: 전환마다 gatekeeper 검증 · 재시도는 대상 하나당 3회
       정지: ① 재시도 소진  ② 국면 실패  ③ 층 전환  ④ 커밋 직전  {auto면 ⑤ 요구 수정 필요}
```

**규모 게이트** — `full` 또는 `auto`일 때. 장기 자율 작업이므로 모델을 확인한다.

```
⚠️ 장기 자율 작업 (국면 다수 · 서브에이전트 병렬 · 긴 실행)
   현재 세션 모델: {감지값}
   Fable 5 권장 — 단 비용 2배 · 턴이 수 분 · 30일 데이터 보존 필요(ZDR 불가)
   바꾸려면 /model 로 전환 후 재실행. 그대로 진행할까요?
```

- 모델은 **권고만** 한다 — 세션 모델은 사용자만 바꿀 수 있다. 무시하고 진행해도 된다.
- Fable 세션이면 절차를 세세히 따르기보다 **목표·제약 중심으로 위임**한다(과도한 절차 지시는 품질을 떨어뜨린다).
- `project auto`는 **가장 무거운 조합**이다 — 여기서 경고를 건너뛰지 않는다.

**1. 범위 펼치기** (`project`·`{도메인}`일 때만 — **`fix`는 해당 없음**)

> **`fix`는 대상이 하나다.** 유닛이 이미 정해져 있어 펼칠 것이 없다 — 절차 2로 바로 간다. `fix project`는 받지 않는다(버그를 제품 전체 범위로 고치지 않는다).

대상 목록을 **미리 알 수 없다.** 앞 층이 끝나야 다음 층 목록이 나온다.

| 층 | 무엇 | 끝나면 |
|:--|:--|:--|
| 1 | `prd sys` → `design sys` | 도메인 목록이 나온다 |
| 2 | 도메인마다 `prd domain` → `design domain` | **`09.domain`의 `유닛 계획`** 이 나온다 |
| 3 | 유닛마다 `prd func` → `design` → `spec` → `build` → `verify unit` → `review` | — |
| **4** | **`verify project`** — 전체 통합테스트 + 요구 커버리지 | **`project` 범위에서만** |
| 5 | `sync` | 커밋 직전 정지 |

- **층이 넘어갈 때 목록을 보여주고 승인받는다.** 도메인을 4개로 나눌지 6개로 나눌지는 판단이다 — 잘못된 층 위에 다음 층을 쌓지 않는다.
- **도메인이 하나면 1·2층을 합칠지 묻는다.** 층을 나누는 값이 없다 — 도메인 목록이 나올 것이 하나뿐이다.

  ```
  도메인이 하나로 보입니다(convert). 1·2층을 합쳐 돌까요?
    ① 합친다 — prd sys + prd domain + design 을 한 번에 (권장)
    ② 나눈다 — 층마다 승인받는다
  ```

  **`SYS-*`가 0개여도 정상이다** — 횡단 제약이 없으면 시스템 요구가 없다(`traceability`). 억지로 만들지 않는다.
- 여기서 말하는 **승인은 절차**다 — 개발자가 진행 여부를 정하는 것. **제품이 갖는 승인 기능**(사용자 결재·검수)과 다르다. 그건 요구·설계·구현 대상이다.
- 범위가 `{도메인}`이면 2층부터, `{유닛}`이거나 비었으면 3층만 돈다.
- **3층 대상은 `유닛 계획`에서 온다.** 폴더가 이미 있다고 전제하지 않는다 — 처음이면 비어 있다. 계획이 없으면 2층으로 돌아간다.
- **역추출만 한 도메인은 3층 대상이 아니다.** `유닛 계획`이 비어 있는 게 정상이다 — 무엇을 만들지 정하려면 `/flow:design domain`을 먼저 돈다. 그 도메인을 건너뛰고 이유를 밝힌다.

**4층(`verify project`)은 `project` 범위에서만 돈다.**

| 범위 | 4층 |
|:--|:--|
| `project` | **돈다** — 유닛을 전부 만든 뒤라 커버리지가 의미 있다 |
| `{도메인}` · `{유닛}` · 비움 | **안 돈다** — 일부만 만든 상태에서 돌리면 **대부분이 gap으로 나와** 리포트가 쓸모없다 |

**`verify branch`는 체인에 없다** — 머지 시점을 이 커맨드가 모르기 때문이다.

| | 언제 | 누가 |
|:--|:--|:--|
| `verify unit` | task마다 | 3층이 돈다 |
| **`verify branch`** | **머지 직전** — 그 브랜치 유닛들의 조합 | **사람이 `/flow:verify branch`를 부른다.** push·merge가 사람 몫이라 체인이 그 시점을 알 수 없다 |
| `verify project` | 유닛을 전부 만든 뒤 | 4층이 돈다 (`project` 범위만) |

- **혼자 하는 프로젝트면 건너뛴다** — `project`와 시점이 같다.
- 여럿이면 **`/flow:commit`이 브랜치 유닛이 둘 이상인데 조합 검증이 없으면 알린다.** 차단은 하지 않는다.

- 3층 유닛이 **하나라도 실패·정지 상태면 4층을 돌리지 않는다** — 미완성 위에서 잰 커버리지는 의미가 없다. 그 상태를 리포트하고 멈춘다.
- **원가·성능 요구는 여기서 처음 측정된다** — 실제 호출이 발생하니 비용이 든다(`test-spec`).
- **3층은 도메인이 끝날 때마다 멈춘다.** 유닛을 몇 개씩 묶느냐가 아니라 **경계에서 멈추는 것**이라 유닛 수가 달라도 일관된다.

  ```
  collect 유닛 3개 → ⏸   report 유닛 2개 → ⏸   shorts 유닛 4개 → ⏸   insight 유닛 2개 → ⏸
  ```

  - **한 도메인 안 유닛은 서로 얽혀 있다** — 중간에 끊으면 반쪽만 도는 상태가 된다. 도메인 하나가 온전히 끝난 뒤 보는 게 판단하기 쉽다.
  - 도메인 하나에 유닛이 **6개를 넘으면** 그 안에서도 한 번 끊는다 — 너무 오래 손을 못 대는 것도 위험하다.
  - 범위가 `{유닛}`이거나 비었으면 멈출 경계가 없다 — 체인 끝까지 간다.

**1-A. 멈춰 있던 유닛을 재개할 때** *(`정지` 상태일 때만)* — 사유부터 본다

**`정지` 상태에 그냥 다시 부르면 같은 지점에서 또 멈춘다.** 사유마다 먼저 할 일이 다르다.

| 사유 | 먼저 볼 것 | 그다음 |
|:--|:--|:--|
| `정지(빌드 3회)` | task `History`의 **3회 시도 이력** — 무엇을 시도했나 | 같은 방법을 또 쓰지 않는다. 설계를 의심할 근거면 `/flow:design`으로 |
| **`정지(critical)`** | **`6.review/`의 미해결 critical** — **전 회차 누적**(`code-review`) | **그것부터 고친다.** 안 고치고 `build`를 돌리면 리뷰에서 또 막힌다 |
| **`정지(요구)`** | 요구의 `확인 필요` 절 · 쿼터 `충돌` 표기 | **사람이 결정해야 한다** — 결정 없이 진행하지 않는다 |
| `정지(되돌아가기 2회)` | `auto`가 무엇을 두 번 고쳤나 (`6.review/`의 `상태` — `수정됨(NN회차)`) | 설계를 사람이 본다. `auto`로 다시 돌리지 않는다 |

```
[/flow:run] user/00.login — 상태: 정지(critical)

  미해결 critical 2건 (6.review/ 전 회차 누적)
    00.코드리뷰.20260710  SQL 주입 — src/UserMapper.java:42   미해결
    01.코드리뷰.20260715  세션 고정 — SessionFilter.java:18    미해결

  → 이것부터 고쳐야 합니다. 체인을 build 부터 돌리면 review 에서 또 막힙니다.
     ① 지금 고친다        ② 그래도 체인을 돌린다 (또 막힐 수 있음)
```

- **재시도 횟수는 초기화된다** — 새 세션이고 사람이 개입했으니 3회를 다시 준다. 다만 **같은 방법을 반복하면 그 사실을 적는다.**
- **`정지(요구)`는 자동 재개하지 않는다.** 사람 결정이 입력이다.

**2. 국면 실행** — 체인 순서대로. 각 국면은 자기 커맨드 정의를 따른다.

**3. 단계 게이트** (국면이 끝날 때마다)

작업한 에이전트가 **자기 일을 검증하지 않는다** — 편향되기 때문이다. `gatekeeper`가 확인한다(기준 상세는 그 정의).

| 전환 | 게이트가 확인하는 것 |
|:--|:--|
| prd → design | 요구에 ID·측정 가능한 완료 기준이 있나 |
| design → spec | 설계 요소가 요구를 빠짐없이 덮나 (`D-N` ↔ 요구 ID) |
| spec → build | task가 설계 요소를 덮나 · 계약이 `contract-gate` 통과했나 |
| build → verify | 구현이 task·계약대로인가 (임의 변경 없나) |
| verify → review | 테스트가 완료 기준을 덮고 실제 통과했나 |
| review → sync | critical 미해결이 없나 |

- 산출 문서가 **제 템플릿대로인지도** 본다 — 빠진 절·빈 껍데기·남은 자리표시자(`doc-verify`). 그 단계 산출물만 본다.
- **통과** → 다음 국면. **실패** → 사유와 함께 **직전 국면을 다시 실행**.

**재시도 상한은 대상 하나당 3회다.**

전환마다 3회가 아니다. `/flow:build`가 이미 내부에 3회 루프를 갖고 있어, 전환마다 3회를 주면 곱해져 비용이 몇 배로 뛴다.

- 유닛 하나를 도는 동안 **어느 전환에서 쓰든 남은 횟수를 깎는다.** 소진되면 그 지점에서 정지·리포트.
- 다음 대상으로 넘어가면 **다시 3회**가 된다 — 유닛 12개에 총 3회는 말이 안 된다.
- 재실행할 때는 **게이트가 준 실패 사유를 함께 넘긴다** — 같은 실수를 반복하지 않게.
- 국면 내부 루프(예: `build`의 구현↔테스트 3회)는 그 국면 정의를 따르며, **여기 상한과 별개로 세지 않는다.**

**4. 되돌아가 고치기** (`auto`일 때만)

기본 모드는 설계 결함을 만나면 멈춘다. `auto`는 **거슬러 올라가 고치고 이어간다.** 대신 **어디까지 올라가느냐에 선이 있다.**

| 원인 | 고칠 곳 | auto |
|:--|:--|:--|
| 구현 버그 | 코드 | ✅ 기본 모드도 함 (build 3회 루프) |
| **설계 결함** | `1.design.md` → 영향받는 task → 재구현 | ✅ **여기서만 허용** |
| **요구 충돌·모호** | `0.requirement.md` | ❌ **절대 안 함 — 정지·리포트** |

**`review critical`도 고친다** — 기본 모드는 멈추지만 `auto`는 고쳐서 잇는다.

근거는 우리 등급 규칙이다 — **critical은 룰 기반(1·2·5층)이 낸 것만**이고, LLM 단독 판단은 등급과 무관하게 리포트다. 룰이 낸 것이면 **고친 뒤 같은 룰로 재확인**해 검증된다.

| critical | auto |
|:--|:--|
| 컴파일 오류 | ✅ build 루프가 이미 함 |
| SQL 주입·XSS 등 (OCR·`claude-security`) | ✅ 고친다. `claude-security`는 **패치까지 제안**한다 |
| 데이터 손실 마이그레이션 | ✅ 설계 결함 → 되돌아가 고친다 |
| **요구를 고쳐야 하는 것** (예: 기능 자체가 법 위반) | ❌ **정지** — 요구는 바닥선이다 |

- **고친 뒤 같은 층을 다시 돌려 통과를 확인한다.** 안 하면 "고쳤다"는 말만 남는다.
- **되돌아가기 상한(유닛당 2회) 안에서**만 시도한다. 두 번 고쳐도 critical이 남으면 정지.
- **고친 내용을 `6.review/`의 그 발견 행 `상태`에 `수정됨(NN회차)`으로 적는다** — 자율로 고친 것이 조용히 묻히면 안 된다.

**요구가 바닥선이다.** 사용자가 원한 것을 AI가 고쳐서 "완성"하면 그건 다른 물건이다.

**무엇을 다시 도나 — 태그로 계산한다** (`traceability`)

```
D-2를 고쳤다
  → grep "design:.*D-2"  →  2.task/01.length-check.md 만 걸림
  → 그 task만 spec → build → verify 재실행
  → D-1 쪽 task는 건드리지 않는다
```

- **태그에 걸리지 않는 것을 임의로 다시 돌리지 않는다.** 범위를 넓히면 끝이 없다.
- 고친 내용은 그 문서 `History`에 **왜 고쳤는지** 남긴다 — 자율로 바꾼 것이 조용히 묻히면 안 된다.
- **되돌아가기는 유닛당 2회까지.** 두 번 고쳐도 안 되면 설계가 아니라 요구 문제일 확률이 높다 → 정지.

**auto가 멈추는 조건**

| 조건 | 왜 |
|:--|:--|
| 요구를 고쳐야 한다 | 사람 결정이다 |
| 같은 실패가 3회 반복 | 자기 수정이 안 통한다 |
| 한 바퀴 돌았는데 **진전 없음** | 무한 루프 방지 |
| 되돌아가기 2회 초과 | 위와 같음 |
| **critical을 두 번 고쳐도 안 없어짐** | 자기 수정 범위를 넘었다 |
| **요구를 고쳐야 하는 critical** | 요구는 바닥선이다 |
| 커밋 직전 | 변함없음 |

**5. 커밋 직전 정지** — `drift-check` 결과와 변경 목록을 제시하고 **멈춘다.** 커밋하지 않는다.

## 종료 조건

- 체인 끝까지 + 커밋 미리보기 제시 후 사람 대기, 또는
- 재시도 소진 / 국면 실패 / (auto면) 요구 수정 필요 시 그 지점 정지 + 리포트.

## 가드레일

- **자동 커밋·push·merge 금지.** `/flow:run`은 `/flow:commit`을 스스로 호출하지 않는다.
- **게이트를 건너뛰거나 기준을 낮추지 않는다.** 통과 못 하면 진행하지 않는다.
- **재시도 3회 상한 — 대상 하나당이다.** 소진 시 사람 에스컬레이션 — 무한 루프 금지.
- **층이 넘어갈 때 승인 없이 진행하지 않는다.** 대상 목록은 그때 정해진다.
- **레벨에 맞지 않는 국면을 실행하지 않는다.** 시스템·도메인은 `design`에서 끝난다 — `spec`을 부르면 거부당한다.
- **기본 모드는 실패 시 정지·리포트, 자율 수정 금지.** 테스트 약화·우회 금지.
- **`auto`여도 요구는 고치지 않는다.** 설계까지만 되돌아간다. 요구를 삭제·축소해 통과시키는 것은 금지.
- **`auto`가 고친 것은 반드시 `History`에 사유를 남긴다.** 조용히 바꾸지 않는다.
- **review critical을 남긴 채 넘기지 않는다.** 기본 모드는 정지하고, `auto`는 고쳐서 **같은 층으로 재확인**한다 — 어느 쪽도 미해결로 통과시키지 않는다.
- **`auto`가 고친 것은 `6.review/`의 `상태`에 `수정됨(NN회차)`으로 남긴다.** 조용히 바꾸지 않는다.
- 각 국면의 가드레일을 상속한다.
