# /flow:spec — 실행 명세

설계도(`1.design.md`)를 **AI가 구현하기 좋은 단위**로 나눈다.
산출: `2.task/`(순서 있는 task) · `3.contract/`(타입·스키마).

> **기능 레벨 전용.** 시스템·도메인 레벨은 `/flow:design`에서 끝난다 — 여기서 호출하면 거부하고 안내한다.
> **구현 코드는 작성하지 않는다.**

## 연결

- **에이전트**: `explorer` (기존 계약·호출부 광범위 확인 시)
- **스킬**: `traceability`(태그) · `doc-template`(task 골격) · `plain-writing` · `default-reference` · `contract-gate` · `impact-analysis`(기존 수정 시) · `code-graph`(정밀 영향, 선택)
- **템플릿**: `02.task-doc` · `03.api-contract`
- **도구**(있으면 씀): Context7(MCP — 계약에 쓰는 라이브러리 타입의 최신 시그니처) · LSP

## 입력 (`$ARGUMENTS`)

| 인자 | 동작 |
|:--|:--|
| (비움) | 자동 식별 — **`1.design.md`은 있고 `2.task/`가 없는 유닛**(`traceability`). 애매하면 질문 |
| `{도메인}/{NN.유닛}` | 대상 유닛 지정 (예: `user/00.login`) |

## 절차

**1. 대상 확정 선언**

```
[/flow:spec] 유닛: {domain}/{NN.unit}   입력: 1.design.md (D-1, D-2 …)
        산출: 2.task/ · 3.contract/
```

- `1.design.md`가 없으면 중단하고 `/flow:design`을 먼저 안내한다.
- 레벨이 시스템·도메인이면 거부한다(위 규칙).

**2. task 분할**

- 설계 요소(`D-N`)를 **구현 가능한 최소 단위**로 나눈다. 한 task = 한 관심사.
- **의존 순서**를 정한다 — 번호가 곧 실행 순서(`00.` → `01.` → …).

**입도 기준: `/flow:build`가 한 task를 3회 루프 안에 끝낼 수 있어야 한다.**

| 너무 크다 | 너무 작다 |
|:--|:--|
| 파일 10개 이상을 건드린다 | 파일 하나에 한 줄 |
| 완료 기준이 5개를 넘는다 | 완료 기준이 없다 |
| BE와 FE를 한 task에 넣었다 | 앞 task 없이는 의미가 없다 |
| "그리고"로 이어지는 목적이 둘 이상 | |

**버그 수정에는 "너무 작다"를 적용하지 않는다.** 한 줄만 고치는 것도 task를 만든다.

| 왜 | |
|:--|:--|
| **task가 없으면 `/flow:build`가 돌 대상이 없다** | 입력이 "미완료 task 자동 식별"이다 |
| **`5.verify/`가 task 번호와 1:1이다** | task가 없으면 검증 기록이 붙을 곳이 없다 |
| **추적이 끊긴다** | 자동 발급한 요구 → `D-N` → **task** → build → verify 사슬에 구멍이 생긴다 |

- 위 표의 **`너무 작다`는 신규 기능을 쪼갤 때의 기준**이다. 버그는 크기가 아니라 **하나의 원인**이 단위다.
- **원인이 둘이면 task도 둘이다.** 증상이 하나여도 원인이 갈리면 나눈다 — 하나만 고치고 통과하는 일을 막는다.
- **판단이 어려우면 쪼갠다.** 작으면 합치기 쉽지만, 커서 3회에 못 끝나면 되돌릴 게 많다.
- `D-N` 하나가 task 여럿이 될 수 있고, 반대는 안 된다 — **task 하나가 설계 요소 여럿을 묶지 않는다.**
- 파일: `2.task/NN.name.md`. 이 번호·이름을 `4.build/`·`5.verify/`가 물려받는다(스파인 1:1).
- 섹션 골격은 `doc-template`, 문장은 `plain-writing`.
- **task는 실행 지시서다.** 완료 기준·설계 결정·화면을 복사해 오지 않는다 — frontmatter에 **요구·설계 ID로 가리킨다.**

**3. 계약 확정** — `3.contract/`

- 형식은 `workflow.config`의 `contract`(기본 `.ts`). `contract-gate` 통과 필수.
- URL·필드·에러코드는 task와 **동일 값**이어야 한다.

**계약은 이 유닛의 것이다.** `3.contract/{도메인}.ts` — 유닛 사슬의 3번 자리다(`0.requirement`→`1.design`→`2.task`→**`3.contract`**→`4.build`→…).

- **유닛마다 자기 계약을 갖는다.** 그 유닛이 만들거나 쓰는 엔드포인트·타입만 담는다.
- **파일명은 `{도메인}.ts`** — 어느 도메인 API인지 드러난다. 경로가 어느 유닛인지 말해준다.
- **`self-contained`로 쓴다** — 외부 import 없이 타입·상수·enum을 자기 안에 갖는다(`contract-gate`의 단일 파일 게이트 전제).

| 상황 | 처리 |
|:--|:--|
| 이 유닛 계약이 없다 | `{도메인}.ts` 새로 만든다 |
| 이미 있다 | **그 파일에 추가**한다 |
| **다른 유닛이 같은 엔드포인트를 이미 정의했다** | **중단·보고.** 두 유닛이 같은 API를 만드는 것이라 **유닛 경계 문제**다 — 유닛 분할을 다시 본다 |
| 여러 도메인에 걸친다 | 각 도메인 파일에 자기 몫만 넣는다 |

**공유 타입이 반복되는 것은 감수한다** — `self-contained`의 대가다. 대신 **위험을 알고 있어야 한다.**

```
00.login/3.contract/user.ts:   interface User { id: number; email: string }
01.reset/3.contract/user.ts:   interface User { id: string;  email: string }
                                             ↑ 다르다. 각각 self-contained라 둘 다 컴파일 통과
```

- **`contract-gate`는 이걸 못 잡는다** — 파일별로 컴파일하기 때문이다.
- **`/flow:review`의 ① 계약 정합성이 유일한 방어다** — 같은 도메인의 계약 파일들을 나란히 놓고 **같은 이름의 타입이 다르게 정의됐나** 본다.
- **엔드포인트가 겹치면 유닛 경계를 다시 본다.** 타입 반복은 감수하지만 **엔드포인트 중복은 감수하지 않는다.**

- 계약은 task와 **M:N**이다 — 한 계약을 여러 task가 쓰고, 한 task가 여러 계약을 쓴다. 그래서 어느 task가 무엇을 쓰는지는 **task 문서 `사용 계약` 절**에서 추적한다.

**계약 파일 머리에 범위를 적는다.** 누가 쓰는지에 따라 **바꿀 수 있는 정도가 다르다.**

| 표기 | 누가 쓰나 | 깨는 변경 |
|:--|:--|:--|
| `내부 전용` | 이 배포 단위 안에서만 | **자유** |
| `서비스 간` | **우리** 다른 서비스 | 조심 — **같이 배포하면 된다.** 호출하는 서비스를 찾아 함께 고친다 |
| **`외부 제공`** | **다른 조직·팀** | **불가** — 상대 배포 일정을 모른다. 아래 규칙 |

배포 단위는 `00.ref/00.architecture/01.design.md`의 구성 요소 표에 있다.

**`외부 제공` 계약은 규칙이 다르다.**

| 규칙 | 왜 |
|:--|:--|
| **경로에 버전을 넣는다** (`/api/v1/…`) | 새 버전을 내야 깨는 변경이 가능하다 |
| **필드를 지우거나 뜻을 바꾸지 않는다** | 추가는 되지만 제거·의미 변경은 상대를 깨뜨린다 |
| **폐기는 예고한다** | `@deprecated {폐기 예정일}` + 대체 경로. 이행 기간 없이 끊지 않는다 |
| **바꾸면 사람이 상대에게 알린다** | 우리가 알릴 수 없다 — **`/flow:commit`이 "이 계약은 `외부 제공`이다"를 알리는 데까지**다(`drift-check`). 차단하지 않는다 |

- **`contract-gate`는 우리 코드만 컴파일한다.** 외부가 깨지는 것은 **아무 게이트도 안 잡는다** — 표기가 유일한 방어다.
- **표기가 없으면 `내부 전용`으로 본다.** 외부에 열었으면 반드시 적는다.

**LLM 프롬프트도 계약이다** — `3.contract/`에 둔다.

| 왜 계약인가 | |
|:--|:--|
| **바꾸면 출력이 바뀐다** | API 시그니처를 바꾸면 호출부가 깨지는 것과 같다 |
| **여러 곳이 쓴다** | 한 프롬프트를 여러 task가 공유 (M:N) |
| **이력이 남아야 한다** | 코드에 문자열로 박으면 왜 바꿨는지 사라진다 |

```
3.contract/{도메인}.prompt.md      프롬프트 본문 + 변수 + 기대 출력 형식
3.contract/{도메인}.ts             출력 스키마 (타입 — contract-gate가 검증)
```

- **출력 형식은 `.ts`에 타입으로** 둔다 — 그러면 `contract-gate`가 컴파일로 검증한다. 프롬프트 본문은 텍스트라 검증이 안 되니 **형식만 떼어 타입으로** 만든다.
- 프롬프트를 바꾸면 **`impact-analysis`로 쓰는 task를 전부 찾는다** — 출력이 달라지면 그 task의 테스트가 깨질 수 있다.
- **코드에 프롬프트를 문자열로 박지 않는다.** `3.contract/`에서 읽어 쓴다.
- 유닛 폴더 안에 두므로 **코드가 유닛 경로를 직접 import한다.** 그래서 **유닛 폴더명은 바꾸지 않는다** — 폴더명이 ID의 일부다(`traceability`). 범위가 달라졌으면 유닛을 닫고 새로 만든다.

**4. 태그** — `traceability`

각 task frontmatter에 자기가 충족하는 상위 ID를 단다. **직접 충족만** 적는다(부모는 전이).

```yaml
---
requirement: [USER-LOGIN-1]
design: [D-1]
---
```

**5. 교차 검증**

- task ↔ 계약 값 일치 확인.
- 설계 요소(`D-N`) 중 **task가 없는 것**이 있으면 알린다(누락 방지).
- 기존 로직을 고치는 task는 `impact-analysis`로 회귀 표면을 뽑아 task에 명시.

## 가드레일

- **구현 코드 작성 금지.** 산출물은 task 문서와 계약뿐.
- **설계를 새로 만들지 않는다.** 구조가 빠졌으면 `/flow:design`으로 돌려보낸다.
- 계약은 `contract-gate` 통과 전까지 완료로 보고하지 않는다.
- task 번호는 실행 순서다 — 임의로 재배열하지 않는다.
- **task 하나가 설계 요소 여럿을 묶지 않는다.** 3회 루프에 못 끝날 크기면 쪼갠다.
- **다른 유닛이 정의한 엔드포인트를 또 정의하지 않는다.** 겹치면 멈추고 보고한다 — 유닛 경계 문제다.
