# /flow:design — 설계도

요구를 **분석**해 구조를 확정한다. 산출: `*.design.md` — 데이터·기능·(프론트)화면 구조.
분석은 이 커맨드의 **첫 스텝**이고, 결과물은 **설계도**다.

> **task 분할·계약은 하지 않는다** — `/flow:spec`의 일이다. **구현 코드도 쓰지 않는다.**
> **단일 정문**: 동작·로직이 바뀌는 변경은 전부 여기를 지난다. 오타·문구만 flow 밖.

## 연결

- **에이전트**: `explorer` (영향·사각지대 광범위 스캔 시)
- **스킬**: `traceability`(레벨·경로·태그) · **`usecase`**(버그·변경 요청에서 요구를 발급할 때) · `plain-writing` · `default-reference` · `impact-analysis`(기존 변경 회귀 표면) · `code-graph`(정밀 영향, 선택) · `theme-apply`(화면 구조에서 토큰 참조)
- **템플릿**: 레벨별 — `sys`→`13.architecture` · `domain`→`09.domain` · `func`→`01.design` · 결정은 `08.adr`
- **도구**(있으면 씀): GitHub MCP(PR·이슈 논의로 배경 확인) · DB MCP(실제 컬럼) · LSP·Joern(정밀 영향)

## 입력 (`$ARGUMENTS`)

| 인자 | 동작 |
|:--|:--|
| (비움) | 최근 `/flow:prd` 산출을 자동 식별 (애매하면 질문) |
| `{도메인}/{NN.유닛}` | 기능 레벨 대상 지정 |
| 자유 문장 | 버그·변경 요청 (예: `로그인 후 401 간헐 발생`) |
| `REFERENCE @파일` | 로그·기존 코드·스키마 |

## 절차

**1. 레벨·대상 선언** — `traceability`

```
[/flow:design] 레벨: {시스템|도메인|기능}  대상: {…}
          입력: {요구 ID 목록}   산출: {라우팅 경로}
```

- 요구가 없으면: **버그·변경 요청이면 요구를 자동 발급**해 `0.requirement.md`에 append(`traceability`). 신규 기능이면 `/flow:prd`를 먼저 안내.
- 도메인은 `00.ref/01.domain/` 기존을 재사용한다 — 유사 도메인이 있으면 새로 만들지 말고 확인.

**자동 발급한 요구의 완료 기준은 재현 케이스로 쓴다.** 요구엔 측정 가능한 완료 기준이 필수인데, 버그는 "고쳐졌다"가 애매하다.

| 상황 | 완료 기준 |
|:--|:--|
| 버그 | **재현 조건 → 기대 결과.** 예: `만료 토큰으로 요청 시 401 (현재 200)` |
| 변경 요청 | 바뀐 뒤의 관찰 가능한 동작. 예: `잠금 기준 3회 → 5회` |

**성능·원가 버그는 `종류`와 `측정 방법`을 함께 적는다.** 참·거짓으로 안 갈리기 때문이다.

| | 기능 버그 | **성능·원가 버그** |
|:--|:--|:--|
| 완료 기준 | `401이 나온다` — **참/거짓** | `p95 1초 이하 (현재 30초)` — **수치** |
| `종류` 칸 | 비운다 (기능 제약) | **`성능`·`원가`를 적는다** |
| `측정 방법` | 불필요 | **필수** — 무엇으로·어떤 부하·데이터 몇 건에서 |

```
APPROVAL-LINE-9 | 성능 | 목록 조회 p95 1초 이하 (현재 30초)
                | 측정: 운영 데이터 100만 건 · k6 50 VU 3분 · p95
```

- **측정 방법 없이 고치면 "고쳐졌다"를 확인할 수 없다.** 개발 데이터 100건에서는 인덱스가 없어도 빠르다.
- **적은 도구가 실제로 있는지 확인한다** (`presets/tools` 성능·원가 측정 절). 없으면 있는 도구로 방법을 바꾼다.
- **`fix` 체인에서도 같다** — `prd`를 안 지나지만 요구 형식은 같아야 `verify`가 잴 수 있다.

- **근본원인을 확정하기 전엔 완료 기준을 쓰지 않는다** — 증상만 적으면 엉뚱한 걸 고친다.
- 재현이 안 되면 요구를 발급하지 말고 **재현 조건부터 사용자에게 묻는다.**

**2. 분석** (설계의 근거)

- 기존 DB·API·외부 연동 **영향**을 능동 탐색 (넓게 훑을 땐 `explorer`, 관계를 정밀히 볼 땐 `code-graph`).
- **기존 코드를 고치는 설계면 `impact-analysis`로 회귀 표면을 뽑는다** — 무엇이 같이 깨질 수 있나. 순수 신규면 생략.
- repo 이력에서 "모르는 것조차 모르는 것" 추출 — revert·중단된 마이그레이션·우회 미들웨어. **GitHub MCP가 있으면 PR 리뷰 코멘트·이슈 논의까지** 본다(커밋 메시지에 없는 배경이 거기 있다). 없으면 로컬 `git log`만.
- 버그면 **재현·근본원인**까지 확정한다(추정 금지).
- 결과는 설계도의 `## 분석` 절에 남긴다 — 제약·사각지대·리스크·회귀 표면.

**3. 설계 인터뷰** (step Q&A · 모호할 때만)

한 번에 하나씩, 답이 구조를 크게 바꾸는 순서로. **이미 답이 요구·인자·참조에 있으면 건너뛴다** — 다 주어졌으면 인터뷰 없이 바로 설계도로 간다.

**레벨마다 묻는 게 다르다.** 시스템 설계에 "어떤 데이터가 필요합니까"를 물으면 답이 안 나온다.

| 스텝 | sys | domain | func | 질문 예시 (플레이스홀더) |
|:--|:--:|:--:|:--:|:--|
| 구성 | ✓ | | | `배포 단위를 어떻게 나눕니까? 각자 어느 도메인·저장소를 맡습니까? (예: user-svc = user 도메인 + Postgres)` |
| 의존 방향 | ✓ | | | `금지할 방향이 있습니까? (예: 서비스끼리 직접 호출 금지, 이벤트로)` |
| 크로스커팅 | ✓ | | | `모든 도메인이 지킬 규칙은? (예: 시각 UTC · 금액 정수 · 에러코드 U001)` |
| **화면 목록** | ✓ | | | *(FE가 있을 때)* `화면이 몇 개쯤 되고 어디서 어디로 갑니까? (예: 로그인 → 대시보드 → 회원 목록 → 상세)` |
| **측정 수단** | ✓ | | | *(성능·원가 요구가 있을 때)* `이걸 재려면 무엇을 기록해야 합니까? 어디에? (예: 편당 LLM 토큰·TTS 문자·렌더 초 → cost_log 테이블)` |
| 경계 | | ✓ | | `이 도메인이 책임지는 것과 아닌 것은? (예: 계정·인증은 함 / 결제수단은 안 함)` |
| 용어 | | ✓ | | `이 도메인만 쓰는 말이 있습니까? (예: 휴면 = 1년 미접속, 로그인은 막고 데이터는 유지)` |
| 업무 흐름 | ✓ | ✓ | | `시작 신호·갈림길·인계·끝나는 상태는? (예: 신청 → 결재 → 반영 / 반려)` |
| **유닛 분할** | | ✓ | | `이 도메인을 몇 덩어리로 만듭니까? 순서는? (예: 00.collect → 01.script → 02.render)` |
| 데이터 | | | ✓ | `어떤 데이터가 새로 필요합니까? 어느 저장소에? (예: 재설정 토큰·만료 시각 → Postgres)` |
| 기능 | | | ✓ | `처리 흐름은? (예: 요청 → 토큰 발급 → 메일 발송 → 검증 → 변경)` |
| 화면 | | | ✓ | `(프론트) 어떤 화면이 필요합니까? 빈 상태·로딩·오류도. (예: 요청 폼 · 완료 안내)` |
| 엣지 케이스 | | | ✓ | `정상 흐름 밖에 뭐가 있습니까? (예: 연속 요청 · 만료 직전 클릭 · 탈퇴 계정)` |
| 배포·롤백 | | | ✓ | `되돌릴 수 없는 게 있습니까? 배포 순서는? (예: 테이블 신설 → BE → FE / 데이터 삭제는 비가역)` |
| 대안 | ✓ | ✓ | ✓ | `A안(동기 발송)과 B안(큐)이 갈립니다. 제약은?` |

- `sys`의 업무 흐름은 **여러 도메인을 가로지르는 것**만. 한 도메인 안 흐름은 `domain`에서 묻는다.

**성능·원가 요구는 잴 수단이 설계 요소로 나와야 한다.** 요구에 `측정 방법`이 적혀 있어도, **그 데이터를 남기는 코드가 없으면 잴 수 없다.**

| 요구 종류 | 측정 방법 | 필요한 설계 요소 |
|:--|:--|:--|
| **원가** | `LLM 토큰 + TTS 문자 + 렌더 초 합산` | **`D-N` 원가 로깅** — 무엇을·어디에 기록하나. 없으면 합산할 데이터가 없다 |
| **성능** | `k6로 100 VU 5분 → p95` | 부하 도구가 붙을 **엔드포인트**가 있나. 큐·배치면 **처리 시각 로그** |

- **`측정 방법`만 채워지고 로깅이 없으면 `doc-verify`는 통과한다** — 잴 수 있다고 적혀 있고 잴 수 없다. `verify project`에서 영구 gap이 된다.
- **원가·성능 요구가 있으면 `D-N`을 하나 이상 만들어 태그한다** — `SYS-*`뿐 아니라 **기능 레벨(`종류: 성능`)도 같다.** 태그가 없으면 `gatekeeper`가 `design → spec`에서 잡는다.
- 크로스커팅이라 **한 도메인 것이 아니다** — `00.architecture/01.design.md`에 둔다.

**`domain`의 산출은 `유닛 계획`이다** — 다음 층이 이 목록을 하나씩 돈다. 비어 있으면 **무엇을 만들지가 없어** `prd func`가 진입할 대상이 없다.

- 기준은 `09.domain`의 `유닛 계획` 절에 있다 — **혼자 검증되나 · 요구를 덮나 · 번호가 순서인가**.
- **번호는 의존 순서로 준다.** 앞 유닛의 산출이 뒤 유닛의 입력이다.
- 사용자가 "알아서 나눠"라고 하면 **나눠서 제시하고 승인받는다.** 승인 없이 다음 층으로 넘기지 않는다 — 잘못 나눈 위에 유닛 6개를 쌓으면 되돌릴 게 너무 많다.
- **레거시면 역추출한 현행 요구를 근거로 나눈다.** 요구가 `확인 필요` 상태여도 유닛은 정할 수 있다 — **이번에 손댈 범위**를 정하는 것이라 현행 확정과 별개다. 손대지 않을 부분은 유닛으로 만들지 않는다.

**4. 설계도 작성** — `*.design.md`

| 절 | 내용 |
|:--|:--|
| 분석 | 영향·제약·사각지대·(버그면) 근본원인 |
| 데이터 구조 | 엔티티·필드·관계 + **그림**(관계형=ERD · 그래프=노드·관계도) + **인덱스·제약**. DDL 정본은 `00.ref/02.db-schema/` — 실행문을 여기 중복 작성하지 않는다 |
| 기능 구조 | 흐름·책임·경계 + **시퀀스 다이어그램**(PlantUML — 표기는 `doc-template`) |
| 화면 구조 | 프론트만. 화면별 **배치·요소 표·상태(빈/로딩/오류)·이동**. 토큰은 `00.ref/04.theme/` 정본 참조 — 재정의 금지 (규약: `theme-apply`) |
| 엣지 케이스 | 정상 흐름 밖. **여기서 빠뜨리면 구현·테스트에서도 빠진다** |
| 배포·롤백·마이그레이션 | 무중단으로 넣을 순서, **되돌리는 방법**, 되돌릴 수 없는 것 |
| 설계 요소 표 | `D-N` · 요소 · **충족 요구 ID** |

**레벨마다 템플릿이 다르다.** 위 표는 기능 레벨(`01.design`)이다.

| 레벨 | 템플릿 | 고유 절 |
|:--|:--|:--|
| 시스템 | `13.architecture` | 구성 요소(**배포 단위 ↔ 도메인 ↔ 저장소 매핑**) · 의존 방향 · **크로스 도메인 업무 흐름** · 크로스커팅 규칙(UTC·금액·에러코드) · **화면 지도**(FE가 있을 때) |
| 도메인 | `09.domain` | 배포 단위 · 경계 · 용어 · **한 도메인 업무 흐름**(시작 신호·갈림길·인계·끝나는 상태) |
| 기능 | `01.design` | 위 표 |

- **업무 흐름이 여러 도메인에 걸치면 시스템 레벨로 올린다.** 한 도메인 문서가 남의 흐름을 소유하지 않는다.

**FE가 있으면 `sys`에서 `화면 지도`를 만든다** — `SCR-N`을 여기서 발급한다(`traceability`). **유닛이 하나여도 만든다.**

- 화면 지도가 없으면 각 유닛이 **`SCR-1`부터 새로 시작**해 같은 번호가 여러 곳에 생긴다 — 화면 이동을 가리킬 수 없다.
- `sys`를 건너뛴 프로젝트에 FE를 붙이게 되면 **그때 `design sys`를 돌려 화면 지도만 만든다.** 유닛 설계도에서 발급하지 않는다.
- 지도엔 **무엇이 있고 어디로 가나**만. 화면별 배치·요소는 유닛의 `1.design.md`가 갖는다.

**시스템·도메인은 `/flow:prd`와 자리를 나눈다.** 요구 절은 건드리지 않는다.

| 레벨 | `/flow:prd` | `/flow:design` |
|:--|:--|:--|
| sys | `00.architecture/00.requirement.md` — **별도 파일** | `00.architecture/01.design.md` |
| domain | `01.domain/{도메인}.md`의 `요구`·`확인 필요` 절 | **같은 파일**의 `경계`·`용어`·`업무 흐름` |

- 판단이 갈린 결정은 **택한 안 + 기각 대안**을 함께 남긴다.

**"승인"이 두 가지 뜻으로 쓰인다 — 헷갈리지 않게 구분한다.**

| | 무엇 | 어디 |
|:--|:--|:--|
| **제품 기능으로서의 승인** | 사용자가 무언가를 확인·결재하는 **기능**. 요구가 있고 설계·구현·테스트 대상이다 | `0.requirement`·`1.design`·코드 |
| **flow의 단계 승인** | `/flow:run`이 층을 넘길 때 **사람에게 묻는 것.** 절차이지 기능이 아니다 | `/flow:run` 절차 |

- 설계도에 승인 흐름을 그릴 때는 **누가 무엇을 승인하나**를 명시한다 — 제품 사용자인지, 개발자인지.
- **제품의 승인 게이트는 구현해야 한다.** flow가 대신해 주지 않는다.
- 태그는 **직접 충족만**(부모는 전이). 횡단 요구(`SYS-*`)는 직접 적는다.

**5. 착지·기록**

- **시스템·도메인 레벨 → 여기서 정지.** 결과가 `00.ref/` 정본이 된다. `/flow:spec`으로 넘기지 않는다.
- **기능 레벨 → 다음은 `/flow:spec`.**
- 중요한 아키텍처 결정·정책 변경 → `doc/02.decisions/` ADR (템플릿 `08.adr` · README 색인 갱신).
- 새 용어·도메인 경계 → `00.ref/01.domain/` 갱신 제안 (확정은 사람).

## 가드레일

- **task 분할·계약 작성 금지** (`/flow:spec`), **구현 코드 금지**.
- 영향도가 모호하면 **즉시 중단하고 질문.** 추측으로 설계를 채우지 않는다.
- 요구에 없는 기능을 설계에 넣지 않는다 — 필요하면 요구부터 추가한다.
- **도메인 파일의 `요구` 절을 고치지 않는다** — `/flow:prd`의 자리다.
- 버그는 근본원인을 확정하기 전에 수정 설계를 내지 않는다.
- 추측과 확인을 구분해 표기한다.
