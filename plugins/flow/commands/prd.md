# /flow:prd — 요구사항 정의

무엇을·누가·왜·어떤 기능인가를 확정하고 **요구마다 ID를 발급**한다.
이 ID가 `design → spec → build → verify`를 관통하는 **추적 축**이 된다.

> **설계하지 않는다.** 구조·기술 선택은 `/flow:design`의 일이다. 여기서는 "무엇이 필요한가"만 정한다.

## 연결

- **에이전트**: `explorer` (기존 요구·코드 광범위 확인 · `legacy` 필수)
- **스킬**: `traceability`(레벨 판별·저장 위치·ID 발급) · **`usecase`**(기능 레벨 — 입도·필드·관계 표기) · `plain-writing` · `default-reference`
- **템플릿**: 레벨별 — `sys`→`13.architecture` · `domain`→`09.domain` · `func`→`00.requirement`
- **도구**(있으면 씀): GitHub·DB(MCP — `legacy` 역추출에서 "왜 이렇게 됐나"의 근거) · **ponytail**(플러그인 — `legacy`에서 과설계 지도)

## 입력 (`$ARGUMENTS`)

| 인자 | 동작 |
|:--|:--|
| (비움) | 대화형 — 레벨부터 질문 |
| `sys` | 시스템 레벨 — 제품 전체·횡단 (예: 인증 방식·성능 기준) |
| `domain {도메인}` | 도메인 레벨 — 한 도메인의 요구 (예: `domain user`) |
| `func {도메인}/{NN.유닛}` | 기능 레벨 — work-unit (예: `func user/00.login`) |
| **`{레벨} legacy`** | **역추출 모드** — 기획서 대신 **코드**를 읽어 현행 요구를 뽑는다. **레벨과 함께 준다** (예: `sys legacy`·`domain user legacy`) |
| `REFERENCE @파일` | 기획서·회의록·기존 요구 |

**`legacy`는 레벨의 수식어다 — 단독 인자가 아니다.** 레벨이 읽을 범위를 정하기 때문이다(절차 2').

| 입력 | 처리 |
|:--|:--|
| `sys legacy` | 횡단 구현(인증·에러·로깅·설정)에서 `SYS-*` 역추출 |
| `domain {도메인} legacy` | 그 도메인의 엔티티·서비스 경계·용어에서 역추출 |
| `func {도메인}/{유닛} legacy` | 그 유닛 모듈 동작 — **유닛이 이미 있을 때만**(아래 규칙) |
| **`legacy` 단독** | **레벨을 묻는다.** 지어내지 않는다 — 어디를 읽을지가 안 정해진다 |

## 절차

**1. 레벨 판별** — `traceability`

```
[/flow:prd] 레벨: {시스템|도메인|기능}  대상: {…}
       산출: {라우팅 경로}   ID 형식: {SYS-N | {도메인}-N | {도메인}-{유닛}-N}
```

- 판별 기준: **여러 도메인에 걸치면 시스템 · 한 도메인에서 끝나면 도메인 · work-unit 하나면 기능.**
- 애매하면 질문한다 — 예: `이 요구가 결제·주문에도 적용됩니까? (예=시스템)`
- 기능 레벨이면 상위(도메인·시스템) 요구를 먼저 읽고 **참조**한다. 없으면 고아로 진행하되 알린다.

**규모 게이트** — `legacy`일 때만. 코드베이스 전체를 읽으므로 모델을 확인한다.

```
⚠️ 대규모 역추출 (수백 파일 · 서브에이전트 병렬 · 긴 실행)
   현재 세션 모델: {감지값}
   Fable 5 권장 — 단 비용 2배 · 턴이 수 분 · 30일 데이터 보존 필요(ZDR 불가)
   바꾸려면 /model 로 전환 후 재실행. 그대로 진행할까요?
```

- 모델은 **권고만** 한다. 무시하고 진행해도 된다.

**2. 요구 인터뷰** (step Q&A) — *`legacy`면 2' 로 대체*

한 번에 하나씩, **답이 범위를 크게 바꾸는 순서로** 묻는다. 이미 답이 인자·참조에 있으면 건너뛴다.

**레벨마다 묻는 게 다르다.** 시스템 요구("모든 API는 JWT")에 액터·기능을 물으면 답이 안 나온다.

| 스텝 | sys | domain | func | 질문 예시 (플레이스홀더) |
|:--|:--:|:--:|:--:|:--|
| 목적 | ✓ | ✓ | ✓ | `무엇을 해결합니까? (예: 회원이 비밀번호를 잊어도 스스로 복구)` |
| 목표 | ✓ | | | `이루려는 것이 있습니까? 우리가 못 만드는 것도. (예: 월 100만원 수익 · 조회수 10만)` |
| 액터 | | ✓ | ✓ | `누가·무엇이 씁니까? 주 액터와 연동 시스템을 나눠서. (예: 일반 회원 / 인증 서버)` |
| 기능 | | ✓ | ✓ | `필요한 기능을 나열하면? (예: 이메일 인증 · 재설정 링크 · 만료 처리)` |
| 흐름 | | | ✓ | `각 기능이 어떤 순서로 흐릅니까? 예외도. (예: 요청 → 발송 → 검증 → 변경 / 만료 시 U003)` |
| **사전·사후조건** | | | ✓ | `시작하려면 무엇이 참이어야 하고, 끝나면 무엇이 남습니까? (예: 계정이 잠금 아님 / 세션 생성·마지막 로그인 갱신)` |
| **업무 규칙** | | ✓ | ✓ | `판정 기준·한도·예외 대상이 있습니까? 숫자로. (예: 3회 실패 시 잠금 — 관리자는 예외)` · **`domain`이면 이어서** `이 규칙이 이 도메인의 여러 기능에 걸립니까?` |
| 적용 범위 | ✓ | | | `이 제약이 어디까지 적용됩니까? (예: 모든 외부 API. 내부 배치는 제외)` |
| 외부 의존 | ✓ | | | `남의 서비스에 매달린 게 있습니까? **쿼터·상한**은? (예: 유튜브 API 하루 10,000 units)` |
| 완료 기준 | ✓ | ✓ | ✓ | `무엇이 되면 완료입니까? 측정 가능하게. (예: 링크 10분 만료, 실패 시 U002)` |
| **측정 방법** | ✓ | ✓ | ✓ | *(`종류`가 있는 요구가 나왔을 때 — 성능·원가·법·정책)* `이걸 어떻게 잽니까? (예: k6로 100 VU 5분 · LLM 토큰 로그 + S3 용량 합산 · 법·정책이면 "사람 판단")` |
| 의존 | ✓ | ✓ | ✓ | `먼저 끝나야 하는 게 있습니까? (예: 인증 서버 토큰 API · USER-1 가입)` |
| 범위 밖 | ✓ | ✓ | ✓ | `이번에 하지 않을 것은? (예: SMS 인증 · 생체 인증)` — **요구로 등록한 것을 여기 적지 않는다** |

- 추측으로 채우지 않는다. 모르면 `확인 필요`로 남긴다.

**2'. 역추출** (`legacy` — 레거시 프로젝트)

기획서가 없고 **코드가 유일한 진실**일 때. 코드에 구현된 사실을 요구로 등록한다.

- **`explorer`에 위임**한다 — 코드베이스 원문을 메인 컨텍스트로 끌어오지 않는다.
- **GitHub MCP가 있으면 이슈·PR 논의도 근거로 쓴다** — 코드만 보면 "무엇을 하는가"는 알아도 "왜"는 모른다. 없으면 코드와 `git log`만.
- **ponytail이 있으면 `/ponytail-audit`으로 과설계 지도를 함께 뽑는다** — 어디가 과하게 만들어졌나. 요구 역추출과 별개 정보다. 결과는 요구가 아니라 **`확인 필요`에 참고로** 남긴다.
- 레벨별로 읽는 것: `sys`=인증·에러·로깅·설정 등 **횡단 구현** · `domain`=엔티티·서비스 경계·용어 · `func`=해당 모듈 동작.
- 뽑은 항목은 **전부 `확인 필요`로 표기**한다. 구현 세부와 의도는 다르다 — 확정은 사람이 한다.
- 의도가 불분명한 코드(우회·임시 처리)는 요구로 승격하지 말고 **`의도 불명`으로 별도 나열**한다.

**역추출 요구엔 신규용 게이트를 걸지 않는다.** 이미 운영 중인 것에 "완료 기준이 측정 가능한가"를 물으면 레거시에 flow를 못 붙인다.

| 무엇 | 역추출에서 |
|:--|:--|
| 측정 가능한 완료 기준 | **면제** — 코드가 하는 일을 옮긴 것이다 |
| 쿼터 대조 | **`현행 — {실제 동작}`** 으로 적는다. 넘는 것 같아도 돌고 있다면 어떻게 넘기는지(재시도·큐)를 적는다 |
| 측정 수단 `D-N` | **면제** — 설계 단계가 아니다 |

- **면제 근거는 `상태: 확인 필요`다.** 사람이 검수해 `확정`으로 바꾸면 그때부터 신규와 같은 게이트가 걸린다.
- **`확인 필요`를 게이트 우회용으로 쓰지 않는다** — 신규 요구를 그렇게 적으면 `gatekeeper`가 판정에 적는다.

**`func legacy`는 유닛을 새로 만들지 않는다.** 레거시 코드에는 work-unit 경계가 없어 번호를 지어내야 하는데, 지어낸 번호는 나중에 실제 작업 단위와 어긋난다.

| 대상 | 처리 |
|:--|:--|
| 유닛이 이미 있다 | 그 유닛의 `0.requirement.md`에 **현행 동작을 append** |
| 유닛이 없다 | **거부하고 `domain legacy`를 안내**한다 — 도메인 파일에 현행 요구를 모으고, 실제로 손댈 때 `/flow:prd func`로 유닛을 만든다 |

**표는 새로 만들지 않는다** — 해당 템플릿의 요구 표에 행을 더하고 `상태`를 `확인 필요`로 적는다. `근거`는 요구 칸에 붙인다.

```markdown
| ID | 종류 | 요구 | 완료 기준 | 측정 방법 | 상태 |
|:--|:--|:--|:--|:--|:--|
| SYS-9 | 기능 제약 | 현행: 모든 API는 세션 인증 | | 역추출 — `AuthFilter.java` | 확인 필요 |
```

- **`상태`를 비우면 `확정`이다** (`traceability`) — 역추출은 반드시 `확인 필요`로 적는다. 안 적으면 신규 게이트가 걸려 전부 FAIL이 된다.

**3. ID 발급 · 기록** — `traceability`

- 요구마다 ID(불변·append-only). 기존 파일이 있으면 **이어서 발급**한다(재편 금지).
- **`SYS-*`를 발급하기 전에 원격 기본 브랜치의 요구 파일을 본다** (`traceability`). 로컬만 보면 남이 이미 쓴 번호를 다시 쓴다 — 도메인 요구는 접두가 갈려 안 부딪히지만 `SYS-*`는 여럿이 같이 건드린다.
- ID는 **폴더·파일 이름에서 번호를 떼고 대문자로** 만든다(`traceability`). 새 도메인·유닛을 만들 때 **이름을 짧게** 지어야 ID가 짧아진다 — 한 단어 권장, 두 단어까지.
- 상위 참조를 문서 상단에 한 번 선언. 각 요구에 중복 기재하지 않는다.

**기능 레벨은 요구를 유스케이스로 쓴다** — 액터·흐름·예외가 곧 요구다. 별도 `UC-N`을 만들지 않는다.

```markdown
상위: USER-1 ← SYS-1

| ID | 종류 | 유스케이스 | 액터 | 주 흐름 | 예외 | 완료 기준 | 측정 방법 |
|:--|:--|:--|:--|:--|:--|:--|:--|
| USER-LOGIN-1 | | 이메일 로그인 | 일반 회원 | 입력 → 검증 → JWT 발급 | 불일치 → U001 | 성공 시 JWT 발급(30분) | — |
| USER-LOGIN-4 | 성능 | 로그인 응답 3초 내 | — | — | — | p95 3초 | k6로 50 VU 3분 · p95 |
```

- 표를 채운 뒤 **유스케이스 그림(PlantUML)** 을 같은 문서에 그린다. 표기·입도·정본 분담은 **`usecase` 스킬**이 정본이다.
- **입도는 sea-level** — 하나의 유스케이스 = 사용자가 한 자리에서 끝내는 하나의 목표. CRUD를 넷으로 쪼개지 않고, 실패 처리를 별도 유스케이스로 빼지 않는다.
- **`종류`가 비면 `기능 제약`이다.** 이 유스케이스만의 비기능(예: `성능` — 로그인 응답 3초)은 **별도 요구로 등록**한다. 시스템 횡단이면 `SYS-*`다.
- **`종류`가 있으면 `측정 방법`을 반드시 채운다** — 레벨과 무관하다(세 템플릿 모두 열이 있다). 비면 **영구 gap**이 되고, `법·정책`은 `사람 판단 — 자동화 불가`라고 적는다.
- **업무 규칙이 있거나 예외 흐름이 둘 이상이면 `유스케이스 상세`를 쓴다** — 조건부 필수. 없으면 표 한 줄로 끝낸다.
- **업무 규칙은 걸리는 범위의 레벨에 적는다** (`usecase`) — 이 유스케이스만이면 `R번호`, 도메인의 여러 기능에 걸리면 `09.domain`의 **`DR번호`**, 여러 도메인이면 `SYS-*`. **올린 규칙은 `참조:`로 번호만 가리킨다** — 내용을 복사하면 고칠 곳이 둘이 된다.
- **그림 대상은 `종류`가 비고 액터가 있는 행뿐이다.** 성능·원가 요구와 역추출은 그림에 올리지 않는다.
- 시스템·도메인 레벨은 흐름이 없다 → 액터·주 흐름·예외 칸을 쓰지 않는다.

**시스템 요구는 `종류`를 함께 적는다** — 검증 방법이 달라서다.

| 종류 | 검증 |
|:--|:--|
| 기능 제약 · 보안 | 테스트 |
| **성능** | 부하 측정 |
| **원가** | 비용 계산 |
| **법·정책** | **사람 판단 — 자동 검증 불가** |

- **목표와 요구를 섞지 않는다.** "조회수 10만"은 우리가 만드는 게 아니라 완료 기준이 될 수 없다 — `목표` 절에 두고, 그걸 위해 **우리가 하는 것**만 요구로 발급한다.
- `법·정책` 요구는 테스트가 없는 게 정상이다 — `/flow:verify project`가 **gap이 아니라 `사람 확인 필요`** 로 분류한다.

**`측정 방법`을 비워두지 않는다.** 비면 그 요구는 **영구 gap**이 된다 — 검증할 길이 없으니 영원히 확인이 안 된다.

| 종류 | 무엇을 적나 |
|:--|:--|
| 성능 | **도구 · 부하 조건 · 뽑을 값** — "부하 측정"만으로는 부족하다 |
| 원가 | **무엇을 합산하나 · 데이터 출처** (실행 로그·청구서·계량 API) |
| 법·정책 · UX | **"사람 판단 — 자동화 불가"** 라고 적는다. 이건 비운 게 아니다 |

- **측정 방법을 모르면 요구를 확정하지 않는다** — `확인 필요`에 적는다. "원가 500원"만 있고 무엇을 합산할지 모르면 그건 요구가 아니라 바람이다.
- **적은 도구가 실제로 있는지 확인한다** (`presets/tools` 성능·원가 측정 절). 없으면 **그 요구는 영구 gap**이다 — 잴 방법이 없으니 영원히 검증 안 된다.

  ```
  ⚠ SYS-4 측정 방법에 k6를 적었는데 설치돼 있지 않습니다.
    ① 설치합니다 (brew install k6)
    ② 있는 도구로 방법을 바꿉니다
  ```

- **원가는 도구로 안 잰다.** 편당 얼마를 알려면 **우리가 토큰·용량·전송량을 로그로 남겨야** 한다 — 그 로깅이 `/flow:design`에서 **설계 요소로 나와야** 한다. 측정 방법에 "합산한다"만 적고 로깅을 안 만들면 `verify project`에서 잴 게 없다.

**외부 쿼터를 요구에 대고 계산한다** — `쿼터 ÷ 1회 사용량 = 하루 상한`. 요구가 그 안인지 **여기서 확인**한다.

`외부 의존` 표의 `우리 요구와 맞나`에 **셋 중 하나로 적는다**: `OK — {계산}` · **`충돌 — {계산}`** · `확인 필요 — {무엇을 모르나}`.

- **`충돌`이면 여기서 멈춘다.** 요구가 처음부터 불가능하다 — 요구를 줄이거나 쿼터를 올린다. **사람이 정한다.**

  ```
  ⛔ SYS-1(하루 20편) vs 유튜브 Data API 업로드 쿼터(일 6편) — 충돌
     ① 요구를 하루 6편으로 줄인다
     ② 쿼터 상향을 신청한다 (승인까지 시간이 걸린다)
     ③ 업로드를 사람이 한다 → 자동화 범위가 바뀐다 = 요구 변경
     어느 쪽입니까?
  ```

- **비워두면 `gatekeeper`가 `prd → design`을 차단**한다. 설계·구현을 다 한 뒤 `verify project`에서 드러나면 되돌릴 게 너무 많다.
- **설계로 넘기지 않는다.** 우회 방식이 답이면 그것도 요구 변경이라 여기로 돌아온다.

**시스템·도메인은 `/flow:design`과 자리를 나눈다.** 여기서 요구만 쓰고 **나머지는 손대지 않는다.**

| 레벨 | `/flow:prd` | `/flow:design` |
|:--|:--|:--|
| sys | `00.architecture/00.requirement.md` — **별도 파일** | `00.architecture/01.design.md` |
| domain | `01.domain/{도메인}.md`의 **`요구`·`확인 필요` 절만** | 같은 파일의 `배포 단위`·`경계`·`용어`·`업무 흐름` |

- 도메인은 **한 파일을 두 커맨드가 나눠 쓴다** — 남의 절을 건드리면 상대가 덮어쓴다.
- `09.domain`의 `하위 기능`은 `/flow:sync`가 자동 색인한다 — 손으로 쓰지 않는다.

**4. 요약**

- 발급 ID 목록 · 범위 밖 · `확인 필요` 항목을 보여주고 검수 요청.
- 다음 안내: 시스템·도메인 → `/flow:design`(구조 확정 후 정지) · 기능 → `/flow:design` → `/flow:spec`.

## 가드레일

- **설계 금지.** 기술 선택·구조·API 형태는 산출물에 넣지 않는다.
- **ID 재편 금지.** 삭제는 `deprecated` 표기, 분할은 하위 ID(`USER-3` → `3.1`·`3.2`).
- 측정 불가능한 완료 기준은 그대로 두지 않는다 — 되묻거나 `확인 필요`로 표기.
- 기존 요구를 덮어쓰지 않는다. 충돌하면 중단·보고.
- **`legacy` 역추출은 사람 검수 전까지 정본이 아니다** — 전부 `확인 필요`. 코드 수정도 하지 않는다.
- **유닛 번호를 지어내지 않는다.** 없는 유닛에 `func`를 쓰려 하면 거부하고 `domain`을 안내한다.
- **시스템·도메인 파일에서 요구 절 밖을 건드리지 않는다** — 경계·용어·구조는 `/flow:design` 몫이다.
- 추측과 확인을 구분해 표기한다.
