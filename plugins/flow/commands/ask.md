# /flow:ask — 진입 안내

하고 싶은 일을 아무렇게나 쓰면 **어느 커맨드로 가야 하는지 정리해 보여주고, 승인하면 실행**한다.
커맨드를 이미 알면 쓸 필요 없다 — 바로 그 커맨드를 부르면 된다.

> **여기서 일하지 않는다.** 문서도 코드도 쓰지 않는다. 정리하고 넘길 뿐이다.

## 연결

- **에이전트**: 없음 — **메인 세션이 직접 판별**한다. 넓게 읽을 일이 없어 위임하지 않는다(필요하면 넘겨받은 커맨드가 `explorer`를 쓴다)
- **스킬**: `traceability`(레벨 판별) · `default-reference`(참조 후보) · `ops-doc`(파이프라인 밖 문서면 여기로)
- **템플릿**: 없음 — 판별해 넘길 뿐 문서를 만들지 않는다. 만들게 되면 `ops-doc`이 제 템플릿을 연다

## 입력 (`$ARGUMENTS`)

| 인자 | 동작 |
|:--|:--|
| 자유 문장 | 무엇을 하고 싶은지 (예: `로그인이 자꾸 401 나는데 고쳐줘`) |
| (비움) | `무엇을 하고 싶습니까?` 한 줄 질문 |
| `REFERENCE @파일` | 기획서·로그·화면 등 참고 자료 |

## 절차

**1. 작업 유형 판별**

**프로젝트가 세팅돼 있나 먼저 본다.** `CLAUDE.md`·`workflow.config.json`·`doc/`이 없으면 무엇을 물었든 **`/flow:setup`부터** 안내한다.

| 사용자가 말한 것 | 유형 | 보낼 곳 |
|:--|:--|:--|
| **하던 것을 이어서 하고 싶다** · 어디까지 했는지 모른다 | **재개** | **아래 절차 1-B** — 파일을 세어 지점을 찾고 알맞은 커맨드로 |
| 프로젝트를 새로 시작한다 · 여기에 flow를 얹고 싶다 | 세팅 | `/flow:setup` |
| 없던 기능을 만들고 싶다 | 신규 | `/flow:prd func {도메인}/{유닛}` |
| 제품 전체·횡단 규칙을 정하고 싶다 | 시스템 요구 | `/flow:prd sys` |
| 한 도메인의 범위·용어를 정하고 싶다 | 도메인 요구 | `/flow:prd domain {도메인}` |
| 안 되던 게 있다 · 고쳐야 한다 | 버그·변경 | `/flow:design` (요구 자동 발급) · **끝까지 알아서면 `/flow:run fix {유닛}`** |
| **운영이 지금 안 된다 · 장애다** | **장애** | **아래 절차 1-A** — 완화 먼저, 그다음 `fix`, **회고까지 잇는다** |
| 되는지 모르겠다 · 해봐야 안다 | 불확실 | `/flow:spike` |
| 남의 코드를 파악해야 한다 | 레거시 | `/flow:prd sys legacy` |
| 설계는 있고 나누기만 하면 된다 | 명세 | `/flow:spec` |
| 코드를 짜면 된다 | 구현 | `/flow:build` |
| 돌려보고 싶다 | 검증 | `/flow:verify` |
| 품질·보안을 보고 싶다 | 점검 | `/flow:review` |
| 문서가 제대로 됐나 보고 싶다 | 문서 점검 | `/flow:review doc` |
| 코드는 고쳤는데 문서가 안 맞는다 | 동기화 | `/flow:sync` |
| 커밋하자 | 커밋 | `/flow:commit` |
| 화면 색·폰트를 바꾸고 싶다 | 테마 | `/flow:theme` |
| 결과를 노션에 올리고 싶다 | 발행 | `/flow:publish` |
| 처음부터 끝까지 알아서 | 자동 | `/flow:run full` |
| **버그를 고치는 것부터 동기화까지 알아서** | **자동·버그** | **`/flow:run fix {도메인}/{유닛}`** |
| 제품 전체를 만들고 싶다 (도메인 여럿) | 자동·전체 | `/flow:run full project` |
| 전체를 만들되 **막히면 스스로 고쳐가며** | 자동·자율 | `/flow:run full project auto` |
| 장애 회고·운영 절차·설명 노트를 쓰고 싶다 | 파이프라인 밖 문서 | **`ops-doc` 스킬** (커맨드 아님 — 바로 위임) |
| **적어둔 절차대로 실행해 달라** | **절차 실행** | **커맨드가 아니다** — 아래 절차 1-D |

- 레벨(시스템·도메인·기능) 판별은 `traceability`.
- **두 개 이상에 걸치면 후보를 나열하고 고르게 한다.** 임의로 정하지 않는다.
- 오타·문구 수정처럼 **동작이 안 바뀌는 일이면 "flow 밖에서 그냥 고치세요"**라고 답하고 끝낸다.

**1-A. 운영 장애일 때** — 순서가 다르다

기능 버그와 성격이 다르다. **지금 서비스가 안 되는 상태**라 순서를 바꿔야 한다.

| | 기능 버그 | **운영 장애** |
|:--|:--|:--|
| 먼저 할 것 | 근본 원인 확정 | **완화** — 되돌리기·재시작·우회로 서비스를 살린다 |
| 그다음 | 설계 → 구현 | 근본 원인 → `fix` 체인 |
| 뒤에 오는 것 | 없음 | **회고가 반드시 따라온다** |

```
[/flow:ask] 유형: 운영 장애

  ① 지금 서비스가 되고 있습니까?
       안 된다 → 완화가 먼저입니다. 되돌릴 배포가 있습니까?
       된다(느리거나 일부만) → ②로

  ② 근본 원인을 찾아 고칩니다 → /flow:run fix {유닛}
       성능·원가 문제면 종류·측정 방법을 함께 정합니다 (/flow:design)

  ③ 고친 뒤 회고를 씁니다 → ops-doc (11.postmortem)
       재발 방지 조치마다 "어디로"를 적어야 파이프라인에 들어갑니다
```

- **완화를 우리가 실행하지 않는다.** 되돌리기·재시작은 **배포 시스템과 사람**의 일이다(`CLAUDE.md`의 `가드레일`). 무엇을 해야 하는지 제시하고 멈춘다.
- **③을 빠뜨리지 않는다.** `fix`로 고치고 끝내면 회고가 안 남고, 같은 장애가 다시 온다. **고친 뒤 회고를 쓸지 반드시 묻는다.**
- 장애 시각·영향 범위는 **추정하지 않는다** — 로그·알람에서 확인하거나 사용자에게 묻는다(`ops-doc`).

**1-B. 재개할 때** — 파일을 세어 지점을 찾는다

**README의 `상태`를 믿지 않는다.** `sync`를 안 돌리고 멈췄으면 낡았다 — **파일이 정본**이다(`traceability`).

```
[/flow:ask] 재개 — user/00.login (파일에서 계산)

  0.requirement ✅   1.design ✅   3.contract ✅
  2.task/   00.login-api  01.session  02.lockout
  4.build/  00.login-api  01.session              ← 02 미착수
  5.verify/ 00.login-api                          ← 01 미검증
  6.review/ 없음

  계산한 상태: 구현중        README에 적힌 값: 명세  ← 낡았다

  이어갈 곳
    ① /flow:verify unit user/00.login   01 검증부터 (권장 — 앞선 것을 먼저 닫는다)
    ② /flow:build user/00.login         02 구현부터
    ③ /flow:run build user/00.login     verify·review·sync까지 이어서
```

- **앞선 단계를 먼저 닫는 쪽을 권한다** — 미검증을 두고 다음 task를 구현하면 실패가 쌓인다.
- **계산한 상태가 README와 다르면 알린다.** `/flow:sync`를 권하되 여기서 고치지 않는다.
- **`정지(사유)` 상태면 사유부터 본다** — `/flow:run`의 재개 절차로 보낸다.
- **3주 전 맥락은 문서에 있다** — task `History`의 `Deviation`·`6.review/`의 미해결·`확인 필요` 절을 함께 읽어 보여준다.

**1-D. 적어둔 절차를 실행해 달라고 할 때** — 단계마다 갈린다

`04.ops/`의 운영 절차(SOP·런북)는 **사람이 따라 하는 문서**다. 통째로 실행하지 않는다.

| 단계 | 누가 |
|:--|:--|
| **`사람만`으로 표시된 단계** | **실행하지 않는다.** 무엇을 해야 하는지 제시하고 멈춘다 |
| 표시 없는 단계 (개발·로컬) | 실행한다 |
| **표시 자체가 없는 문서** | **묻는다** — 구버전 템플릿이다. 어느 단계가 사람 몫인지 확인받고 진행 |

- **`사람만` 표시는 SOP 템플릿의 `담당` 표에 있다** — 운영 반영·권한 부여·과금·데이터 삭제.
- **절차 문서가 없으면 실행하지 않는다.** 기억으로 배포 순서를 재구성하지 않는다 — 먼저 `ops-doc`으로 절차를 적는다.
- **끝났는지 확인**까지 하고, 사람 몫으로 남긴 단계를 목록으로 낸다.

**2. 빠진 것을 두 갈래로 나눈다**

| 갈래 | 뜻 | 누가 |
|:--|:--|:--|
| **갈림길** | 답에 따라 **보낼 커맨드가 바뀐다** | **여기서 묻는다** |
| **준비물** | 보낼 커맨드가 물어서 채운다 | **나열만 한다** |

**갈림길 예시** — 이걸 모르면 잘못 보낸다.

| 물을 것 | 갈리는 것 |
|:--|:--|
| `안 되던 겁니까, 새로 만드는 겁니까?` | `/flow:design`(버그) ↔ `/flow:prd`(신규) |
| `고치는 것만 볼까요, 커밋 직전까지 알아서 갈까요?` | `/flow:design` ↔ `/flow:run fix` |
| `이게 다른 도메인에도 적용됩니까?` | `sys` ↔ `domain` ↔ `func` (`traceability`) |
| `되는지 확실합니까?` | `/flow:spike`를 켤지 |
| `유닛이 이미 있습니까?` | `func legacy` 거부 여부 |

**준비물은 묻지 않는다** — 목적·액터·완료 기준·스택 같은 것. **대상 커맨드에 step Q&A가 있다.** 여기서 물으면 질문이 두 겹이 되고 사람이 같은 답을 두 번 한다.

**3. 정리 선언** (작업 전 필수)

```
[/flow:ask] 작업: {한 줄 요약} · 유형: {신규|버그|불확실|레거시|점검…}
            보낼 곳: {/flow:xxx 인자}
            근거: {왜 이 커맨드인지 한 줄}
            참조: {읽을 문서·경로}
            갈림길: {없음 | 물어서 답을 받은 내용}
            준비물: {대상 커맨드가 물을 것 — 미리 챙기라고 알림}
            → 이대로 실행할까요?  [실행 / 고치기 / 취소]
```

- **갈림길이 남아 있으면 승인을 받지 않는다** — 잘못 보내면 되돌아온다.
- **준비물은 경고가 아니라 안내다** — 없어도 진행한다. 대상 커맨드가 묻는다.
- 참조 후보는 `default-reference`의 그 커맨드 기본값 + 사용자가 준 `@파일`.

**4. 실행**

- **실행**을 고르면 그 커맨드를 인자와 함께 호출한다. 이후는 전적으로 그 커맨드의 절차를 따른다.
- **고치기**를 고르면 사용자 수정을 받아 3으로 돌아간다.
- **취소**면 아무것도 하지 않는다.

**5. 되돌아오면 한 번만 다시 보낸다**

넘긴 커맨드가 "선행이 없다"며 돌려보낼 수 있다(예: `/flow:design` → `/flow:prd`).

- **한 번만** 그 선행 커맨드로 다시 보낸다. 승인은 다시 받는다.
- **두 번째로 되돌아오면 멈추고 사람에게 리포트한다** — 왕복하지 않는다.

## 가드레일

- **승인 없이 실행하지 않는다.** 정리 → 확인 → 실행 순서를 건너뛰지 않는다.
- **여기서 산출물을 만들지 않는다** — 요구·설계·코드는 넘겨받은 커맨드가 쓴다.
- **갈림길을 추측으로 넘기지 않는다.** 답에 따라 커맨드가 갈리면 **묻는다** — 잘못 보내면 되돌아온다.
- **준비물은 묻지 않는다.** 대상 커맨드의 step Q&A가 채운다 — 같은 질문을 두 번 하지 않는다.
- **커맨드를 새로 지어내지 않는다** — 위 표에 있는 것만 보낸다.
- 파이프라인 밖 문서는 커맨드가 없다 — `ops-doc`에 넘기고 끝낸다.
- **왕복하지 않는다.** 되돌아온 것을 다시 보내는 건 한 번까지다.
- 작은 일에 절차를 강요하지 않는다 — flow 밖이 맞으면 그렇게 답한다.
