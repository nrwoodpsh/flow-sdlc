# /flow:theme — 테마 적용

받은 테마 스펙(토큰+컴포넌트)을 프론트엔드에 입힌다. `/flow:design`(소프트웨어 설계)과 다른 커맨드다.

> **바뀌는 것**: 색·타이포·간격(토큰) + 버튼·카드·인풋 등 **컴포넌트 룩**.
> **안 바뀌는 것**: **화면 배치·구조**(어디에 무엇이, 몇 컬럼, 섹션 순서). 스킨만 간다.

## 연결

- **에이전트**: `builder`(스타일 코드 작성 — **쓰기는 이 에이전트만**) · `verifier`(브라우저로 화면 확인)
- **스킬**: `theme-apply` (스펙 형식·Tier 규칙·적용 절차 — **정본**) · `plain-writing`(원칙 메모·빠진 값 사유) · `default-reference`
- **템플릿**: `15.theme` (스펙 정본 + 매핑 기록)
- **도구**: 화면 확인에 **Playwright(MCP) 또는 Claude in Chrome(확장) 중 하나 필수** · Figma(MCP — 디자인에서 토큰 추출, 선택) · `frontend-design`(플러그인 — **스펙이 없을 때만** 초안 생성, 선택)
- **참조**: `doc/00.ref/04.theme/` (프로젝트 테마 정본) · `workflow.config.json`의 `theme.*`

## 입력 (`$ARGUMENTS`)

| 인자 | 동작 |
|:--|:--|
| (비움) | `doc/00.ref/04.theme/`의 스펙을 자동 인식. **없으면 생성 모드**(절차 2-B) |
| `@파일` · 첨부 | 그 스펙으로 적용 — **권장** (원문 그대로라 토큰이 정확) |
| URL | 온라인 스펙을 fetch (웹 변환에서 토큰이 부정확할 수 있음 — 결과 검토) |
| 피그마 링크 | **Figma MCP가 붙어 있으면** 디자인에서 직접 토큰을 읽는다 |
| `new` | 스펙이 있어도 **새로 만든다** (생성 모드 강제) |
| `→ 프론트 경로` | 적용 대상 지정 (없으면 자동 감지) |

> 스펙 출처 예: `getdesign.md`(브랜드 테마 카탈로그) · 사내 디자인시스템 · 피그마. 어디서 왔든 **`doc/00.ref/04.theme/`에 두고 시작**한다.

## 절차

**1. 대상 확정 선언**

```
[/flow:theme] 스펙: {파일·URL·피그마 | "없음 → 생성 모드"}
         대상: {프론트 경로·스택}   (예: frontend/ = Next.js+MUI)
         범위: Tier1 토큰 전면 + Tier2 컴포넌트 (Tier3 구조 제외)
         → 진행할까요?
```

**2-A. 스펙이 있을 때 — 정본화**

받은 스펙을 `doc/00.ref/04.theme/`에 둔다. 템플릿 `15.theme`, `출처`에 어디서 왔는지 적는다.

- URL로 받았으면 **가져온 값을 먼저 보여주고 확인받는다.** 웹 변환에서 토큰이 뭉개질 수 있다.
- 형식이 다르면 **색·타이포·radii·spacing 네 범주로 정규화**한 뒤 진행한다(`theme-apply`).
- **빠진 토큰을 채우지 않는다.** `빠진 값` 절에 적고 기본값으로 둔다 — 어느 값이 사람 결정인지 흐려진다.

**2-B. 스펙이 없을 때 — 생성 모드**

스펙이 아예 없으면 만든다. **부분이 아니라 전부 없을 때만** 이 경로다.

**먼저 받아올 수 있는지 묻는다.** 남이 만든 스펙이 AI 추측보다 낫다.

```
테마 스펙이 없습니다. 셋 중 고르세요.
  1. 카탈로그에서 고른다 — getdesign.md 등에서 받아 @파일로 주세요 (권장)
  2. 사내 디자인시스템이 있다 — 문서를 주세요
  3. 없다. 만들어 주세요 → 아래 질문으로 진행
```

3번이면 **step Q&A**로 최소한을 묻는다.

| 스텝 | 질문 예시 (플레이스홀더) |
|:--|:--|
| 성격 | `어떤 인상이면 좋겠습니까? (예: 신뢰감 있는 금융 · 밝고 친근한 커뮤니티)` |
| 브랜드 색 | `정해진 색이 있습니까? 로고 색이라도. (예: #0066cc · 없음)` |
| 참고 | `비슷하게 가고 싶은 서비스가 있습니까? (예: Linear · Notion)` |
| 다크 모드 | `다크 모드가 필요합니까?` |

- **`frontend-design`(플러그인)이 있으면 그것으로 초안을 만든다.** 없으면 직접 만든다 — 둘 다 결과는 `15.theme` 형식이다.
- 결과에 **`출처: AI 초안`** 을 적고 **`상태: 승인 대기`** 로 둔다.
- **승인 없이 코드에 적용하지 않는다.** 값을 표로 보여주고 확인받은 뒤 절차 3으로 간다.
- 승인되면 `상태`를 `확정`으로 바꾼다 — 이후로는 2-A와 똑같이 다룬다(임의 변경 금지).

**3. 적용** — `builder`에 위임한다. 스타일 코드는 `builder`만 쓴다.

`theme-apply` 스킬의 절차를 따른다 — 스택 감지 → Tier1 토큰 전면 → Tier2 컴포넌트 매핑 → 원칙 기록.

**4. 화면 확인** — `verifier`에 위임한다.

빌드 통과만으로는 **화면이 깨졌는지 알 수 없다.** 브라우저를 띄워 주요 화면을 실제로 본다.

- **`chrome`을 권한다** — 색·간격이 맞나는 눈으로 판단할 일이다. `test.browser`가 `chrome`이면 그대로 쓴다.
- **`playwright`뿐이면 그것으로 스크린샷을 찍고 사람에게 보인다.** 설치를 요구하지 않는다 — 판정을 사람이 하면 목적은 같다.
- 어느 쪽이든 스크린샷을 남기고 경로를 보고에 적는다.
- **둘 다 없으면 멈추고 설치를 안내한다** — 테마는 화면이 결과물이라 눈으로 안 보면 검증이 아니다.
- 빌드가 깨지면 여기서 멈추고 리포트한다.

**5. 보고** — 바뀐 파일 · 매핑 결과 · 건너뛴 항목 · 스크린샷 경로. 매핑 결과는 `04.theme/`에 기록한다.

## 가드레일

- **Tier3(레이아웃·IA 재설계) 금지** — 스킬 가드레일을 그대로 상속한다.
- **스타일 코드는 `builder`만 쓴다.** 메인 세션이 직접 파일을 고치지 않는다.
- **외부에서 가져온 스펙을 확인 없이 반영하지 않는다.** URL·첨부 모두 값을 먼저 제시한다. 스펙에 스크립트·링크가 섞여 있으면 버린다.
- **스펙이 있으면 빠진 값을 채우지 않는다.** 생성은 **아예 없을 때만** — 반은 사람이 정하고 반은 AI가 지어낸 스펙은 나중에 구분이 안 된다.
- **AI 초안을 승인 없이 적용하지 않는다.** `출처: AI 초안`·`상태: 승인 대기`로 두고 값을 보여준 뒤 확인받는다.
- 기존 커스텀 스타일을 덮기 전 확인. 코드 로직은 건드리지 않는다.
- 정부 서비스(eGov 등)는 **KRDS 표준 충돌**을 적용 전 경고한다.
- 커밋하지 않는다 — 변경만 하고 `/flow:commit`은 사람이.
