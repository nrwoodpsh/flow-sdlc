# 설계 절차 — 기능 레벨

`/flow:design` 이 레벨을 기능으로 판정했을 때 읽는다. **기능마다 반복되는 절차다.**
산출은 유닛의 설계 문서 · task 문서 · 계약이다. **구현 코드는 쓰지 않는다.**

## 요구를 확인하거나 자동 발급한다

버그·변경 요청이면 여기서 요구를 발급해 유닛의 요구 문서에 append 한다. 신규 기능인데 요구가 없으면 `/flow:prd` 로 돌려보낸다.

| 상황 | 완료 기준 |
|:--|:--|
| 버그 | **재현 조건 → 기대 결과.** 예: 만료 토큰으로 요청하면 401 (지금은 200) |
| 변경 요청 | 바뀐 뒤의 관찰 가능한 동작. 예: 잠금 기준 3회 → 5회 |

**성능·원가 버그는 `종류` 와 `측정 방법` 을 함께 적는다.** 참·거짓으로 안 갈리기 때문이다.

| | 기능 버그 | 성능·원가 버그 |
|:--|:--|:--|
| 완료 기준 | `401 이 나온다` — 참/거짓 | `p95 1초 이하 (지금 30초)` — 수치 |
| `종류` 칸 | 비운다 | **`성능`·`원가` 를 적는다** |
| `측정 방법` | 불필요 | **필수** — 무엇으로·어떤 부하·데이터 몇 건에서 |

- **측정 방법 없이 고치면 "고쳐졌다" 를 확인할 수 없다.** 개발 데이터 100건에서는 인덱스가 없어도 빠르다.
- **근본원인을 확정하기 전에 완료 기준을 쓰지 않는다** — 증상만 적으면 엉뚱한 것을 고친다.
- 재현이 안 되면 요구를 발급하지 말고 **재현 조건부터 묻는다.**
- ID 는 이어서 발급한다 — 재편하지 않는다(`traceability`).

## 분석한다

- 저장소·API·외부 연동의 영향을 능동적으로 찾는다. 버그면 **재현과 근본원인까지 확정한다** — 추정으로 넘어가지 않는다.
- **기존 코드를 고치는 설계면 `impact-analysis` 의 `regression-surface` 조각으로 회귀 표면을 뽑는다.** 순수 신규면 생략한다. 정밀한 호출 관계가 필요하면 그 조각이 코드 그래프 질의로 넘긴다.
- 결과는 설계 문서의 분석 절에 남긴다 — 제약·사각지대·리스크·회귀 표면.

## 설계 문서를 쓴다

| 절 | 내용 |
|:--|:--|
| 분석 | 영향·제약·사각지대·(버그면) 근본원인 |
| 데이터 구조 | 엔티티·필드·관계 + 그림 + 인덱스·제약. **스키마 정본에 있는 실행문을 여기 옮겨 적지 않는다** |
| 기능 구조 | 흐름·책임·경계 + 시퀀스 그림 |
| 화면 구조 | 화면이 있을 때. 배치·요소·상태(빈·로딩·오류)·이동. **토큰은 참조만 하고 재정의하지 않는다** |
| 엣지 케이스 | 정상 흐름 밖. **여기서 빠뜨리면 구현과 테스트에서도 빠진다** |
| 배포·롤백 | 무중단 순서 · 되돌리는 방법 · **되돌릴 수 없는 것** |
| 설계 요소 표 | 요소 번호 · 요소 · **충족하는 요구 ID** |

- 그림 표기는 `doc-template` 이, 같은 값이 두 문서에 있을 때의 정본 판정은 `doc-verify` 의 `canon-map` 조각이 정본이다.
- **되돌릴 수 없는 것을 사람에게 넘긴다** — 데이터 삭제·비가역 마이그레이션은 실행 순서를 적고 실행은 배포 시스템과 사람의 일이다.

## task 로 나눈다

설계 요소를 **구현 가능한 최소 단위**로 나눈다. 한 task 는 한 관심사이고, **번호가 곧 실행 순서다.**
문서 골격은 `doc-template` 의 `task-doc` 조각이 정본이다 — 절 목록을 여기 옮겨 적지 않는다.

| 너무 크다 | 너무 작다 |
|:--|:--|
| 파일 10개 이상을 건드린다 | 파일 하나에 한 줄 |
| 완료 기준이 5개를 넘는다 | 완료 기준이 없다 |
| 화면과 서버를 한 task 에 넣었다 | 앞 task 없이는 의미가 없다 |
| "그리고" 로 이어지는 목적이 둘 이상 | |

- **입도 기준은 구현이 3회 루프 안에 끝낼 수 있는가다.**
- **버그 수정에는 `너무 작다` 를 적용하지 않는다.** 한 줄만 고쳐도 task 를 만든다 — task 가 없으면 구현이 돌 대상이 없고, 검증 기록이 붙을 곳이 없고, 추적 사슬에 구멍이 생긴다.
- **원인이 둘이면 task 도 둘이다.** 증상이 하나여도 원인이 갈리면 나눈다 — 하나만 고치고 통과하는 일을 막는다.
- **task 하나가 설계 요소 여럿을 묶지 않는다.** 반대(요소 하나가 task 여럿)는 된다.
- **task 는 실행 지시서다.** 완료 기준·설계 결정·화면을 복사해 오지 않는다 — 요구·설계 ID 로 가리킨다.
- **파일 목록을 task 에 적는다.** 그 목록이 소스와 유닛을 잇는 정본이고, 진입 게이트 훅이 그것을 읽는다. 비우면 쓰기가 막히거나 거친 판정으로 떨어진다.

## 계약을 확정한다

형식과 검증 명령은 프로젝트 설정에서 온다 — 판정 규칙은 `contract-gate` 의 `config` 조각이 정본이다.
**계약 게이트를 통과하기 전까지 완료로 보고하지 않는다.** 실패했을 때 계약이 틀린 것인지 환경이 틀린 것인지는 `failure` 조각이 가른다 — **코드에 맞춰 계약을 고치지 않는다.**

| 상황 | 처리 |
|:--|:--|
| 이 유닛 계약이 없다 | 새로 만든다 |
| 이미 있다 | 그 파일에 추가한다 |
| **다른 유닛이 같은 엔드포인트를 이미 정의했다** | **중단하고 보고한다.** 두 유닛이 같은 API 를 만드는 것이라 **유닛 경계 문제다** |
| 여러 도메인에 걸친다 | 각 도메인 파일에 자기 몫만 넣는다 |

- 계약은 **유닛마다 self-contained** 로 쓴다. 그 규약은 `doc-template` 의 `task-doc` 조각이 정본이다.
- **공유 타입이 반복되는 것은 감수한다** — 파일별로 컴파일하므로 같은 이름의 타입이 유닛마다 다르게 정의돼도 게이트는 못 잡는다. 리뷰의 계약 정합성 점검이 유일한 방어다. **타입 반복은 감수해도 엔드포인트 중복은 감수하지 않는다.**
- **계약 머리에 범위를 적는다**(`내부 전용`·`서비스 간`·`외부 제공`). 표기 규약과 외부 제공 규칙의 정본은 `code-graph` 의 `service-boundary` 조각이다 — 필요하면 그것을 읽는다. **표기가 없으면 내부 전용으로 본다.**
- **LLM 프롬프트도 계약이다** — 바꾸면 출력이 바뀌고, 여러 task 가 공유하고, 이력이 남아야 한다. 계약 폴더에 두고 **출력 형식만 떼어 타입으로** 만든다(그래야 게이트가 검증한다). 코드에 문자열로 박지 않는다.
- 계약과 task 는 M:N 이다 — 어느 task 가 무엇을 쓰는지는 task 문서가 적는다.
- 코드가 유닛 경로를 직접 참조하므로 **유닛 폴더명을 바꾸지 않는다.** 범위가 달라졌으면 유닛을 닫고 새로 만든다.

## 태그를 단다

각 task 에 자기가 **직접 충족하는** 상위 ID 를 단다. 부모는 전이로 추적한다.
어느 파일에 무엇을 적나·`SYS-*` 예외는 `traceability` 의 `tagging` 조각이 정본이다.

- **태그는 기계가 읽는다.** 진입 게이트 훅이 task 의 요구 태그를 보고 소스 쓰기를 판정한다 — 채워지지 않은 자리표시자는 태그가 없는 것으로 본다.

## 교차 검증하고 넘긴다

- task 와 계약의 값(경로·필드·에러코드)이 일치하는지 본다.
- 설계 요소 중 **task 가 없는 것**이 있으면 알린다.
- 기존 로직을 고치는 task 는 회귀 표면을 task 에 명시한다.
- 넘기기 전에 **`gatekeeper` 에게 "설계 요소가 요구를 덮나 · task 가 설계 요소를 덮나 · 계약이 게이트를 통과했나" 를 판정시킨다.** 진행하는 쪽이 자기 산출을 승인하지 않는다.
