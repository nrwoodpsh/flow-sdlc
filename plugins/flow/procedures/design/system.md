# 설계 절차 — 시스템·도메인 레벨

`/flow:design` 이 레벨을 시스템·도메인으로 판정했을 때 읽는다. **도메인당 1회 도는 절차다.**
기능 레벨은 이 파일을 읽지 않는다 — 반복되는 쪽이 이 절차를 같이 싣지 않는 것이 분리한 이유다.

## 분석 — 설계의 근거

- 기존 저장소·API·외부 연동의 **영향**을 능동적으로 찾는다. 넓게 훑을 일이면 `explorer` 에 위임한다.
- repo 이력에서 "모르는 것조차 모르는 것" 을 뽑는다 — 되돌린 커밋·중단된 마이그레이션·우회 미들웨어.
- 결과는 설계 문서의 분석 절에 남긴다: 제약·사각지대·리스크.

## 설계 인터뷰 — 모호할 때만

한 번에 하나씩, **답이 구조를 크게 바꾸는 순서로** 묻는다. 이미 답이 요구·인자·참조에 있으면 건너뛴다.

| 스텝 | sys | domain | 질문 예시 |
|:--|:--:|:--:|:--|
| 구성 | ✓ | | 배포 단위를 어떻게 나눕니까? 각자 어느 도메인·저장소를 맡습니까? |
| 의존 방향 | ✓ | | 금지할 방향이 있습니까? |
| 크로스커팅 | ✓ | | 모든 도메인이 지킬 규칙은? (시각·금액·에러코드) |
| 화면 목록 | ✓ | | *(화면이 있을 때)* 화면이 몇 개쯤 되고 어디서 어디로 갑니까? |
| 측정 수단 | ✓ | | *(성능·원가 요구가 있을 때)* 이걸 재려면 무엇을 어디에 기록해야 합니까? |
| 경계 | | ✓ | 이 도메인이 책임지는 것과 아닌 것은? |
| 용어 | | ✓ | 이 도메인만 쓰는 말이 있습니까? |
| 업무 흐름 | ✓ | ✓ | 시작 신호·갈림길·인계·끝나는 상태는? |
| 유닛 분할 | | ✓ | 이 도메인을 몇 덩어리로 만듭니까? 순서는? |
| 대안 | ✓ | ✓ | 갈리는 안이 있습니까? 제약은? |

- 시스템의 업무 흐름은 **여러 도메인을 가로지르는 것**만이다. 한 도메인 안 흐름은 도메인 레벨에서 묻는다.
- **업무 흐름이 여러 도메인에 걸치면 시스템 레벨로 올린다.** 한 도메인 문서가 남의 흐름을 소유하지 않는다.
- 업무 규칙을 어느 레벨에 두나는 `usecase` 의 `rule-level` 조각이 정본이다. 올린 규칙은 번호로만 가리킨다.

## 산출 — 레벨마다 고유 절이 다르다

| 레벨 | 고유 절 |
|:--|:--|
| 시스템 | 구성 요소(배포 단위 ↔ 도메인 ↔ 저장소 매핑) · 의존 방향 · 크로스 도메인 업무 흐름 · 크로스커팅 규칙 · 화면 지도 |
| 도메인 | 배포 단위 · 경계 · 용어 · 한 도메인 업무 흐름 · **유닛 계획** |

- 그림 표기는 `doc-template` 의 `diagram` 조각이 정본이다. **표기 규칙을 여기 옮겨 적지 않는다.**
- 템플릿에 요구하는 절이 없으면 지어내지 않는다 — `doc-template` 의 `template-gap` 조각을 따라 선택을 받는다.
- 화면 토큰의 정본은 프로젝트 테마 참조다. **설계에서 재정의하지 않는다**(`theme-apply`).

## 화면 지도 — 화면이 있으면 시스템에서 만든다

화면 번호를 **여기서 발급한다.** 유닛이 하나여도 만든다. 발급 규약은 `traceability` 의 `id-system` 조각이 정본이다.

- 지도가 없으면 각 유닛이 1번부터 새로 시작해 **같은 번호가 여러 곳에 생긴다** — 화면 이동을 가리킬 수 없다.
- 시스템 레벨을 건너뛴 프로젝트에 화면을 붙이게 되면 **그때 시스템 설계를 돌려 화면 지도만 만든다.** 유닛 설계에서 발급하지 않는다.
- 지도에는 **무엇이 있고 어디로 가나**만 적는다. 화면별 배치·요소는 유닛 설계가 갖는다.

## 측정 수단 — 잴 코드가 없으면 못 잰다

요구에 `측정 방법` 이 적혀 있어도 **그 데이터를 남기는 코드가 없으면 잴 수 없다.**

| 요구 종류 | 필요한 설계 요소 |
|:--|:--|
| 원가 | **원가 로깅** — 무엇을 어디에 기록하나. 없으면 합산할 데이터가 없다 |
| 성능 | 부하 도구가 붙을 **엔드포인트**. 큐·배치면 **처리 시각 로그** |

- **`측정 방법` 만 채워지고 로깅이 없으면 문서 채점은 통과한다** — 잴 수 있다고 적혀 있고 잴 수 없다. 나중에 영구 gap 이 된다.
- **원가·성능 요구가 있으면 설계 요소를 하나 이상 만들어 태그한다.** 태그가 없으면 `gatekeeper` 가 다음 국면에서 잡는다.
- 크로스커팅이라 한 도메인 것이 아니다 — 시스템 설계 문서에 둔다.

## 유닛 계획 — 도메인의 산출이다

다음 국면이 이 목록을 하나씩 돈다. 비어 있으면 **무엇을 만들지가 없어** 기능 레벨이 진입할 대상이 없다.

- 기준은 템플릿의 유닛 계획 절에 있다 — 혼자 검증되나 · 요구를 덮나 · 번호가 순서인가.
- **번호는 의존 순서로 준다.** 앞 유닛의 산출이 뒤 유닛의 입력이다.
- 사용자가 "알아서 나눠" 라고 하면 **나눠서 제시하고 승인받는다.** 잘못 나눈 위에 유닛을 여럿 쌓으면 되돌릴 게 너무 많다.
- **레거시면 역추출한 현행 요구를 근거로 나눈다.** 요구가 `확인 필요` 여도 유닛은 정할 수 있다 — **이번에 손댈 범위**를 정하는 것이라 현행 확정과 별개다. 손대지 않을 부분은 유닛으로 만들지 않는다.

## 착지

- **시스템·도메인은 여기서 정지한다.** 결과가 참조 정본이 되고, task 로 나누지 않는다.
- 요구 절은 건드리지 않는다 — 자리 나눔은 `/flow:prd` 가 정본이다.
- 새 용어·도메인 경계는 갱신을 제안한다. 확정은 사람이 한다.
- 넘기기 전에 **`gatekeeper` 에게 "설계 요소가 요구를 빠짐없이 덮나" 를 판정시킨다** — `exit.content` 의 `requirement-covered` 다. 설계가 나온 뒤에만 볼 수 있어 끝낼 때 판정한다.
