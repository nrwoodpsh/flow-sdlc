# /flow:verify — 요구 커버리지 감사

`coverage` 범위가 읽는 조각이다. **테스트를 돌리지 않는다** — 추적 축을 대조한다.

통과한 테스트만 보고 "다 됐다" 고 하지 않는다. **애초에 테스트가 없는 요구는 통과 목록에 나타나지도 않는다.**

분류 기준·gap 판정·역추출 요구 면제·고아를 발견한 뒤에 할 일은 **`traceability/coverage` 가 정본이다.** 여기 옮겨 적지 않는다.

## 무엇을 정본으로 대조하나

- 요구 등록소가 정본이다 — 시스템 요구와 도메인 요구 문서(`traceability/coverage` 가 자리를 갖는다).
- 태그를 grep 해 역인덱스를 만든다: `요구 ID → 설계 → task → build → 검증 결과`.
- **본문에서 ID 모양을 grep 하지 않는다** — 태그 자리가 정해져 있다(`traceability/tagging`).

## 대조는 도메인 단위로 묶어 병렬 위임한다

요구별로 나누면 **요구 250개에 에이전트 250개**가 된다.

| 묶는 단위 | 언제 |
|:--|:--|
| **도메인** (기본) | 도메인 8개면 갈래 8개. 한 도메인의 요구·유닛·검증 결과가 한 갈래에 모인다 |
| 유닛 | 한 도메인의 유닛이 너무 많아 한 갈래가 다 못 읽을 때 |
| 횡단 요구는 따로 | 특정 도메인에 안 속한다 — 한 갈래가 전부 본다 |

- **각 갈래는 결론만 돌려준다** — 요구 ID 별 분류와 사유다. 원문을 메인으로 끌어오지 않는다(`default-reference/delegation`).
- **규모를 먼저 알린다.** 대조 전에 몇 개를 몇 갈래로 도는지 제시한다 — 비용이 여기서 정해진다.

```
[/flow:verify coverage] 도메인 8 + 횡단 1 = 9 갈래
   요구 250건 · 유닛 60개 · 문서 약 400개를 읽습니다  → 진행할까요?
```

- **한 갈래가 너무 크면 그 갈래만 유닛으로 다시 쪼갠다.** 전체를 다시 나누지 않는다.

## 결론은 gatekeeper 가 대조한다

분류표가 나오면 `/flow:verify` 의 `게이트` 절이 적은 대로 `gatekeeper` 에 넘긴다 — `entry.content` 의 `coverage-gap` 이다. **감사한 쪽이 자기 결론을 확인하지 않는다.**

- 뒤집힌 항목은 분류를 고치고 **뒤집힌 사유를 함께 적는다.**
- **요구에 적힌 `측정 방법` 을 그대로 실행한다.** 방법을 새로 지어내지 않고, 비어 있으면 그 사실이 사유다 — `/flow:prd` 로 돌려보낸다.

## 어디에 적나

- **그 범위의 통합 결과 파일 안에** 적는다. 커버리지만 담은 별 파일을 만들지 않으면 어느 실행의 결과인지 끊기지 않는다.
- **리포트만 하고 두지 않는다** — 발견마다 갈 곳(요구 소급 발급·코드 제거·기한 붙인 유지)을 함께 낸다. 매 실행이 같은 것을 다시 적으면 노이즈가 된다.
- **판정만 한다.** 요구·코드·테스트를 여기서 고치지 않는다.
