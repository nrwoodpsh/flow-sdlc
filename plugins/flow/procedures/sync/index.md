# /flow:sync — 색인 갱신

색인은 **계산되는 것**이다. 손으로 채우면 다음 `sync` 가 또 바꾼다.

## 무엇을 어디서 계산하나

| 색인 | 무엇으로 계산하나 |
|:--|:--|
| `doc/01.work/README` (상단) | **git 분석** — 브랜치 → 유닛을 묶어 링크한다. 한 브랜치가 여러 도메인의 유닛을 낳으면 그 아래 함께 적는다(교차 도메인이 드러난다) |
| 유닛 `README` | 그 유닛 폴더의 목차. 유닛이 생기면 만든다 |
| `02.decisions`·`03.integration`·`04.ops` 의 `README` | 목록 갱신. 없으면 만든다 |
| 도메인 문서의 `하위 기능` 절 | 태그를 grep 해 계산한다(`traceability/tagging`) — **그 절 밖은 건드리지 않는다** |

**유닛 `README` 의 골격은 넷이다** — 한 줄 소개 · 요구 ID 와 상태와 브랜치 · 단계별 파일 링크.

- 상태값은 `traceability/unit-state` 가 정본이다. 여기서 지어내지 않는다.
- **`2.task` 부터 `7.summary` 까지 폴더 안 파일을 전부 링크한다** — 검증·리뷰·요약은 회차가 쌓인다.
- 담당자 한 명이 소유하므로 충돌하지 않는다.

**안 만드는 곳**: 도메인 폴더(상단 색인이 대신한다) · `00.ref` 하위 · 단계 폴더. **"이 폴더는 X" 라벨 README 를 만들지 않는다.**

## 색인이 머지 충돌하면 손으로 풀지 않는다

계산된 것이라 **다시 돌리면 맞는다.**

```
git checkout --ours doc/01.work/README.md    (--theirs 여도 된다 — 어느 쪽이든)
/flow:sync                                    → 다시 계산해 덮는다
```

- **내용을 섞어 풀지 않는다.** 손으로 합치면 계산 결과와 어긋나 다음 `sync` 가 또 바꾼다.
- **사람이 쓴 문서는 다르다** — 요구·설계·task·ADR 본문은 **정상적으로 머지한다.** 재생성 대상은 위 표의 색인뿐이다.
- 유닛 `README` 는 소유자가 하나라 부딪히지 않는다.

## 왜 계산으로 두나

색인을 손으로 채우면 두 곳(코드 상태와 색인)이 정본이 되고, 어긋난 채로 남는다. **README 는 캐시다** — 상태를 알아야 할 때는 파일을 센다(`traceability/unit-state`).
