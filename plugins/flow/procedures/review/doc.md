# /flow:review — 문서 리뷰

`doc-verify` 에 위임한다. **기준은 그 문서의 템플릿이고, 별도 체크리스트를 만들지 않는다.** 채점 절차는 `doc-verify/scoring`, 절 등급은 `doc-verify/grade`, 같은 값이 두 문서에 있는 것은 `doc-verify/canon-map` 이 정본이다.

```
[/flow:review doc] 대상: {유닛 경로 | 00.ref/ | 02.decisions/ | 04.ops/}
                   기준: 프로젝트 템플릿 (프로젝트가 고친 쪽이 기준이다)
                   기록: {유닛이면 6.review/ · 아니면 리포트만}
```

- **유닛을 넘으면 `explorer` 에 위임한다**(`default-reference/delegation`) — 채점 결과는 FAIL 목록이라 결론만 받으면 된다.
- **무엇이 채점 대상이 아닌가는 `doc-verify` 의 `scoring` 조각이 정본이다** — 계약 파일이 그중 하나다.
- **문서를 고치지 않는다.** 지적만 하고 판단은 사람이 한다.

## 무엇을 대조하나

| 대상 | 무엇으로 |
|:--|:--|
| 유스케이스 · 요구 표 | 입도와 표 칸 규칙(`usecase/granularity`) · 표와 그림의 이름 집합(`usecase/figure-scope`) |
| 업무 규칙 | 규칙을 어느 레벨에 뒀나(`usecase/rule-level`) |
| 요구 ↔ 산출 연결 | 태그 역인덱스와 고아(`traceability/coverage`) |
| 회고 (`04.ops/`) | 조치가 실제로 등록됐나 (아래) |

**전수 채점은 사람이 이 커맨드를 부를 때만 한다.** 게이트의 `gatekeeper` 도 `doc-verify/grade` 를 쓰지만 **그 단계 산출물 하나만** 보고 차단 여부만 판정한다 — 채점하지 않는다.

## 회고 조치가 등록됐는지 본다

회고는 조치를 *어디로 보낸다* 고만 적는다. **아무도 그 커맨드를 안 돌리면 표 한 줄로 남고 같은 장애가 다시 온다**(`ops-doc/postmortem`).

- `어디로` 의 ID 를 요구 등록소와 대조하고, **미등록된 최우선 항목을 맨 앞에** 낸다.
- 등급 판정이 아니다 — 등록 여부의 사실 확인이다.

## 설명 노트가 필요한 시점을 함께 본다

아무 커맨드도 이걸 만들지 않아, 요청이 없으면 영원히 안 생긴다.

| 신호 | 왜 필요한가 |
|:--|:--|
| ADR 이 쌓였는데 설명 노트 자리가 비어 있다 | *"왜 이렇게 돼 있나"* 를 알려면 ADR 을 여러 개 읽어야 한다 — 묶은 문서가 없다 |
| 도메인 문서가 여럿인데 전체를 잇는 글이 없다 | 용어·경계만으로는 그림이 안 보인다 |
| 새 사람이 합류한다 | 읽는 순서가 비어 있다 |

- **제안만 한다.** 채점 항목이 아니고 차단하지 않는다 — 필요를 아는 것은 사람이다.
- 쓰는 것은 `ops-doc` 이 정본이다. **이 커맨드가 문서를 쓰지 않는다.**
