# TDD 검증

AI 환각 방지. **테스트가 물리적으로 통과했는지를 Exit code로 확인**한다. "통과할 것입니다"라는 추론은 검증이 아니다. 실행은 `verifier` 에이전트가 격리 수행한다.

## 절차

### 실패하는 테스트 먼저 (구현 전)

`task`의 `Verification`에 명시된 기준을 **실패하는 테스트**로 변환. "처음엔 실패해야 한다"를 확인해 환각을 차단. **로직·계산·분기가 있는 부분에 한한다** — 단순 배선·설정·UI 텍스트는 생략 가능. 프레임워크는 `workflow.config.json`의 `test` 설정을 따른다(JUnit/pytest/Vitest 등).

**화면 테스트는 설정을 따른다** — 여기서 도구·모드를 정하지 않는다.

| 무엇 | 어디서 정하나 |
|:--|:--|
| 도구 | `test.browser` — `playwright`(기본) 또는 `chrome`. **둘 중 하나는 필수** |
| 창을 띄우나 | `test.headless` — **기본은 `false`(띄운다)**. 사람이 무슨 일이 일어나는지 볼 수 있어야 한다 |

- **headless로 못박지 않는다.** 화면이 깨졌는지는 눈으로만 보인다.

### verifier로 실행

`test.command` 또는 task의 Verification 명령을 `verifier`에게 넘겨 실행. verifier는 통과/실패·근거만 반환.

```jsonc
{ "test": { "command": "npm test" } }   // 또는 "mvn test" / "pytest" 등
```

### 구현↔테스트 루프 (/flow:build, 최대 3회)

```
builder 구현 → verifier 실행
  Exit 0            → 통과, 다음 단계
  Exit ≠ 0 (1·2회차) → 실패 분석 → builder 재수정 → 재실행
  Exit ≠ 0 (3회차)   → 중단, 사람에게 리포트  (자율 무한루프 금지)
```

- 루프 상한은 **3회 고정**. 3회 안에 못 넘기면 멈추고 원인·시도 이력을 보고한다.

### 기록

**두 자리를 나눠 쓴다** — 같은 내용을 두 번 적지 않는다.

| 어디 | 무엇 |
|:--|:--|
| **`{유닛}/5.verify/NN.md`** | **명세·결과·결함의 정본** — 시나리오, 완료 기준 매핑, 기대값 출처, 아티팩트 경로 (`test-spec`·`05.verify`) |
| task `History` | **실행 로그 한 줄** — 언제 무엇을 돌려 몇 회차에 어떻게 됐나 |

```
- {YYYYMMDD HH:MM} — Verification: {명령} → Exit {code}, {회차}/3, {pass/fail 요약}
```

- **실패 케이스의 입력·기대·실제는 `5.verify/`의 `결함` 절에** 적는다. History에 옮기지 않는다.

## 경계

- **테스트를 약화·mock 처리해 통과시키는 것 절대 금지.**
- **기대값을 구현에서 역산하지 않는다** (`test-spec`). 요구의 완료 기준·사후조건·업무 규칙 또는 계약에서만 온다 — **구현을 돌려 나온 값을 기대값으로 적으면 테스트가 코드의 복사본**이 되어 무엇도 검증하지 않는다. 절차 1의 "실패하는 테스트 먼저"가 이걸 막는 장치다.
- **LLM 기능도 Exit code로 판정한다** — 형식·범위·경계는 결정론이고, 흔들리는 것은 **횟수·임계**(예: 10회 중 8회)로 고정한다. 1회 돌려 판정하지 않는다. 규약은 `test-spec`.
- 통합/E2E는 Verification에 명시된 것만 실행. 임의의 무거운 테스트 추가 실행 금지.
- 3회 초과 자율 반복 금지 — 사람 판단으로 넘긴다.
- **실패 원인이 코드인지 환경인지 먼저 가른다.** `command not found`·`Cannot find module`·네트워크 오류·Exit 127은 **코드 문제가 아니다** — **3회 루프에 넣지 않고 즉시 멈추고 `/flow:setup`을 안내**한다. 코드를 고치려 3회를 태우면 아무것도 안 된다(`contract-gate`의 실패 원인 구분과 같은 규칙).
