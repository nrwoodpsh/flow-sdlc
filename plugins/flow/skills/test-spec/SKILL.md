# test-spec — 테스트 명세 표준

테스트를 어떻게 명세·저장하나. 범위는 단위 / 통합 둘.

## 시작 전 확인

**케이스를 만들기 전에 근거가 있는지 본다.** 없으면 지어내게 된다.

| 확인 | 없으면 |
|:--|:--|
| **요구의 완료 기준·사후조건** | **멈춘다** — 기대값의 출처가 없다. `확인 필요`로 남긴다 |
| 요구의 `업무 규칙` (`R`·`DR`·`SYS` 번호) | 경계값 테스트를 건너뛴다. **규칙을 만들어 늘리지 않는다** |
| 계약 (`3.contract/`) | 타입·에러코드 케이스를 못 만든다 |
| **조합 매트릭스** *(`branch`·`project`일 때)* | 요구·계약에서 축과 값을 뽑아 **제안하고 승인받는다.** 승인 전엔 돌리지 않는다 |
| `test.browser` *(화면 테스트일 때)* | 화면은 실제로 클릭해야 한다. 모드가 없으면 물어본다 |
| 앞 범위의 `미검증` 목록 | 첫 실행이다. 있으면 **그것부터 모은다** |
| LLM 호출 상한 *(LLM 기능일 때)* | task `Verification`에 적고 시작한다 |

**구현을 아직 보지 않았다면 그대로 시작한다.** 본 뒤에 기대값을 적으면 역산이 섞인다.

## 단위 (unit) — `/flow:verify unit` · `/flow:build` 루프

- **시나리오+결과를 한 파일**에: `{unit}/5.verify/NN.md` (task의 완료 기준 매핑, 시나리오와 결과를 같이 둠 — 나누지 않음).
- 실행 가능한 **테스트 코드는 `tests/scenarios/`**(source), doc엔 명세+결과.
- `5.verify/NN`은 **task 번호 1:1**. 재실행 시 in-place 갱신(결과는 날짜와 함께).

## 통합 (branch·project) — `/flow:verify branch|project`

- 템플릿 **`14.integration`** — 조합 매트릭스 · 시나리오 · 결과 · 결함 · (프로젝트면) 요구 커버리지가 **한 파일**에.
- **조합 매트릭스 안에서만** 케이스를 만든다 — 매트릭스에 없는 조합을 지어내면 케이스가 무한히 늘어난다.
- 매트릭스는 **축과 값**으로 적는다: `사용자 등급 = 일반·관리자` / `상태 = 정상·잠금·휴면`.

**매트릭스가 없으면 만들되, 승인 없이 쓰지 않는다.** 혼자 하는 프로젝트엔 책임자가 없다 — 그렇다고 통합테스트를 못 도는 것은 아니다.

| 상황 | 어떻게 |
|:--|:--|
| **책임자(PL)가 줬다** | 그 안에서만. 축·값을 늘리지 않는다 |
| **없다** | **요구의 `업무 규칙`·계약의 열거 타입에서 축과 값을 뽑아 제안**하고 승인받는다 |
| 승인 못 받았다 | **돌리지 않는다** — 매트릭스가 케이스 수를 정한다 |

- **뽑는 것과 지어내는 것은 다르다** — 축은 요구·계약에 이미 있는 것만 쓴다. 없는 축(예: `브라우저 종류`)을 추가하지 않는다.
- **제안한 매트릭스를 `14.integration`의 `조합 매트릭스` 절에 적고 출처를 밝힌다** — `제안(승인 20260730)`.
- 결과 위치: 브랜치 통합 `03.integration/00.branch/{브랜치}/` · 프로젝트 E2E `03.integration/01.project/`.
- **화면 테스트는 브라우저를 띄워 실제로 클릭한다.** 모드는 `test.browser`(`playwright` | `chrome`).

## 절차

### 1단계 — 기대값의 출처를 찾는다

**구현을 돌려보고 나온 값을 기대값으로 적지 않는다.** 그러면 테스트가 코드의 복사본이 되어 아무것도 검증하지 않는다.

요구: *"로그인 성공 시 JWT 30분 만료"*

| | 어떻게 | 코드가 틀렸을 때 |
|:--|:--|:--|
| **정상** | 요구를 보고 → `expect(exp).toBe(30*60)` | **FAIL — 잡는다** |
| **역산** | 코드를 돌려봄 → `180` → `expect(exp).toBe(180)` | **PASS — 못 잡는다** |

**AI가 특히 이렇게 하기 쉽다** — 방금 자기가 쓴 구현이라 그 값을 이미 알고 있다.

**출처는 넷뿐이다.**

| 출처 | 무엇 |
|:--|:--|
| 요구의 **완료 기준** | 완료 판정 |
| 요구의 **사후조건** | 끝난 뒤 남는 상태 |
| 요구의 **업무 규칙** | 경계값·예외 대상 |
| **계약** (`3.contract/`) | 타입·에러코드·응답 형식 |

- **출처를 `5.verify/`의 `완료 기준 매핑` 표에 적는다** — 요구 ID 또는 `R번호`. 못 적으면 역산했다는 뜻이다.
- **출처를 못 찾으면 멈춘다.** 요구를 보완하거나 `확인 필요`로 남긴다 — **코드를 보고 채우지 않는다.**
- **"테스트 약화"와 다르다.** 약화는 통과시키려 기준을 낮추는 것이고, 역산은 **처음부터 기준이 코드**인 것이다. 역산은 흔적이 남지 않아 더 위험하다.

### 2단계 — 업무 규칙에서 경계값을 뽑는다

요구의 **`업무 규칙`**(`usecase`)에서 케이스를 만든다. **지어내지 않는다** — 규칙에 적힌 숫자·기간·예외 대상이 곧 경계다.

```
R1. 3회 실패 시 잠금 (관리자는 예외)
```

| 케이스 | 입력 | 기대 | 왜 |
|:--|:--|:--|:--|
| 경계 아래 | 2회 실패 | **통과** — 안 잠김 | 한도 직전은 정상이어야 한다 |
| **경계** | **3회 실패** | **잠김** | 규칙이 정한 지점 |
| 경계 위 | 4회 실패 | 잠김 (이미 잠김) | 넘어도 같은 상태 |
| **예외 대상** | 관리자 3회 실패 | **안 잠김** | 예외를 안 테스트하면 규칙 절반만 검증된다 |

- **규칙 하나에 최소 3케이스** — 경계 아래·경계·예외. 예외 대상이 없으면 둘.
- **`R번호`를 케이스에 적는다** — 어느 규칙을 검증하는지 추적된다.
- **기간·금액도 같다** — `링크 10분 만료` → 9분 통과 / 10분 만료 / 11분 만료.
- **규칙이 없으면 건너뛴다.** 규칙을 만들어 테스트를 늘리지 않는다 — 요구에 없는 것을 검증하면 그건 추측이다.

**기술적 경계와 다르다.**

| | 무엇 | 어디서 나오나 |
|:--|:--|:--|
| 기술적 경계 | 빈 입력 · 초과 길이 · 타임아웃 | 계약(타입·제약) |
| **업무 규칙 경계** | **3회 / 10분 / 관리자 예외** | **요구의 `업무 규칙`** |

### 3단계 — 규칙 레벨로 검증 범위를 가른다

**규칙 번호를 보면 어디서 돌려야 하는지 알 수 있다** (`usecase`).

| 규칙 | 어디 있나 | 어느 범위에서 |
|:--|:--|:--|
| **`R번호`** | 그 유스케이스 상세 | **`unit`** — 유닛 안에서 끝난다 |
| **`DR번호`** | `09.domain` 업무 규칙 | **`branch`** — 그 도메인 유닛들이 모여야 검증된다 |
| **`SYS-*`** | `13.architecture` | **`project`** — 여러 도메인이 얽힌다 |

```
LEAVE-REQUEST-1 휴가 신청·제출
  R1  반차는 반일 단위로만          → unit 에서 검증
  DR-2 3일 이상 2단 결재 (참조)     → branch — approval 유닛이 있어야 한다
  SYS-3 타인 내역 조회 금지 (참조)   → project
```

**`unit`에서 못 돌리는 규칙을 조용히 빼지 않는다.**

| 상황 | 어떻게 |
|:--|:--|
| `R번호`인데 다른 유닛이 필요하다 | **규칙 레벨이 틀렸다** — `DR번호`로 올려야 한다. 그 사실을 리포트한다 |
| `DR번호`·`SYS-*` 참조 | `5.verify/`에 **`미검증(범위: branch)`** 으로 남긴다 |
| 그 범위를 아직 안 돌렸다 | 남아 있는 것이 정상 — **`verify branch`·`project`가 닫는다** |

- **`미검증`을 안 적으면 사라진다** — 유닛 테스트가 다 통과했으니 규칙도 검증된 줄 안다.
- **`verify branch`·`project`는 `미검증`으로 남은 규칙을 먼저 모아 돌린다** — 새로 지어내지 않는다.
- **`branch`를 건너뛰는 프로젝트는 `project`가 `DR번호`도 함께 닫는다.** 혼자 하면 브랜치와 프로젝트의 시점이 같다 — 안 그러면 도메인 규칙이 **영원히 `미검증`으로 남는다.** 닫은 범위를 결과에 적는다(`DR-2 — project에서 검증`).

### 4단계 — LLM 기능은 네 층으로 나눈다

LLM을 부르는 기능은 결과가 매번 다르다. **그래도 대부분은 결정론적으로 테스트된다.**

| 층 | 무엇을 | 판정 | 결정론? |
|:--|:--|:--|:--:|
| **1. 형식** | JSON 파싱되나 · 필수 필드 있나 · 타입 맞나 | Exit code | ✅ |
| **2. 범위** | 값이 정해진 범위 안인가 (예: 대본 60초 ±5초) | Exit code | ✅ |
| **3. 경계** | 빈 입력 · 초과 길이 · 타임아웃 · 부적절 입력 거부 | Exit code | ✅ |
| **4. 품질** | 재미있나 · 자연스럽나 | **사람** | ❌ |

- **1~3층이 대부분이다.** 4층만 사람이 본다 — 요구 `종류`를 `UX·체감`으로 적고 `/flow:verify project`가 `사람 확인 필요`로 분류한다.
- **`tdd-verify`의 "Exit code로 판정" 원칙은 그대로다.**

**흔들리는 것은 횟수와 임계로 고정한다.**

```
10회 돌려 8회 이상 60초 ±5초 → 통과
```

- **횟수와 임계를 요구 완료 기준에 적는다.** 정하면 결정론이 된다 — `8/10`은 Exit code로 판정된다.
- **1회만 돌려 판정하지 않는다.** 우연히 통과하거나 우연히 실패한다.
- 실패한 회차의 **입력·출력을 결함에 남긴다** — 어떤 입력에서 흔들리는지가 단서다.

### 5단계 — 돈 드는 테스트는 상한 안에서만

| 무엇 | 규칙 |
|:--|:--|
| **호출 횟수 상한** | task `Verification`에 적는다 (예: `LLM 10회 · 1회당 약 2원`) |
| **CI에서는 줄인다** | 매 push마다 전액을 쓰지 않는다 — 형식·경계는 mock, 범위는 소수 회차 |
| **원가 요구 검증** | `/flow:verify project`에서만 실제로 돌린다. **몇 편을 만들어 평균을 낼지**는 요구의 `측정 방법`에 있다 |
| **초과하면 멈춘다** | 상한을 넘으면 중단·리포트. 계속 돌리지 않는다 |

- **mock으로는 원가를 못 잰다.** 원가 검증은 실제 호출이 필요하니 **`project` 범위에서만** 한다.
- **비용이 드는 테스트를 사람 승인 없이 반복하지 않는다.**

## 출력 형식

**단위** — `{unit}/5.verify/NN.md` (`05.verify` 템플릿). 시나리오와 결과가 한 파일에 있고, **기대값 출처 칸이 비면 역산이다.**

```markdown
## 판정

결과: FAIL   Pass 3 / Fail 1 / Exit 1
실패: 만료가 3분 (USER-LOGIN-1)

## 완료 기준 매핑

| 시나리오 | 기대 | 기대값 출처 | 결과 |
|:--|:--|:--|:--|
| 2회 실패 | 안 잠김 | R1 | PASS |
| 3회 실패 | 잠김 | R1 | PASS |
| 관리자 3회 | 안 잠김 | R1 (예외) | PASS |
| 토큰 만료 | exp = 1800 | USER-LOGIN-1 완료 기준 | FAIL |

## 미검증

| 규칙 | 범위 | 왜 |
|:--|:--|:--|
| DR-2 | branch | approval 유닛이 아직 없다 |
| SYS-3 | project | 여러 도메인이 얽힌다 |

## 결함

| 무엇 | 입력 | 나온 값 | 기대 |
|:--|:--|:--|:--|
| 만료가 3분 | 정상 로그인 | exp = 180 | 1800 |

## 특이사항

LLM 호출 24회 / 상한 30회 · 약 48원
```

**통합** — `14.integration` 템플릿. `조합 매트릭스`에 **축·값·출처**를 적고, 앞 범위에서 모은 규칙은 **`모아 온 미검증`에 닫았는지까지** 적는다.

```markdown
## 판정

결과: PASS   케이스 6 / Pass 6 / Fail 0 / Exit 0

## 조합 매트릭스

출처: 요구 LEAVE-1 업무 규칙 + 계약 열거 타입 · 제안(승인 20260730)

| 축 | 값 |
|:--|:--|
| 사용자 등급 | 일반 · 관리자 |
| 신청 일수 | 반차 · 1일 · 3일 이상 |

## 결과 상세

| 조합 | 기대 | 기대값 출처 | 결과 |
|:--|:--|:--|:--|
| 일반 · 3일 이상 | 2단 결재로 간다 | DR-2 | PASS |
| 관리자 · 반차 | 1단 | DR-2 예외 | PASS |

## 결함

없다.

## 모아 온 미검증

| 규칙 | 어디서 왔나 | 결과 |
|:--|:--|:--|
| DR-2 | leave/01.request 5.verify | 닫음 — 이 회차 |
| SYS-3 | leave/01.request 5.verify | **못 닫음 — project로 넘김** |
```

`미검증`이 없으면 그 절을 `없다`로 적는다. **지우지 않는다** — 다음 범위가 모아 갈 자리다.

## 경계

- **단위**: `task` 1:1, 시나리오+결과 한 파일 (나누지 않음). **`5.verify/NN`을 task 번호와 다르게 붙이지 않는다** — 스파인 1:1이 깨진다.
- **통합**: 매트릭스 밖 조합·무한 증식 금지. **축을 더하지 않는다** — `브라우저 종류` 하나로 케이스가 배로 는다.
- **구현을 먼저 읽고 기대값을 적지 않는다** — 값을 이미 알면 역산인지 스스로도 구분이 안 된다. **기대값 출처 칸이 비면 역산이다.**
- **`미검증`을 지우지 않는다** — 유닛이 전부 통과해도 도메인 규칙은 안 닫혔다.
- **LLM 기능은 1회 판정 금지** — 횟수·임계를 정해 돌린다. 품질(4층)을 통과로 적지 않는다.
- **돈 드는 테스트는 상한 안에서만.** 초과하면 멈추고 리포트한다.
- **`chrome` 모드에서 모달·확인창을 띄우는 조작을 피한다** — 대화가 멈춘다. 불가피하면 먼저 알린다.
