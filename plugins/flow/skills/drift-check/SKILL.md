# 드리프트 판정

소스가 바뀌었는데 대응 문서가 함께 오지 않았나 확인한다. **여기가 규칙의 정본**이고 git 훅·CI 게이트가 같은 규칙을 쓴다.

## 왜 이걸 보나

문서 주도 워크플로우의 최대 사망 원인은 **문서 드리프트**다. 코드는 고쳤는데 task·계약을 갱신하지 않으면 문서가 거짓말을 시작한다. AI 는 그 낡은 문서를 진실로 믿는다 — **문서가 없느니만 못한 상태**가 된다.

## 어느 조각을 읽나

| 이 상황이면 | 반드시 읽는다 |
|:--|:--|
| 이번 커밋에 드리프트가 있나 **판정한다** | `references/rule.md` |
| 이번 변경에 **계약 파일이 있다** | `code-graph/references/service-boundary.md` — **정본이 거기다** |

계약 범위 알림을 여기 옮겨 적지 않는다. 앞선 판은 같은 개념을 세 스킬에 흩어 놓고 서술을 달리 써서 중복 검사에도 안 걸렸다.

## 경계

- **여기서 하는 것은 차단이 아니라 확인이다.** 오타·주석·설정 같은 사소한 변경까지 동기화를 강요하지 않는다 — 판단은 사용자가 한다.
- **차단은 git 훅과 CI 가 한다.** 이 스킬은 확인까지다.
- **판정 규칙을 여기만 고치지 않는다** — `drift-hook.sh` 와 CI 워크플로를 함께 맞춘다. 어긋나면 "로컬은 통과, CI 는 차단"이 된다.
- **repo 를 넘는 변경을 잡았다고 하지 않는다** — `git diff` 는 한 repo 만 본다.
- 드리프트 방어의 1차 수단은 여전히 `/flow:sync` 다. 이 확인은 "깜빡"을 잡는 백스톱이다.
