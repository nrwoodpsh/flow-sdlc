# 실행과 판정

## 실패하는 테스트 먼저 (구현 전)

task 의 `Verification` 에 적힌 기준을 **실패하는 테스트**로 옮긴다. "처음엔 실패해야 한다"를 확인해 환각을 차단한다.

- **로직·계산·분기가 있는 부분에 한한다** — 단순 배선·설정·UI 텍스트는 생략할 수 있다.
- 프레임워크·명령은 `workflow.config.json` 의 `test` 설정을 따른다.
- **화면은 창을 띄워 본다.** `test.headless` 의 기본값이 `false` 인 것은 화면이 깨졌는지가 눈으로만 보이기 때문이다.

## verifier 로 실행

`test.command` 또는 task 의 `Verification` 명령을 `verifier` 에게 넘긴다. verifier 는 통과·실패와 근거만 돌려준다.

```jsonc
{ "test": { "command": "npm test" } }   // 또는 "mvn test" / "pytest" 등
```

## 구현↔테스트 루프 (최대 3회)

```
builder 구현 → verifier 실행
  Exit 0            → 통과, 다음 단계
  Exit ≠ 0 (1·2회차) → 실패 분석 → builder 재수정 → 재실행
  Exit ≠ 0 (3회차)   → 중단, 사람에게 리포트  (자율 무한루프 금지)
```

- 루프 상한은 **3회 고정**이다. 3회 안에 못 넘기면 멈추고 원인·시도 이력을 보고한다.

## 실패 원인이 코드인지 환경인지 먼저 가른다

`command not found`·`Cannot find module`·네트워크 오류·Exit 127 은 **코드 문제가 아니다.**

- **3회 루프에 넣지 않고 즉시 멈추고 `/flow:setup` 을 안내한다.** 코드를 고치려 3회를 태우면 아무것도 안 된다.
- 같은 이분법을 계약 게이트가 쓴다 — 신호 목록과 오프라인 처리는 `contract-gate` 의 실패 조각이 정본이다.

## 기록

**두 자리를 나눠 쓴다** — 같은 내용을 두 번 적지 않는다.

| 어디 | 무엇 |
|:--|:--|
| **`{유닛}/5.verify/NN.md`** | **명세·결과·결함의 정본** — 시나리오, 완료 기준 매핑, 기대값 출처, 아티팩트 경로 |
| task 의 `History` | **실행 로그 한 줄** — 언제 무엇을 돌려 몇 회차에 어떻게 됐나 |

```
- {YYYYMMDD HH:MM} — Verification: {명령} → Exit {code}, {회차}/3, {pass/fail 요약}
```

- **실패 케이스의 입력·기대·실제는 `5.verify/` 의 결함 절에** 적는다. `History` 에 옮기지 않는다.
- 재실행하면 `5.verify/NN` 을 날짜와 함께 제자리 갱신한다. 파일을 늘리지 않는다.
