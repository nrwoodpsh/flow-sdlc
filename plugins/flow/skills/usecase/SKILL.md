# 유스케이스 작성 규약

유스케이스는 **기능 레벨 요구의 표현 형식**이다. 세 곳에서 쓰이는데 형식이 갈리면 추적이 끊긴다 — 규약을 여기 한 곳에 둔다.

**유스케이스만으로 시스템이 완성되지 않는다.** 비기능·횡단 제약은 `SYS-*`, 경계·용어는 도메인 요구가 맡는다. 여기는 **기능 레벨의 표현**만 정한다.

## 입도 — 하나의 목표 (Cockburn sea-level)

**유스케이스 하나 = 사용자가 한 자리에서 끝내는 하나의 목표.**

| ✕ 너무 잘게 | ✓ 목표 단위 |
|:--|:--|
| `USER-BOARD-1` 게시글 등록 | `USER-BOARD-1` **게시글 작성·게시** |
| `USER-BOARD-2` 게시글 수정 | ↑ 등록·수정·삭제·조회는 **흐름 스텝**으로 |
| `USER-BOARD-3` 게시글 삭제 | |
| `USER-BOARD-4` 게시글 조회 | |

- **엔드포인트 하나 = 유스케이스 하나가 아니다.** CRUD는 유스케이스 하나로 묶는다.
- **실패·예외를 별도 유스케이스로 빼지 않는다.** "로그인 실패 처리"는 목표가 아니라 `로그인`의 예외 흐름이다.
- **판단 기준**: 사용자가 "이걸 하러 왔다"고 말할 수 있나. 못 하면 스텝이거나 예외다.
- **유닛과 대개 1:1**이지만 강제하지 않는다. 유닛 하나에 유스케이스가 둘이면 **유닛이 큰 것**이다.

## 필드

### 표 (전부 채운다)

| 칸 | 규칙 |
|:--|:--|
| ID | `traceability`. 불변·append-only |
| **종류** | **비우면 `기능 제약`.** 이 유스케이스만의 비기능이면 적는다 — `성능`·`보안`·`원가`·`법·정책` |
| 유스케이스 | 목표를 업무 언어로. 기술 용어 금지 |
| 액터 | 주 액터 · 연동 시스템 |
| 주 흐름 | 한 칸 요약 (상세는 아래) |
| 예외 | 한 칸 요약 |
| 완료 기준 | **측정 가능하게.** 못 쓰면 `확인 필요` |
| **측정 방법** | **`종류`가 있는 요구만 채운다** — 기능 제약은 `—`. 비면 **영구 gap**이다. `법·정책`은 `사람 판단 — 자동화 불가` |
| 상태 | `traceability`. 비우면 `확정` |

**`종류`가 있어야 UC 국지 비기능을 등록할 수 있다.** Cockburn은 `Special Requirements`를 유스케이스 안에 두지만, 우리는 **별도 요구로 등록**한다 — ID가 있어야 `/flow:verify project` 커버리지에 나오고 측정 방법을 붙일 수 있다.

```
| ID           | 종류 | 유스케이스         | … | 완료 기준 | 측정 방법            |
| USER-LOGIN-1 |      | 이메일 로그인      | … | JWT 30분  | —                    |   ← 기능 제약
| USER-LOGIN-3 | 성능 | 로그인 응답 3초 내 | … | p95 3초   | k6 50 VU 3분 · p95   |   ← 국지 비기능
```

**`측정 방법`은 별도 칸이다** — 완료 기준 칸에 `측정: …`으로 뭉치지 않는다. 뭉치면 `doc-verify`가 "측정 방법 미정"을 판정할 수 없고 `verify project`가 영구 gap으로 낸다.

- **시스템 횡단이면 `SYS-*`다.** "모든 API는 JWT"는 여기가 아니다.

### 상세 절 — 조건부 필수

**둘 중 하나라도 해당하면 쓴다.**

| 조건 | 왜 |
|:--|:--|
| **업무 규칙이 있다** | 규칙이 없으면 경계값 테스트를 도출할 근거가 없다 |
| **예외 흐름이 둘 이상이다** | 표 한 칸에 안 들어간다 |

둘 다 아니면 **표 한 줄로 끝낸다.** 자명한 조회에 문서를 쓰지 않는다.

상세 절 필드:

| 필드 | 언제 |
|:--|:--|
| **시작 신호** | **액터가 사람이 아닐 때만** — 배치·스케줄·이벤트 수신. 사용자 행동이면 주 흐름 1스텝이 곧 그것이라 **생략** |
| 사전조건 | 항상 |
| 주 흐름 | 항상. 한 스텝에 한 동작, 현재형 평서문 |
| 대안 흐름 | 있으면 |
| 예외 흐름 | 있으면 |
| 사후조건 | 항상 — **무엇이 남는가**. 테스트의 assert 대상 |
| **업무 규칙** | **있으면 필수** — 아래 |

### 업무 규칙 — 경계값 테스트의 근거

```
- 업무 규칙:
    R1. 3회 실패 시 잠금 (관리자는 예외)
    R2. 휴면은 1년 미접속
```

- **규칙마다 `R번호`를 단다.** 테스트가 어느 규칙을 검증하는지 가리킬 수 있어야 한다.
- **숫자·기간·예외를 명시한다.** "여러 번 실패하면"은 규칙이 아니다.
- `test-spec`이 이걸 읽어 **경계값**을 만든다 — 2회 통과 / 3회 잠김 / 관리자 3회 안 잠김.
- **완료 기준과 다르다.** 완료 기준은 *"이 유스케이스가 끝났나"*, 업무 규칙은 *"어떤 조건에서 어떻게 되나"*다.

### 규칙은 걸리는 범위의 레벨에 적는다

**여기(유스케이스)에 남의 규칙을 적지 않는다.** 여러 곳에 복사되면 한쪽만 고쳐져 어긋난다.

| 규칙이 걸리는 범위 | 어디 | ID |
|:--|:--|:--|
| **이 유스케이스 하나** | 여기 — 상세 절 | `R번호` |
| 이 도메인의 여러 유스케이스 | `09.domain`의 **업무 규칙** 절 | **`DR번호`** |
| 여러 도메인 | `13.architecture`의 `SYS-*` | `SYS-번호` |

**판별**: *"다른 유스케이스에도 이 규칙이 걸리나?"* → 걸리면 올린다.

```
LEAVE-REQUEST-1 휴가 신청·제출
- 업무 규칙:
    R1. 반차 신청은 반일 단위로만 고를 수 있다     ← 이 UC만
    참조: DR-2(3일 이상 2단 결재)                ← approval 소관 · 복사 안 함
    참조: SYS-3(타인 내역 조회 금지)
```

- **올린 규칙은 `참조:`로 적고 번호만 가리킨다.** 내용을 옮겨 적지 않는다.
- **다른 도메인의 규칙을 참조할 때도 같다** — 결재 단수는 `approval`의 `DR-*`이고 `leave`는 참조만 한다.
- **`test-spec`이 레벨을 보고 검증 범위를 정한다** — `R번호`는 `unit`, `DR번호`·`SYS-*`는 도메인을 넘을 수 있어 `branch`·`project`다.

## 작성 순서

한 번에 하나씩 묻는다. 인자·참조에 답이 있으면 건너뛴다.

| 스텝 | 묻는 것 |
|:--|:--|
| 1 액터 | 누가·무엇이 쓰나. 주 액터와 연동 시스템을 나눠서 |
| 2 목표 | 각 액터가 **한 자리에서 끝내려는 것**은 무엇인가 (= 유스케이스) |
| 3 흐름 | 그 목표를 어떤 순서로 이루나 |
| 4 예외 | 정상 흐름 밖에 무엇이 있나 |
| 5 규칙 | 판정 기준·한도·예외 대상이 있나 (숫자로) |
| 6 완료 기준 | 무엇이 되면 완료인가 (측정 가능하게) |

- **2를 먼저 확정한다.** 목표가 흔들리면 3~6이 전부 흔들린다.
- **추측으로 채우지 않는다.** 모르면 `확인 필요`로 남긴다.

## 관계 표기 (그림)

**표기는 PlantUML만 쓴다** — 정본은 `doc-template`의 다이어그램 절.

| 관계 | 표기 | 방향 |
|:--|:--|:--|
| 연관 (액터가 쓴다) | `--` 실선·화살촉 없음 | 방향 없음 |
| `«include»` (항상 포함) | `..>` 점선·열린 화살촉 | **base → 포함 UC** |
| `«extend»` (조건부 확장) | `..>` 점선·열린 화살촉 | **확장 UC → base** |
| 일반화(상속) | **쓰지 않는다** | — |

- `«include»`·`«extend»` 둘 다 **의존(dependency)** 이라 점선 + 열린 화살촉이고, **화살촉은 가리키는 대상 쪽**이다.
- **관계를 남발하지 않는다.** 대부분의 유스케이스는 액터-UC 연관뿐이다. 두 유스케이스가 같은 절차를 공유할 때만 `«include»`를 쓴다.

## 정본 분담 · 대조

**각자 자기 것만 갖는다. 중복이 없으면 드리프트도 없다.**

| 무엇 | 정본 |
|:--|:--|
| UC 목록 · 액터 · 종류 · 완료 기준 · 상태 | **표** |
| **관계** (`«include»`·`«extend»`) | **그림** |
| 흐름 · 조건 · 업무 규칙 | **상세 절** |

**대조는 이름 집합으로 한다** (`doc-verify`).

**먼저 그림 대상을 가른다** — 표의 모든 행이 그림에 올라가는 것이 아니다.

| 표의 행 | 그림 대상 | 왜 |
|:--|:--|:--|
| `종류`가 비어 있고(기능 제약) **액터가 있다** | **✅ 대상** | 액터가 무엇을 하는 것이라 그릴 수 있다 |
| `종류`가 `성능`·`원가`·`법·정책` | ❌ 아니다 | **액터도 흐름도 없다** — 제약이라 그릴 것이 없다 |
| `종류`가 `보안` | 액터가 있으면 대상 | "관리자만 조회"는 그려지고, "전송 구간 암호화"는 안 그려진다 |
| `상태: 확인 필요` (역추출) | ❌ 아니다 | 현행 동작 기록이다. 손댈 때 `확정`으로 바뀌면 그때 그린다 |

```
그림 대상 행의 UC 이름  ↔  그림의 usecase 이름
그림 대상 행의 액터     ↔  그림의 actor 이름

  그림에만 있는 UC        → 표 반영 누락
  그림 대상인데 그림에 없음 → 그림 미갱신
  없는 이름을 가리키는 관계 → 오타
```

- **관계는 대조하지 않는다** — 그림이 정본이라 대조할 짝이 없다.
- **그림 대상이 아닌 행이 그림에 없는 것은 정상이다.** 그걸 누락으로 적으면 리포트가 거짓말이 된다.
- 어긋나면 **지적만** 한다. 어느 쪽이 맞는지는 사람이 정한다.

## 경계

- **유스케이스를 엔드포인트 단위로 쪼개지 않는다.** CRUD는 하나다.
- **실패·예외를 별도 유스케이스로 빼지 않는다** — 예외 흐름이다.
- **업무 규칙을 완료 기준에 섞지 않는다.** 완료 기준은 완료 여부, 규칙은 판정 조건이다.
- **횡단 제약을 유스케이스에 넣지 않는다** — `SYS-*`다.
- **그림에 표에 없는 유스케이스를 넣지 않는다.** 반대도 안 된다.
- **상세 절을 조건 없이 쓰지 않는다** — 자명한 것에 문서를 늘리면 다음 국면이 그걸 다 읽는다.
- **역추출(`legacy`)은 전부 `상태: 확인 필요`**. 코드가 하는 일을 옮긴 것이라 완료 기준·측정이 비어도 된다.
