# 운영·설명 문서

개발 파이프라인(`prd → design → spec → build`)이 만들지 않는 문서를 쓴다. **사람이 읽는 문서**라 골격이 흔들리면 못 쓴다 — 템플릿을 강제한다.

## 절차

**1. 유형·착지 선언**

```
[ops-doc] 유형: {장애 회고 | 운영 절차 | 설명 노트}
          템플릿: 00.ref/03.templates/{NN.유형}/
          착지: {경로}
```

**2. 근거 확보** — 무엇을 보고 쓰나.

| 유형 | 근거 |
|:--|:--|
| 장애 회고 | 로그·알람·배포 이력·`git log`. **시각은 추정하지 않는다** |
| 운영 절차 | 실제 명령·스크립트·CI 설정. 사람이 아는 권한·담당은 **물어본다** |
| 설명 노트 | 코드·`00.ref/`·ADR. 새 결정을 하지 않는다 |

**3. 작성** — 템플릿 절을 그대로 따른다. 근거가 없는 칸은 비우지 말고 **`(근거 자료에 없음)`**, 애매하면 **`[NEEDS CLARIFICATION]`**.

**4. 빠진 것 보고** — 무엇을 못 채웠고 누구에게 물어야 하는지 함께 낸다.

## 유형별 주의

- **장애 회고** — 사람을 탓하지 않는다. `근본 원인`은 증상과 구분한다("서버가 죽었다"는 증상). **재발 방지에 근본 원인과 닿는 항목이 하나도 없으면 회고가 끝난 게 아니다.**
  - **재발 방지 조치마다 `어디로`를 적는다** — `SYS-*` 요구 / 크로스커팅 규칙 / `DR번호` / `run fix` / SOP / ADR. **비우면 조치가 `04.ops/`에 갇혀 아무도 안 본다.**
  - **여기서 요구·규칙을 직접 쓰지 않는다.** 회고는 기록이고 등록은 그 커맨드가 한다 — 가는 곳만 적는다.
  - **적어둔 것으로 끝나지 않는다** — `/flow:review doc 04.ops/`가 `어디로`의 ID가 요구 등록소에 실제로 있는지 대조한다(`doc-verify`). **`P1`이 미등록이면 회고가 닫히지 않았다.**
- **운영 절차** — 따라 하면 되는 문서다. `되돌리기`가 없으면 **"되돌릴 수 없음"이라고 분명히** 적는다.
  - **`담당` 표에 `사람만`을 표시한다** — 운영 반영·권한 부여·과금·데이터 삭제. **표시가 없으면 AI가 실행해도 되는 단계로 읽힌다.**
  - 나중에 "이 절차대로 해줘"라는 요청이 오면 `/flow:ask`가 이 표시를 보고 가른다.
- **설명 노트** — 왜 이렇게 돼 있는지가 본체다. 관련 ADR을 링크한다.
  - **ADR을 묶는 것이 주 목적이다.** 결정이 쌓이면 *"왜 이렇게 돼 있나"* 를 알려고 ADR을 여러 개 읽어야 한다 — 그걸 한 글로 잇는다. `어디에 이어지나`·`더 볼 것` 절이 그 자리다.
  - **`doc/README`의 읽는 순서 5단계**가 이 문서다. 비어 있으면 새 사람이 4에서 8로 건너뛴다.
  - **부르는 곳이 없다** — 파이프라인이 만들지 않는다. `/flow:review doc`이 *"ADR은 쌓였는데 설명 노트가 없다"* 를 제안하고, 사용자가 직접 요청할 수도 있다.

## 경계

- **근거에 없는 걸 지어내지 않는다.** 특히 장애 시각·담당자·권한 — 모르면 물어보거나 `(근거 자료에 없음)`.
- **코드를 고치지 않는다.** 문서만 쓴다.
- **결정하지 않는다** — 설명 노트가 새 규칙을 만들면 그건 ADR(`/flow:design`)로 가야 한다.
- **파이프라인 문서를 이걸로 쓰지 않는다.** 요구·설계·task는 각 커맨드가 쓴다.
- 커밋하지 않는다 — `/flow:commit`은 사람이.
