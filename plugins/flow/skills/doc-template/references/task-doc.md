# task 문서

**task 는 실행 지시서다** — "무엇을 만드나"만 담는다. 판단은 상위 문서에 있다.

**완료 기준·구조·결정·화면·타입을 task 에 복사하지 않는다.** 각각 정본이 따로 있고 task 는 **ID 로 가리킨다** — 어느 값이 어디 사는지는 `doc-verify` 의 정본 지도에 있다.

frontmatter 에 **덮는 요구·설계 ID** 를 태그하고(`traceability` 의 태깅 조각), 본문은 아래 절로 쓴다.

| 절 | 무엇 |
|:--|:--|
| 사용 계약 | 이 task 가 쓰는 계약과 그 부분. 계약은 공유(M:N)라 여기서 추적한다 |
| Logic | 구현 수준의 알고리즘·계산식·쿼리. 구조·책임은 설계도에 있다 |
| File Map | `[New]`·`[Mod]` 파일 경로 — 기계적으로 적는다 |
| Verification | 검증 **명령과 통과 조건**. 완료 기준 자체는 요구 문서에 있다 |
| History | 변경 이력. 계획 이탈은 **Deviation** 으로 기록 |

**`File Map` 이 소스→유닛 매핑의 정본이다.** 기계 게이트가 이 줄을 읽어 "이 소스를 담은 task 문서가 있나"를 판정한다(`flow.topology.json` 의 `gate` 절). 비면 게이트가 유닛을 못 찾는다.

## 산출 위치

`doc/01.work/{도메인}/{유닛}/2.task/NN.name.md`

- `{도메인}` — 기능 영역 (예: `user`·`order`)
- `{유닛}` — 한 덩어리 작업. 번호 폴더 (예: `00.login`)
- `NN.name` — 스파인 번호 두 자리 + kebab-case 이름. **번호가 폴더 안 순서를 고정한다.**
- **날짜 접두어를 붙이지 않는다** — task 는 번호로 정렬한다. 날짜는 시간축이 중요한 곳(ADR·분석)만 쓴다.
- **같은 파일을 덮어쓰지 않는다.** 변경은 `History` 에 사유와 함께 남긴다.

## 계약은 유닛마다 자기 것을 갖는다

`3.contract/{도메인}.ts` 를 **self-contained** 로 쓴다 — 그게 단일 파일 게이트의 전제다(`contract-gate`).

- 어느 task 가 무엇을 쓰는지는 `사용 계약` 절에서 추적한다.
- **같은 엔드포인트를 두 유닛이 정의하면 유닛 경계 문제다.**
- **LLM 프롬프트도 계약이다** — `3.contract/{도메인}.prompt.md`. 바꾸면 출력이 바뀌고 여러 task 가 공유한다. 출력 형식은 타입으로 떼어 게이트가 검증한다.

## 경계

- **상위 문서를 복사해 오지 않는다.** 옮겨 적으면 고칠 곳이 둘이 된다 — **ID 로 가리킨다.**
- **계약 파일과 중복 작성 금지** — 타입·엔드포인트·에러코드는 계약만 갖는다. **필드명만 나열하면 FE 와 BE 가 다르게 해석한다.**
- **BE 와 FE 를 한 task 에 넣지 않는다** — 그건 task 가 크다는 뜻이다.
- **버그 수정은 한 줄이어도 task 를 만든다** — "너무 작다" 기준은 신규 기능을 쪼갤 때의 것이다.
- **frontmatter 태그는 직접 충족만** — 부모 요구는 전이로 추적된다.
