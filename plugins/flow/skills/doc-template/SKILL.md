# task 문서 템플릿

설계 문서의 표준 구조 강제. 누가 쓰든 동일 골격 위에서만 문서를 만든다.

## 절의 등급 — 모든 템플릿 공통

템플릿의 절마다 등급이 붙는다. **`doc-verify`가 이 표기로 판정 강도를 정한다.**

| 등급 | 표기 | 뜻 | 안 채우면 |
|:--|:--|:--|:--|
| **진행 필수** | `**[진행 필수]**` | 다음 커맨드가 **이 내용을 소비**한다 | `doc-verify` FAIL · **`gatekeeper` 차단** |
| **문서 필수** | `**[문서 필수]**` | **업계 표준이 요구**한다(DDD·arc42·ISO 42010·UML·ISO 29119) | `doc-verify` FAIL · **차단은 안 함** |
| 선택 | 표기 없음 · `*(선택)*` · `*(해당 시)*` | 있으면 좋다 | 표시만 |

- **표기가 없으면 선택**이다. 기본값이 선택이라 새 절을 추가할 때 부담이 없다.
- **프로젝트가 절을 더해도 된다** — 그 프로젝트만의 것(규제 근거·정산 대조·밸런스 지표 등)은 표기 없이 넣는다. 채점 대상이 아니다.
- **등급을 커맨드가 바꾸지 않는다.** 템플릿에 적힌 것을 따른다.

## 정본 위치

프로젝트의 `doc/00.ref/03.templates/02.task-doc/task-template.md` (프로젝트가 소유·조정). 이 스킬은 **링크·규약** 역할만.

## 산출 위치

`doc/01.work/{도메인}/{work-unit}/2.task/NN.name.md`

> 계약은 `3.contract/{도메인}.ts` — **유닛마다 자기 것을 갖고 `self-contained`로 쓴다**(`contract-gate` 전제). 어느 task가 무엇을 쓰는지는 아래 `사용 계약` 절에서 추적한다. **같은 엔드포인트를 두 유닛이 정의하면 유닛 경계 문제**다.
> **LLM 프롬프트도 계약이다** — `3.contract/{도메인}.prompt.md`. 바꾸면 출력이 바뀌고 여러 task가 공유한다. 출력 형식은 `.ts`에 타입으로 떼어 `contract-gate`가 검증한다.

- `{도메인}` — 기능 영역 (예: `user`, `order`)
- `{work-unit}` — 한 덩어리 작업 (번호 폴더, 예: `00.login`)
- `2.task/` — work-unit 안의 **설계 단계** 폴더 (0.requirement~7.summary 중)
- `NN.name` — task-spine 번호(2자리) + kebab-case 이름. **번호가 폴더 안 순서를 고정**한다.
- **날짜 접두어 안 붙임** — task는 번호로 정렬. 날짜 접두어는 시간축이 중요한 곳(ADR·analysis)만.
- **충돌·재작업** — 같은 파일을 덮어쓰지 않는다. 변경은 문서 안 `History`에 사유와 함께 남긴다.

## 다이어그램 표기 (정본)

**모든 그림은 PlantUML로 그린다.** 여기가 정본이다 — 커맨드·템플릿이 이 규약을 따른다.

````
```plantuml
@startuml
!pragma layout smetana
…
@enduml
```
````

- **`!pragma layout smetana`를 첫 줄에 넣는다.** Graphviz 없이 렌더된다 — 설치 부담을 없앤다. 시퀀스·활동에는 불필요하지만 넣어도 무해하니 **전부 넣어 규칙을 하나로** 둔다.
- **mermaid를 쓰지 않는다.** UML 유스케이스 다이어그램 타입이 없어 플로차트로 흉내야 하고, 그러면 액터와 유스케이스가 시각적으로 구분되지 않는다.

**무엇을 무엇으로 그리나**

| 대상 | 표기 | 어디 |
|:--|:--|:--|
| 유스케이스 | `usecase` + `actor` + `rectangle` | `00.requirement` |
| 데이터 구조 (관계형) | `entity` + `hide circle` + 까마귀발(`\|\|--o{`) | `01.design` |
| 데이터 구조 (그래프) | `object` | `01.design` |
| 처리 흐름 (시간 축) | 시퀀스 — `actor`·`participant`·`database` | `01.design` |
| 업무 흐름 (분기) | 활동 — `start`·`if…then…else`·`stop` | `09.domain`·`13.architecture` |
| 구성 요소·배포 단위 | `component` + `database` | `13.architecture` |

- **업무 흐름이 여러 도메인을 지나면 `partition`으로 감싼다** — 어느 단계가 누구 책임인지 그림에서 읽힌다.

**표와 그림의 정본이 나뉘는 곳이 있다.** 유스케이스가 그렇다 — **무엇이 표고 무엇이 그림인지는 `usecase`가 정한다.** 여기 옮겨 적지 않는다.

- **각자 자기 것만 가지면 중복이 없고, 중복이 없으면 드리프트도 없다.**
- 그 밖의 그림(ERD·시퀀스·활동·컴포넌트)은 **표·본문의 산출물**이다. 새 정보를 넣지 않는다 — 어긋나면 **글이 맞다.**
- **렌더는 선택이다.** 텍스트만으로도 읽히고, 표↔그림 대조도 텍스트로 한다. 그림을 보려면 편집기 확장 하나면 된다(`presets/tools`).

**밖으로 내보낼 때는 이미지가 필요하다.** PlantUML을 렌더하는 곳이 적다.

| 어디 | PlantUML |
|:--|:--|
| 편집기 (확장 설치 후) | ✅ |
| **Notion** · **docx·pdf** · GitHub 웹 | ❌ **코드 텍스트로 보인다** |

- **`/flow:publish`가 이미지로 렌더해 올린다**(절차 3-1) — 못 하면 그 사실을 알린다.
- **`doc/`의 정본은 텍스트다.** 이미지는 발행물에만 넣고 원본 코드블록을 지우지 않는다.

## 템플릿에 없는 절을 요구할 때

**커맨드가 새 절을 요구하는데 프로젝트 템플릿에 그 절이 없을 수 있다.** 플러그인이 올라갔는데 템플릿을 동기화하지 않은 경우다.

```
/flow:prd func   →  "업무 규칙을 적으시겠습니까?" (새 규칙)
                 →  프로젝트 템플릿에 그 절이 없다
                 →  어디에 쓰나?
```

| 하지 말 것 | 할 것 |
|:--|:--|
| 절을 조용히 지어내 추가한다 | **알리고 선택을 받는다** |
| 절이 없으니 그 내용을 버린다 | 버리면 규칙이 작동하지 않는다 |

```
ℹ️ `업무 규칙` 절이 프로젝트 템플릿(00.requirement)에 없습니다.
   템플릿이 flow 0.8.0 기준이고 이 규칙은 0.9.0에서 추가됐습니다.
   ① 이 문서에만 절을 추가하고 진행    ② 템플릿부터 동기화 (/flow:setup)
```

- **①을 고르면 이 문서에만 절을 넣고 진행한다.** 템플릿은 안 건드린다 — 그건 `/flow:setup`의 일이다.
- **②를 고르면 멈춘다.** 동기화 후 다시 부른다.
- **`doc-verify`가 그 절을 채점하지 않는다는 사실을 함께 알린다** — 템플릿이 기준이라 절이 없으면 채점 대상이 아니다.
- **반대 경우(템플릿에 있는데 커맨드가 안 쓰는 절)는 건드리지 않는다.** 프로젝트가 추가한 절일 수 있다 — 채점도 하지 않는다(`doc-verify`).

## 표준 섹션 (필수)

**task는 실행 지시서다** — "무엇을 만드나"만 담는다. 판단은 상위 문서에 있다.

**완료 기준·구조·결정·화면·타입을 task에 복사하지 않는다.** 각각 정본이 따로 있고 task는 **ID로 가리킨다** — 어느 값이 어디 사는지는 `doc-verify`의 정본 지도에 있다.

frontmatter에 **덮는 요구·설계 ID**를 태그하고, 본문은 아래 절로 쓴다.

1. **사용 계약** — 이 task가 쓰는 계약과 그 부분. 계약은 공유(M:N)라 여기서 추적한다.
2. **Logic** — 구현 수준의 알고리즘·계산식·쿼리. 구조·책임은 설계도에 있다.
3. **File Map** — `[New]`·`[Mod]` 파일 경로 (기계적)
4. **Verification** — 검증 **명령과 통과 조건**. 완료 기준 자체는 요구 문서에 있다.
5. **History** — 변경 이력. 계획 이탈은 **Deviation**으로 기록

## 경계

- **상위 문서를 복사해 오지 않는다.** 완료 기준·설계 결정·화면을 task에 옮겨 적으면 고칠 곳이 둘이 된다 — **ID로 가리킨다.**
- **계약 파일과 중복 작성 금지** — 타입·Endpoint·에러코드는 계약(`3.contract/`)만. 계약이 답할 것(검증 규칙·에러 status·페이징 기준·FE 상태)은 `03.api-contract` 템플릿 헤더에 있다. **필드명만 나열하면 FE/BE가 다르게 해석한다.**
- **BE와 FE를 한 task에 넣지 않는다** — 그건 task가 크다는 뜻이다. `/flow:spec`의 입도 기준을 따라 쪼갠다.
- **버그 수정은 한 줄이어도 task를 만든다** — "너무 작다" 기준은 신규 기능을 쪼갤 때의 것이다(`/flow:spec`).
- **frontmatter 태그는 직접 충족만** — 부모 요구는 전이로 추적된다(`traceability`).
- 설계 변경·이탈은 History에 **사유를 자연어로** 기록. 단순 덮어쓰기 금지.
- **이 스킬은 섹션 골격(구조)만 강제**한다. 문장 가독성은 짝을 이루는 `plain-writing`(쉬운 말)이 맡는다.
