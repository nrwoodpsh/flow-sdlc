# 추적 축 (레벨 · 라우팅 · ID)

레벨이 정해지면 **저장 위치·파이프라인 깊이·ID 형식이 동시에** 결정된다. 이 규약을 한 곳에 두어 커맨드마다 경로 표가 어긋나는 것을 막는다.

## 레벨 판별

**판정 질문은 하나다.**

> **"도메인을 하나 더 추가하면 이 요구가 거기에도 걸리나?"**
> **걸린다 → 시스템.** 안 걸린다 → 그 도메인. work-unit 하나에서 끝나면 → 기능.

| 레벨 | 무엇 | 예 |
|:--|:--|:--|
| 시스템 (`sys`) | 기술 구조 · **횡단 제약** | "모든 API는 JWT" · "모든 작업은 p95 200ms" · "MSA 구성" |
| 도메인 (`domain`) | 비즈니스 구조 — 경계·엔티티·용어 | "회원은 가입·로그인·탈퇴한다" |
| 기능 (`func`) | work-unit | "이메일 로그인" |

**"여러 도메인에 걸치나"로 묻지 않는다.** 도메인이 하나뿐인 프로젝트에서 답할 수 없고, 도메인이 늘 때마다 판정이 뒤집혀 **ID를 다시 매겨야 한다**(`append-only` 위반).

| 요구 | 새 도메인이 생기면 | 레벨 |
|:--|:--|:--|
| "모든 출력은 UTF-8" | **걸린다** | **`SYS-*`** |
| "마크다운 표를 PDF 표로 변환한다" | 안 걸린다 | `CONVERT-*` |
| "변환은 10초 내" | 안 걸린다 (그 도메인 것) | `CONVERT-*` |
| "**모든** 작업은 10초 내" | 걸린다 | **`SYS-*`** |

- **마지막 두 줄이 요점이다** — 같은 성능 요구가 **범위를 어떻게 쓰느냐**로 갈린다.
- **`SYS-*`가 0개여도 정상이다.** 작은 도구에 횡단 제약이 없으면 시스템 요구가 없다 — 억지로 만들지 않는다.
- **착지처가 곧 판별**이다 — 아키텍처 문서에 들어갈 내용이면 시스템, 도메인 경계·용어면 도메인.

## 라우팅 (레벨 → 위치 · 깊이)

| 레벨 | 요구 (`/flow:prd`) | 설계 (`/flow:design`) | 이후 | ID |
|:--|:--|:--|:--|:--|
| 시스템 | `00.ref/00.architecture/00.requirement.md` | `00.ref/00.architecture/01.design.md` | **정지** | `SYS-N` |
| 도메인 | `00.ref/01.domain/{도메인}.md` §요구 | 같은 파일 §경계·용어 | **정지** | `{도메인}-N` |
| 기능 | `01.work/{도메인}/{NN.유닛}/0.requirement.md` | `…/1.design.md` | `/flow:spec`→`/flow:build`→… | `{도메인}-{유닛}-N` |

- 시스템·도메인은 **구현 없이 ref 정본으로 착지**한다(`/flow:spike`가 지식만 남기는 패턴과 같다).
- `/flow:spec`을 시스템·도메인 레벨에서 호출하면 **거부하고 안내**한다.
- 도메인이 커지면 폴더 승격 허용: `01.domain/user/00.requirement.md`·`01.design.md`.

## ID 체계 (2층)

**한 문서 안에서 쪼개지는 것에만** ID를 준다. task 이하는 **파일 경로가 곧 ID** — 별도 번호를 만들지 않는다.

| 층 | 형식 | 예 | 범위 |
|:--|:--|:--|:--|
| 요구 | 위 표 | `SYS-1` · `USER-3` · `USER-LOGIN-1` | 전역 |
| 설계 요소 | `D-N` | `D-1` | 문서 내 로컬 (전역 지칭은 `user/00.login#D-1`) |
| **화면** | **`SCR-N`** | `SCR-1` · `SCR-12` | **전역** — 아래 |
| task·build·verify | — | `2.task/00.login-api.md` | 경로가 ID |

**화면은 왜 전역인가** — `D-N`과 다르다.

| | 참조 범위 |
|:--|:--|
| `D-N` 설계 요소 | 같은 유닛의 task만 가리킨다 → **로컬로 충분** |
| **`SCR-N` 화면** | **화면 이동이 유닛·도메인을 넘는다** — 로그인(`admin/00.login`)에서 대시보드(`admin/01.dashboard`)로 간다 |

- **유닛마다 `SCR-1`부터 시작하면 안 된다.** 같은 번호가 여러 곳에 생겨 이동을 못 가리킨다.
- **발급은 `13.architecture`의 `화면 지도`에서** 한다 — 거기가 화면 목록의 정본이다. `01.design`은 발급받은 번호를 쓴다.
- **FE가 없는 프로젝트는 이 ID를 쓰지 않는다.**

**이름 → ID 만들기**

**번호를 떼고 대문자로.** 하이픈은 그대로 둔다.

| 레벨 | 어디서 따오나 | 예 |
|:--|:--|:--|
| 시스템 | 고정 | `SYS-1` |
| 도메인 | `01.domain/{도메인}.md`의 **도메인 이름** | `collect.md` → `COLLECT-1` |
| 기능 | `01.work/{도메인}/{NN.유닛}/`의 **도메인 + 유닛** | `shorts/00.script-gen/` → `SHORTS-SCRIPT-GEN-1` |

- **번호는 항상 마지막 조각**이다. 첫 조각이 도메인, 가운데가 전부 유닛 이름 — 하이픈이 몇 개든 이 규칙으로 갈린다.
- 폴더·파일 이름을 바꿔도 **ID는 안 바꾼다**(불변). 새 이름은 다음 것부터 적용된다.

**이름은 짧게 짓는다** — ID 길이가 여기서 정해진다.

| 권장 | 피할 것 |
|:--|:--|
| 한 단어 — `login` · `collect` · `upload` | 세 단어 이상 — `daily-report-generator` |
| 두 단어까지 — `script-gen` | 서술형 — `make-shorts-from-report` |

- **약칭을 만들지 않는다.** `SHORTS-SCRIPT-GEN-1`이 길다고 `SSG-1`로 줄이면 무엇의 약자인지 아무도 모르고, 폴더↔ID 매핑표가 또 생긴다.
- 길어도 grep으로 찾을 수 있으면 된다. **짧은 폴더명이 짧은 ID를 만든다.**

**그래서 유닛 폴더명은 바꾸지 않는다.** 폴더명이 ID의 일부라 이름을 바꾸면 **발급한 ID가 전부 바뀐다** — `불변·append-only` 위반이다.

| 무엇이 함께 걸리나 | |
|:--|:--|
| 요구·설계·task의 태그 | `{도메인}-{유닛}-N`을 가리키는 것 전부 |
| `2.task`↔`4.build`↔`5.verify` 스파인 | 번호 1:1이 폴더 기준이다 |
| `13.architecture` 화면 지도의 `소속` | 어느 유닛이 만드는 화면인가 |
| **코드의 import 경로** | 계약·프롬프트를 유닛 폴더에서 직접 읽는다 |

- **이름이 마음에 안 들면 그대로 둔다.** 폴더명은 사람이 읽는 이름이 아니라 **주소**다.
- **범위가 실제로 달라졌으면** 그 유닛을 `~~취소~~`로 닫고 **새 유닛을 만든다** — 이름을 고치는 것이 아니라 대체하는 것이다. 닫은 유닛의 요구는 `deprecated`로 남긴다.
- **처음 만들 때 잘 정한다** — `/flow:design domain`의 `유닛 계획`이 그 시점이다.

**규칙**

1. **불변 · append-only** — 번호 재편 금지. 삭제는 `~~USER-3~~ (deprecated)`, 분할은 하위 ID(`USER-3` → `USER-3.1`·`USER-3.2`). 기존 파일이 있으면 이어서 발급한다.
2. **부모는 문서 상단에 한 번** — `상위: USER-1 ← SYS-1`. 각 요구에 중복 기재하지 않는다.
   - **부모가 있는 것은 기능 요구뿐**이다 — `{도메인}-{유닛}-N`의 부모는 `{도메인}-N`.
   - **도메인 요구엔 부모가 없다.** `SYS-*`는 횡단 제약이라 특정 도메인의 부모가 아니다.
   - **`SYS-*`는 설계 요소가 직접 태그**한다(`태깅` 예외) — 부모 체인으로 안 내려온다.
3. **적정 입도** — 너무 잘게/크게 쪼개지 않는다. 단 **버그는 크기가 아니라 원인 하나가 단위**다(`/flow:spec`).

## 여러 사람이 동시에 발급할 때

**"이어서 발급"은 순차 작업 전제다.** 각자 브랜치에서 발급하면 같은 번호가 나온다.

```
A 브랜치   SYS-9  결재선 캐시      ← 둘 다 "마지막이 SYS-8이니 다음은 9"
B 브랜치   SYS-9  감사 로그 보존
→ 머지     SYS-9가 두 개. 태그가 어느 쪽을 가리키는지 알 수 없다
```

**접두가 갈리면 안 부딪힌다** — 도메인 요구(`USER-*`·`ORDER-*`)·기능 요구가 그렇다. **접두 없이 한 파일에서 이어 발급하는 것**이 부딪힌다.

| 무엇 | 어디서 발급 | 얼마나 자주 늘어나나 | 위험 |
|:--|:--|:--|:--|
| `SYS-*` | `13.architecture` 요구 | 프로젝트 초기에 몰린다 | 중간 |
| **`SCR-N`** 화면 | `13.architecture` **화면 지도** | **FE 유닛마다** — 대시보드면 수십 개 | **높다** |
| **`DR번호`** 도메인 규칙 | `09.domain` 업무 규칙 | 그 도메인을 건드릴 때마다 | 중간 (같은 도메인일 때만) |
| **유닛 번호** (`02.refund`) | `09.domain` **유닛 계획** + 폴더 | 유닛을 추가할 때마다 | **높다** |

- **`R번호`는 안 부딪힌다** — 유스케이스 상세 안이라 한 사람이 쓴다.
- **`D-N`도 안 부딪힌다** — 유닛 문서 안 로컬이다.

```
A 브랜치   SCR-5 로그인      ← 둘 다 "마지막이 SCR-4니 다음은 5"
B 브랜치   SCR-5 결제
→ 머지     같은 번호가 다른 화면을 가리킨다. 화면 이동이 깨진다
```

| 언제 | 무엇을 |
|:--|:--|
| **발급 전** | **원격 기본 브랜치의 그 파일을 기준으로 최대 번호를 본다.** 로컬만 보면 남이 이미 쓴 번호를 다시 쓴다 |
| **머지 전** | 같은 ID·번호가 두 번 나오는지 grep한다. **`/flow:sync`가 이걸 본다** |
| **중복이면** | **나중에 머지하는 쪽이 재발급**한다. 그 번호를 가리키는 것을 **전부 함께** 고친다 |

**중복을 고칠 때 함께 고칠 것** — 빠뜨리면 추적이 끊긴다.

| 무엇이 중복 | 함께 고칠 것 |
|:--|:--|
| `SYS-*` | 설계 요소의 태그 · 요구 커버리지 |
| **`SCR-N`** | **화면 지도의 이동 그림** · 각 유닛 `1.design.md`의 화면 절 |
| `DR번호` | 그 번호를 `참조:`로 가리키는 유스케이스 · `5.verify/`의 기대값 출처 |
| **유닛 번호** | **폴더 이름** · 유닛 계획 표 · 요구 ID(`ORDER-REFUND-*`는 그대로) · 유닛 README |

- **`append-only`는 "머지된 뒤 불변"이다.** 미머지 브랜치의 번호는 아직 확정이 아니라 재발급해도 규칙 위반이 아니다.
- **`impact-analysis`로 그 번호를 쓰는 곳을 전부 찾는다.**
- **유닛 번호는 순서를 뜻한다** — 겹친 것을 고칠 때 **의존 순서를 다시 본다**(`09.domain` 유닛 계획). 번호만 밀면 순서가 틀어진다.

**예방이 낫다.** 특히 **`SCR-N`과 유닛 번호**는 자주 늘어난다.

| 방법 | 언제 |
|:--|:--|
| **구간을 나눠 쓴다** | A는 `SCR-10~19`, B는 `SCR-20~29` — **동시 작업이 예정돼 있을 때** |
| **발급을 한 사람에게 모은다** | 화면 지도·유닛 계획을 한 사람이 관리 |
| 먼저 발급하고 시작한다 | 작업 전에 `13.architecture`·`09.domain`만 먼저 커밋·머지 |

- **세 번째가 가장 싸다** — 번호만 잡아두고 내용은 나중에 채운다.

## 태깅

**직접 충족하는 ID만** 태그한다. 부모는 **전이(transitive)로 추적**된다 — 재기입하면 부모가 바뀔 때 두 곳을 고쳐야 해 드리프트가 난다.

```
SYS-1 → USER-1 → USER-LOGIN-1 → D-1 → 2.task/00.login-api → 4.build/… → 5.verify/…
                       ↑ 상단 1회 선언        ↑ frontmatter
```

- **예외**: 횡단 요구(`SYS-*`)는 기능 요구의 부모 체인에 없으므로 **설계 요소가 직접 태그**한다.
- `1.design.md` — 설계 요소 표에 `| D-N | 요소 | 충족 요구 |`
- `2.task/NN.name.md` — frontmatter:
  ```yaml
  ---
  requirement: [USER-LOGIN-1]
  design: [D-1]
  ---
  ```
- `4.build`·`5.verify`는 task 번호·이름과 함께 **태그도 상속**한다.

## 매트릭스 · gap 판정

태그를 grep해 역인덱스를 만든다(별도 매핑 파일을 두지 않는다 — 드리프트 원인).

```
USER-LOGIN-1 → D-1 → 2.task/00.login-api → 4.build ✓ → 5.verify ✓   = 검증됨
USER-LOGIN-2 → D-2 → (task 없음)                                     = gap
SYS-2        → (설계 요소 없음)                                       = gap
```

`/flow:verify project`(개발 완료 후 전체 통합테스트)가 실행 결과에 이 인덱스를 겹쳐 분류 리포트를 낸다 — **검증됨 / gap / 사람 확인 필요 / 현행(미검증)**. 정의는 `/flow:verify` 절차 5.

**요구의 `종류`가 분류를 가른다.** 시스템 요구는 종류가 적혀 있다(`13.architecture`).

- `성능`·`원가` — 측정 안 했으면 **gap**(자동 검증이 가능한데 안 한 것)
- `법·정책` — **항상 사람 확인 필요.** 테스트가 없는 게 정상이라 **gap으로 세지 않는다**

**요구의 `상태`가 gap 여부를 가른다.** 역추출(`확인 필요`)은 `현행(미검증)`이고 **gap이 아니다** — 코드엔 있고 우리 테스트만 없다. 레거시에서 이걸 안 가르면 **요구 전부가 gap으로 나와** 리포트가 쓸모없어진다. 합계도 분리해 센다.

- 상위 요구에 연결되지 않은 기능은 **"상위 미연결"(고아)** 로 표시한다.
- 도메인 파일에는 하위 기능 목록·상태를 `/flow:sync`가 색인해 **단일 뷰**를 만든다.

## 요구 상태값 (정본)

요구 표의 `상태` 칸이다. **게이트가 이 값으로 판정을 가른다.**

| 상태 | 뜻 | 게이트 |
|:--|:--|:--|
| **비움** = `확정` | 사람이 "이걸로 간다"고 정한 요구 | **신규 기준 전부 적용** — 완료 기준 측정 가능·측정 방법·측정 수단·쿼터 대조 |
| **`확인 필요`** | **`legacy` 역추출**, 또는 아직 확정 안 된 것 | **면제** — 코드가 하는 일을 옮긴 것이다 |
| `~~취소~~` | 폐기 — 지우지 않고 표기만 | 판정 대상 아님 |

- **신규 요구는 칸을 비운다.** 매번 `확정`을 적는 부담을 만들지 않는다 — **비움이 곧 확정**이다.
- **`/flow:prd {레벨} legacy`가 뽑은 것은 전부 `확인 필요`** 로 적는다(절차 2').
- **사람이 검수해 칸을 비우면 그때부터 신규와 같은 게이트가 걸린다.** 그게 "확정했다"는 뜻이다.
- **`확인 필요`를 게이트 우회용으로 쓰지 않는다** — 신규 요구에 붙이면 `gatekeeper`가 판정에 적는다.

## 유닛 상태값 (정본)

`/flow:sync`가 유닛 README·도메인 `하위 기능`에 적는 값이다. **값의 정본은 여기** — 다른 말을 쓰지 않는다.

**상태의 정본은 파일이고, README는 캐시다.**

| | 무엇 |
|:--|:--|
| **파일** | **정본** — 언제 봐도 맞다 |
| README `상태` | **캐시** — `sync`를 돌린 시점의 값이다. **낡을 수 있다** |

`build` 중간에 멈추면 `sync`를 안 돌린 상태다 — README는 `명세`인데 `4.build/`가 이미 있다. **README를 믿지 않고 파일을 센다.**

| 상태 | 판정 근거 (폴더·파일로 계산) |
|:--|:--|
| `설계` | `0.requirement`·`1.design`은 있고 `2.task`가 없다 |
| `명세` | `2.task`·`3.contract`는 있고 `4.build`가 없다 |
| `구현중` | `4.build`는 있고 `5.verify` 판정이 PASS가 아니다 |
| `검증됨` | `5.verify` 판정이 PASS다 |
| **`정지`** | **`/flow:run`이 멈췄다** — 아래 |

### task 단위 — 어디까지 됐나

**유닛 상태만으로는 재개 지점을 모른다.** task가 5개인데 `구현중`이면 몇 번까지 됐나.

**스파인이 1:1이라 번호로 센다** — `2.task/NN` ↔ `4.build/NN` ↔ `5.verify/NN`.

| task NN | 있는 것 | 상태 |
|:--|:--|:--|
| `2.task/NN.md`만 | — | **미착수** |
| + `4.build/NN.md` | 구현 기록 | **구현됨, 미검증** |
| + `5.verify/NN.md` 판정 FAIL | 실패 기록 | **검증 실패** |
| + `5.verify/NN.md` 판정 PASS | — | **완료** |

```
2.task/    00.login-api.md  01.session.md  02.lockout.md
4.build/   00.login-api.md  01.session.md                  ← 02가 없다
5.verify/  00.login-api.md                                 ← 01이 미검증
           ↓
재개 지점: 01 검증 → 02 구현
```

- **`/flow:build`의 "미완료 task 자동 식별"이 이 규칙이다.** `2.task/NN`이 있고 `4.build/NN`이 없는 것이 미완료다.
- **번호가 빠져 있으면(`00`·`02`만 있고 `01` 없음) 그 사실을 알린다** — 스파인이 깨졌다는 뜻이다.
- **`5.verify/NN`의 판정은 `## 판정` 절 첫 줄**을 본다(`05.verify` 템플릿).

### 재개할 때는 다시 계산한다

**새 세션이 붙으면 README를 믿지 않고 파일을 센다.**

| 누가 | 언제 |
|:--|:--|
| `/flow:ask` | 사용자가 "이어서 하고 싶다"고 할 때 |
| `/flow:run` (체인 비움) | 어느 국면부터 돌지 정할 때 |
| `/flow:build`·`/flow:spec` (인자 비움) | 대상을 자동 식별할 때 |

- **계산한 상태가 README와 다르면 알린다** — `sync`를 안 돌린 것이라 `sync`를 권한다.
- **README를 여기서 고치지 않는다** — 색인 갱신은 `/flow:sync`의 일이다.

**`정지`는 사유를 함께 적는다.** 안 적으면 `구현중`과 구분이 안 된다.

| 사유 | 언제 |
|:--|:--|
| `정지(빌드 3회)` | 구현↔테스트 루프 3회 실패 |
| `정지(critical)` | `6.review` critical 미해결 |
| `정지(요구)` | 요구 충돌·쿼터 충돌 — 사람이 정해야 한다 |
| `정지(되돌아가기 2회)` | `auto`가 두 번 고쳐도 안 됐다 |

- **손으로 정하지 않는다** — 폴더와 판정 파일에서 계산한다.
- **`정지`를 `구현중`으로 적지 않는다.** 멈춘 것과 진행 중인 것은 다르다 — 색인만 보고 무엇이 막혔는지 알아야 한다.
- `5.verify`가 여러 회차면 **최신 회차의 판정**을 본다. 단 `6.review` critical은 **전 회차 누적**이다(`code-review`).

## 붕괴 경로에서도 추적 유지

작은 일에 무거운 절차를 강요하면 사람이 flow를 우회한다. 그렇다고 추적을 끊지는 않는다.

| 상황 | 처리 |
|:--|:--|
| 버그·작은 변경 | `/flow:prd` 없이 `/flow:design`부터. **`/flow:design`이 요구를 자동 발급**해 `0.requirement.md`에 append |
| 고아 기능 (상위 없음) | 허용. `/flow:verify project`가 "상위 미연결"로 리포트 — **아래에서 처리를 정한다** |
| 문구·오타 (무동작) | flow 밖 — **진짜 면제** |

### 고아를 발견한 뒤 — 셋 중 하나를 고른다

**"허용"이 방치를 뜻하지 않는다.** 리포트만 하고 두면 매 `verify project`가 같은 것을 다시 적어 **리포트가 노이즈가 된다.**

| 선택 | 언제 | 어떻게 |
|:--|:--|:--|
| **요구를 소급 발급** | **필요한 기능이었다** — 쓰이고 있고 없으면 곤란하다 | `/flow:design`이 버그처럼 요구를 발급한다(`붕괴 경로에서도 추적 유지` 첫 줄과 같은 경로). 완료 기준은 **현재 동작**을 적고 `상태`를 비운다(=확정) |
| **코드를 지운다** | 아무도 안 쓴다 · 실험이 남았다 | `impact-analysis`로 호출부를 먼저 본다. 지우는 것도 변경이라 `/flow:run fix`로 |
| **고아로 유지** | **과도기다** — 곧 요구가 붙을 예정 | **기한을 적는다** — `00.ref/00.architecture/`의 `확인 필요`에 `{언제까지}`와 함께 |

- **판단 기준은 하나다**: *"이 기능이 없어지면 누가 곤란한가?"* 답이 있으면 소급 발급, 없으면 삭제.
- **`고아로 유지`를 기한 없이 쓰지 않는다.** 기한이 없으면 영구 노이즈가 된다.
- **소급 발급한 요구는 역추출과 다르다** — `legacy`는 `상태: 확인 필요`지만, 이건 **쓰기로 정한 것**이라 확정이다. 완료 기준·측정 방법을 채운다.
- **`verify project`가 리포트할 때 이 셋을 함께 제시한다.**

## 경계

- **ID를 재편·재사용하지 않는다.** 한 번 발급한 번호는 의미가 고정된다.
- **task 이하에 새 ID 체계를 만들지 않는다** — 경로가 식별자다.
- **매핑 테이블을 별도 파일로 유지하지 않는다** — 태그에서 계산한다.
- **gap을 요구 삭제·축소로 닫지 않는다** — 리포트가 결론이다.
- 레벨이 애매하면 추측하지 말고 사용자에게 묻는다.
