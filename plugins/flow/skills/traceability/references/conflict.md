# 여러 사람이 동시에 발급할 때

**"이어서 발급"은 순차 작업 전제다.** 각자 브랜치에서 발급하면 같은 번호가 나온다.

```
A 브랜치   SYS-9  결재선 캐시      ← 둘 다 "마지막이 SYS-8이니 다음은 9"
B 브랜치   SYS-9  감사 로그 보존
→ 머지     SYS-9가 두 개. 태그가 어느 쪽을 가리키는지 알 수 없다
```

**접두가 갈리면 안 부딪힌다** — 도메인 요구(`USER-*`·`ORDER-*`)·기능 요구가 그렇다. **접두 없이 한 파일에서 이어 발급하는 것**이 부딪힌다.

| 무엇 | 어디서 발급 | 얼마나 자주 늘어나나 | 위험 |
|:--|:--|:--|:--|
| `SYS-*` | 아키텍처 문서의 요구 절 | 프로젝트 초기에 몰린다 | 중간 |
| **`SCR-N`** 화면 | 아키텍처 문서의 **화면 지도** | **FE 유닛마다** — 대시보드면 수십 개 | **높다** |
| **`DR번호`** 도메인 규칙 | 도메인 문서의 업무 규칙 절 | 그 도메인을 건드릴 때마다 | 중간 (같은 도메인일 때만) |
| **유닛 번호** (`02.refund`) | 도메인 문서의 **유닛 계획** + 폴더 | 유닛을 추가할 때마다 | **높다** |

- **`R번호` 는 안 부딪힌다** — 유스케이스 상세 안이라 한 사람이 쓴다.
- **`D-N` 도 안 부딪힌다** — 유닛 문서 안 로컬이다.

## 언제 무엇을 하나

| 언제 | 무엇을 |
|:--|:--|
| **발급 전** | **원격 기본 브랜치의 그 파일을 기준으로 최대 번호를 본다.** 로컬만 보면 남이 이미 쓴 번호를 다시 쓴다 |
| **머지 전** | 같은 ID·번호가 두 번 나오는지 grep 한다. **`/flow:sync` 가 이걸 본다** |
| **중복이면** | **나중에 머지하는 쪽이 재발급한다.** 그 번호를 가리키는 것을 **전부 함께** 고친다 |

**중복을 고칠 때 함께 고칠 것** — 빠뜨리면 추적이 끊긴다.

| 무엇이 중복 | 함께 고칠 것 |
|:--|:--|
| `SYS-*` | 설계 요소의 태그 · 요구 커버리지 |
| **`SCR-N`** | **화면 지도의 이동 그림** · 각 유닛 설계도의 화면 절 |
| `DR번호` | 그 번호를 `참조:` 로 가리키는 유스케이스 · `5.verify/` 의 기대값 출처 |
| **유닛 번호** | **폴더 이름** · 유닛 계획 표 · 요구 ID(`ORDER-REFUND-*` 는 그대로) · 유닛 README |

- **`불변·append-only` 는 "머지된 뒤 불변"이다.** 미머지 브랜치의 번호는 아직 확정이 아니라 재발급해도 규칙 위반이 아니다.
- **`impact-analysis` 로 그 번호를 쓰는 곳을 전부 찾는다.**
- **유닛 번호는 순서를 뜻한다** — 겹친 것을 고칠 때 의존 순서를 다시 본다. 번호만 밀면 순서가 틀어진다.

## 예방이 낫다

특히 **`SCR-N` 과 유닛 번호** 는 자주 늘어난다.

| 방법 | 언제 |
|:--|:--|
| **구간을 나눠 쓴다** | A는 `SCR-10~19`, B는 `SCR-20~29` — **동시 작업이 예정돼 있을 때** |
| **발급을 한 사람에게 모은다** | 화면 지도·유닛 계획을 한 사람이 관리 |
| 먼저 발급하고 시작한다 | 작업 전에 아키텍처·도메인 문서만 먼저 커밋·머지 |

- **세 번째가 가장 싸다** — 번호만 잡아두고 내용은 나중에 채운다.
