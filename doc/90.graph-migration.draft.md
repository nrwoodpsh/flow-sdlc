# 2flow — 그래프 엔지니어링 전환 검토 (초안)

> **정본이 아니다.** 다음 버전 설계 입력으로 쓰는 검토 문서다. 여기 적힌 것은 아직 아무것도 강제하지
> 않는다 — `flow.topology.json` 도 `lint.py` 도 이 파일을 읽지 않는다.
> **채택하면 이 파일은 지워지고 정본(`00.concept.md` 의 능력 · `01.architecture.md` 의 구조 ·
> `flow.topology.json` 의 절)으로 흡수된다.** 리포에 검토 기록을 남기지 않는 규율은 그대로다.
> 번호가 `90` 인 것은 정본 라인(`00`~`05`)에서 떼어 두려는 것이다.

## 축이 둘이다 — 판정과 수행

전환의 핵심은 노드를 늘리는 것이 아니라 **일마다 사람·코드·AI 를 가르는 것**이다.
flow 에는 그 축이 절반만 있다.

| 축 | 무엇을 가르나 | 지금 |
|:--|:--|:--|
| **판정** | 게이트를 누가 판정하나 | **있다** — `machine` · `content` · `promise` 3분류가 정본에 있고 `lint` 가 대조한다 |
| **수행** | 노드의 일을 누가 하나 | **없다** — 위상 어디에도 `code` · `ai` · `human` 이 없다 |

수행 축이 없으면 노드가 통짜로 AI 것이 된다. 실제로는 노드 하나 안에서 갈린다.

| 노드 | 코드가 할 일 | AI 가 할 일 | 사람이 할 일 |
|:--|:--|:--|:--|
| `prd` | 다음 요구 ID 계산(append-only 라 결정적) | 요구 문장 · 레벨 제안 | 레벨 확정 |
| `design` | 계약 컴파일·타입체크(`contract-gate`) | 설계 판단 · File Map 작성 | 청사진 컨펌 |
| `build` | 게이트 판정 · 테스트 실행 | 구현 | 막혔을 때 결정 |
| `verify` | 테스트 실행(exit code) · 커버리지 대조 | 실패 원인 해석 | — |
| `review` | 룰 기반 발견 · 회귀 표면 추출 | 등급 판단 | critical 처리 |
| `sync` | 변경 파일 목록 · 드리프트 판정 | 문서 갱신 문장 | — |
| `commit` | 변경 목록 · 드리프트 확인 | 메시지 작성 | **커밋 여부** |
| `next` | 유닛 상태 계산 · 겹침 판정 | 어떻게 가를까 | 대상 목록 확정 |

**두 축의 관계가 이 전환의 순서를 정한다.** 결정적 계산을 AI 가 수행하면 결과가 재현되지 않고,
재현되지 않는 결과는 게이트가 근거로 쓸 수 없다. 그래서 판정 축이 `promise` 로 내려간다 —
**수행 축을 코드로 내리는 것이 판정 축을 `machine` 으로 올리는 선행 조건이다.**

`05.orchestration.md` 의 강제력 표에 그 증거가 있다. *"분할에 겹침이 없다 — 약속. `next` 가 계획할
때 계산한다. 안 해도 아무도 모른다."* 겹침 판정은 집합 교집합이라 판정 방법이 없는 것이 아니다.
**수행자가 코드가 아니라서 약속이 됐다.**

## 판별식 — 무엇을 코드로 내리나

| 기준 | 답 | 근거 |
|:--|:--|:--|
| 같은 입력에 같은 출력이 나오나 | **코드** | 재현된다. 게이트가 근거로 쓸 수 있다 |
| 출력이 정답 하나가 아니고 더 나은 쪽이 있나 | **AI** | 룰로 접으면 오탐이 나고, 오탐은 사람이 훅을 끄게 만든다 |
| 되돌릴 수 없거나 밖으로 나가나 | **사람** | 커밋 · 외부 발행 · 면제 등록 |

**역방향도 위험이다.** 코드로 못 접는 것을 코드로 내리면 과차단이 되고, 과차단은 층을 영구히
없앤다(`missingCanon` 이 `fail-closed` 를 버린 이유와 같다). 판별식은 양방향으로 쓴다.

## 진단 — 5개 층 중 셋이 있다

| 층 | 지금 | 무엇이 그 자리인가 |
|:--|:--|:--|
| 그래프 정의 | **있다** | `flow.topology.json` — 노드 · 간선 · 게이트 조건 |
| 코드 규칙 | **있다** | `guard-rules.json` · `hooks/scripts/` — 단 **쓰기 시점에만** 돈다 |
| 판정자 분리 | **있다** | `agents/gatekeeper.md` — 도구 권한으로 진행자와 갈렸다 |
| 결정적 계산기 | **없다** | 산문이 "센다 · 계산한다" 라고 적고 **LLM 이 센다** |
| 실행기 | **없다** | 사람과 세션이 대신한다. `next: [build, spike]` 에서 어느 쪽인지 즉흥 판단이다 |

## 이관 후보 — AI 가 하는데 결정적인 것

산문이 이미 계산 절차를 적어 둔 자리다. 절차가 있으니 코드로 옮기는 일이고, 새로 설계할 것이 아니다.

| 무엇 | 지금 어디에 적혔나 | 옮기면 판정 축이 |
|:--|:--|:--|
| 유닛 상태 — 폴더·판정 파일을 세서 정한다 | `traceability/unit-state.md` (*"README 를 믿지 않고 파일을 센다"*) | `machine` 가능 |
| 스파인 1:1 대조 — `2.task/NN` ↔ `4.build/NN` ↔ `5.verify/NN` | 같음 (*"번호로 센다"*) | `machine` 가능 |
| 소유 집합 겹침 — task 쌍마다 교집합이 비었나 | `traceability/ownership.md` | **`promise` → `machine`** |
| 요구 커버리지 — 태그 대조 · 상태별 분리 합계 | `traceability/coverage.md` | `machine` 가능 |
| 다음 요구 ID — append-only 라 다음 값이 하나다 | `traceability/id-system.md` | `machine` 가능 |
| 되돌림 횟수 — 리뷰 리포트 편수 | 아직 없다 | `loopback` 상한의 근거가 된다 |
| File Map ↔ 실제 변경 파일 대조 | `drift-check/rule.md` (문서 쪽만 훅이 있다) | `machine` 가능 |

**이관의 이득은 셋이다** — 결과가 재현된다 · 게이트가 근거로 쓸 수 있다 · 조각 미적재 위험이 그
계산에서는 사라진다(`01.architecture.md` 가 위험 칸에 둔 그 위험이 코드로 내려간 만큼 줄어든다).

**이관해도 조각은 남는다.** 코드가 무엇을 계산하는지는 코드가 정본이 되고, **왜 그렇게 세는지**는
조각에 남는다. 둘을 같은 것으로 적으면 정본이 둘 된다 — Q2 가 그 질문이다.

## 작업 — 단계별

각 작업은 `무엇 · 정본 · 완료 판정` 을 갖는다. **완료 판정이 없거나 판정자가 지목되지 않은 작업은
착수하지 않는다** — 그러면 위상에 절만 늘고 강제력은 그대로 `promise` 다.

**판정자는 기계여야 하는 것이 아니라 이름이 있어야 한다.** 이 문서의 작업은 전부 판정자가 검사기다 —
구조를 고치는 일이라 그렇다. 다른 종류의 작업은 다른 판정자를 갖는다(`92` 의 study 노트는 사용자가
판정자다). *"완료 판정이 기계가 아니면 착수하지 않는다"* 로 적으면 사람이 판정하는 일이 전부
자격을 잃는데, 그건 이 규율이 막으려던 것이 아니다 — 막으려던 것은 **판정자 없이 절만 늘리는 것**이다.

### 0단계 — 축을 적는다 (폴더 증가 0)

| id | 무엇 | 완료 판정 |
|:--|:--|:--|
| G1 | `nodes[].work[]` — 노드의 일을 단위로 갈라 `by: code\|ai\|human` | `lint` 신설 `work-by-runnable` — `by: code` 인데 실행 명령이 없으면 실패 |
| G2 | `edges[].when` — `next` 후보마다 전환 판정식 + 판정 등급 | `lint` 신설 `edge-when-graded` — 등급 없으면 실패. `machine` 이면 `enforcedBy` 필수 |
| G3 | `loopback[]` — 되돌아가는 간선 · `maxRetries` · `countBy` | `lint` 신설 `loopback-countable` — `countBy` 가 **repo 파일 계산식**이 아니면 실패 |
| G4 | `nodes[].io` — 읽는/쓰는 스테이트 | `lint` 신설 `io-canon-ref` — `writes` 가 `output_templates` 를 가리키지 않으면 실패 |

G1 이 이 단계의 핵심이다. 적는 것만으로 **AI 가 하고 있는 결정적 계산이 목록으로 드러난다** —
이관 대상을 사람이 눈으로 찾지 않게 된다. **폴더 증가 0 이고 다른 결정을 풀어 준다** —
`92` 의 원격 심볼 판정을 산문에 둘지 `runtime/compute/` 에 둘지가 G1 을 적으면 저절로 정해진다.
**0단계에서 하나만 한다면 G1 이다.**

**⚠ G4 는 자를 후보다.** 절 하나와 lint 하나를 더하는데 **없으면 무엇이 무너지나에 답이 없다.**
`output_templates` 가 이미 산출물 정본이고, 노드가 무엇을 쓰는지는 커맨드의 절차가 이미 적는다.
**G4 를 하려면 "이것이 없어서 겪은 일" 을 먼저 적는다** — 못 적으면 빼고 간다.

G2 의 판정식에도 **등급 3분류를 그대로 적용한다.** 전환 조건을 전부 코드로 접을 수는 없다.
`설계가 충분히 확실한가`(design→build)는 `content` 이고 `요구 문서가 있나`는 `machine` 이다.
등급을 섞으면 `entry`/`exit` 가 겪은 문제가 간선에서 반복된다.

### 1단계 — 결정적 계산을 코드로 내린다

| id | 무엇 | 완료 판정 |
|:--|:--|:--|
| G5 | `runtime/compute/` — 이관 후보 표의 계산을 코드로 | 조각의 예시 입력에 조각이 적은 답이 나온다 |
| G6 | 조각 ↔ 계산기 정본 정리 — 계산은 코드가, 이유는 조각이 | `lint` 신설 `compute-canon-single` — 조각이 계산 절차를 다시 적으면 실패(기존 `skill-duplication` 확장) |
| G7 | 이관된 계산을 근거로 `promise` → `machine` 승격 | 되돌려서 실패 확인 — 계산기를 지우면 그 케이스가 **실패해야** 한다 |

**여기가 값의 중심이다.** G7 로 올라가는 것 중 `ownership` 의 겹침 판정이 가장 크다 — 병렬 실행의
안전이 지금 약속 하나에 걸려 있고, 그것이 집합 연산이다.

**G7 은 이 문서에서 유일하게 무언가를 줄이는 항목이다.** 나머지는 절·검사·파일을 더한다.
`promise` 개수가 실제로 내려가는 것을 되돌림 확인으로 증명할 수 있는 자리다.

G5 는 **읽기만 한다.** 상태를 쓰기 시작하면 버린 안(런 원장)이 되살아난다.
(정확히는 **덮어쓰기** 시작하면이다 — 「이미 버린 안을 되살리지 않는 형태」 절의 구분을 보라.)

**`92` 가 G5 의 고객이다.** `92.skill-proposals.draft.md` 의 원격 대조는 **내 변경 심볼 ∩ 원격
커밋 심볼** 을 판정한다 — `ownership.py` 와 같은 집합 연산이고 같은 자리에 얹힌다.
**그 판정을 산문(조각)에 먼저 적으면 G5 가 그것을 다시 코드로 내려야 한다 — 재작업이다.**
`92` 의 배선 절반(`review 코드` 에 `impact-analysis` 를 잇는 것)은 이 문서와 무관하게 먼저 해도 된다.

### 2단계 — 전환 시점 판정기 (훅 1개 신설)

| id | 무엇 | 완료 판정 |
|:--|:--|:--|
| G8 | `hooks/scripts/gate-node-entry.sh` — `UserPromptSubmit` 에서 `/flow:X` 를 가로채 `entry.machine` 과 `edges[].when(machine)` 을 판정 | 기존 `machine-gate-wired` 가 자동으로 검사한다(새 검사 불필요) |
| G9 | 등급 재분류 — 전환 시점에 판정되는 `promise` 를 올린다 | 되돌려서 실패 확인 |

**G8 의 기제는 실측됐다** (2026-08-12 · 스크래치 4팔 실험). `UserPromptSubmit` 이 `/flow:X` 를
가로채 topology 를 읽고 `additionalContext` 를 주입하는 경로가 헤드리스에서 끝까지 돌았다.
같은 실험에서 **조각 로드 주입**(그 커맨드의 `loads` 목록을 컨텍스트로 미는 것)도 검증됐다 —
읽기율은 대조군이 천장이라 못 쟀고, 관측된 이득은 탐색 비용(도구 호출 30→18)이다.
**G8 을 만들 때 주입을 같은 훅에 접는다** — 판정과 주입이 같은 시점·같은 정본이라 훅을 둘로 가르면
topology 를 두 번 읽고 어긋날 자리만 생긴다.

**⚠ G9 는 경로가 반쪽이다.** `UserPromptSubmit` 은 **사람이 친 명령만** 본다 — `next` 가 이어
부르는 체인 경로는 이 훅이 못 본다(`01.architecture.md` 가 적어 둔 그 구멍 그대로).
그러면 사람 경로만 기계이고 AI 경로는 여전히 약속인데, 이걸 `machine` 이라 적으면
**"4겹이라 적고 1겹" 을 우리 손으로 재발**시키는 것이다. G9 는 둘 중 하나다 —
등급 표기에 경로 축을 더하든가(`machine(직접 호출)`), 체인 경로가 덮이기 전에는 `promise` 로 둔다.
`entry-grade-parity` 가 이 구분을 모르는 채로는 승격하지 않는다.

G9 후보 (`wasGrade: machine` 이 이미 달린 것들):

| 항목 | 지금 이유 | 전환 훅이 있으면 |
|:--|:--|:--|
| `next.has-config` · `prd.has-config` | 검사할 도구 호출 시점이 없다 | **판정된다** — 커맨드 입력이 그 시점이다 |
| `design.requirement-doc-exists` | 쓰기 시점에 걸면 도메인 레벨·자동 발급 경로가 막힌다 | 전환 시점이면 그 부작용이 없다. **재검토 대상** |
| `verify.unit-task-doc` | 테스트 Bash 를 막으면 과차단 | **판정된다** — 막는 대상이 Bash 가 아니라 국면 진입이다 |

`ask`(막지도 통과시키지도 않고 사람에게 넘김)가 이 자리에는 없다.

## 이미 버린 안을 되살리지 않는 형태

`05.orchestration.md` 의 「버린 안」과 부딪히는 자리가 셋이다. 셋 다 **형태**로 피한다.

| 부딪히는 것 | 되살아나는 조건 | 피하는 형태 |
|:--|:--|:--|
| 런 원장 (`.run/ledger.json`) | `runtime/` 이 상태를 **쓰기** 시작하면 | 계획은 **산출물이고 입력이 아니다.** 매번 다시 계산하고 버린다 |
| flow 가 워커를 직접 띄운다 | 계획 스크립트가 실행까지 하면 | **인터프리터가 아니라 컴파일러다.** 실행은 환경이 한다 |
| 코디네이터 에이전트 신설 | 실행기를 에이전트로 만들면 | 실행기는 **스크립트**다. 명확한 판단은 코드가 한다 — 이건 설계와 맞는다 |

계산으로 안 나오는 것이 둘 남는다 — **되돌린 횟수**와 **사람이 승인했나**. 앞은 리뷰 리포트 편수를
세면 나오고, 뒤는 커밋 이력에 남는다. 둘 다 계산으로 접히면 원장은 여전히 필요 없다.
**접히지 않으면 원장을 만드는 것이 아니라 그 조건을 `promise` 라고 적는 것이 답이다.**

### 금지 대상은 가변 상태다 — append-only 로그가 아니다

**이 구분을 안 적으면 `91` 로 규율을 옮길 수 없다.** `91` 의 전제는 *"이벤트 로그가 정본, 상태는
로그에서 재생"* 이고 LangGraph 체크포인터가 그 저장을 한다. 위 표의 「런 원장」을 문자 그대로
들고 가면 `91` 의 0단계를 만들 수 없다. 둘은 다른 물건이다.

| | 정본이 될 수 있나 | 왜 |
|:--|:--|:--|
| **가변 상태** (`.run/ledger.json` · claim · lock) | **안 된다** | 덮어써진다. 쓰기 전에 죽으면 거짓이 남고, 거짓인지 알 방법이 없다 |
| **append-only 로그** (이벤트 로그 · git 이력 · 리뷰 회차) | **된다** | 덮어써지지 않는다. 끊긴 지점이 로그에 그대로 보인다 |

```
✗ 상태를 저장하지 않는다
✓ 가변 상태를 정본으로 두지 않는다. append-only 로그는 정본이 될 수 있다
```

flow 가 이미 그렇게 하고 있다 — 리뷰 회차를 합치거나 지우지 않는 것, 커밋 이력을 승인 근거로
쓰는 것이 append-only 를 정본으로 쓰는 것이다. **`runtime/` 에 금지되는 것은 덮어쓰는 파일이다.**

## 하지 않는 것

| 무엇 | 왜 |
|:--|:--|
| 노드 신설 (`/flow:orchestrate` 류) | 산출물이 없고 착지처가 없다. **진입·퇴장이 빈 노드**가 늘어난다 |
| 런 원장 · claim · lock | **가변** 상태는 낡는다. 완료를 적기 전에 죽으면 원장이 거짓말을 한다 |
| flow 가 프로세스를 띄우고 감시 | 실행 층은 환경이다. 워크트리·재시작도 전부 밖이다 |
| AI 가 하던 판단을 룰로 접는 것 | 오탐이 나고 사람이 훅을 끈다. 이관 대상은 **결정적인 것만**이다 |
| 노드 사이 전달물을 새 파일 형식으로 | 유닛 폴더의 번호 붙은 산출물이 이미 그것이다 |
| `runtime/plan.py` 를 1단계보다 먼저 | 계획기가 셀 것이 없다. 계산기가 먼저다 |

## 값 · 비용

| 단계 | 폴더 증가 | 값 |
|:--|:--|:--|
| 0 — 축을 적는다 | 0 | 역할 분담이 보인다. 이관 대상이 목록으로 드러난다 |
| 1 — 계산을 코드로 | `runtime/compute/` | **`promise` 가 실제로 줄어든다.** 결과가 재현된다 |
| 2 — 전환 훅 | 훅 1개 | 국면 진입 판정이 생긴다 |
| 3 — 계획 컴파일러 | — | 조건부. 실측 뒤에 판단한다 |

**0~1단계가 확실한 구간이다.** 노드를 늘리지 않고 실행기도 만들지 않는데 강제력이 오른다.

**착수 조건 — 0.5 실전 테스트가 먼저다** (2026-08-12 결정). 이 문서의 전제는 *"AI 가 결정적
계산을 틀리게 한다"* 인데 그 사례가 아직 실측 0건이다. 실전 테스트에서 AI 가 잘못 센 사례
(유닛 상태 · 커버리지 · 겹침)가 나오면 그것이 1단계의 근거가 되고, 안 나오면 이 전환은
근거 없는 선제 구축이다 — 없으면 무엇이 무너지나에 답하지 못하는 것은 만들지 않는다.

**3단계는 값이 조건부다.** 노드가 11 개고 대부분 사람 확인이 끼고 대화형이다. 병렬이 실제로 값을
내는 자리는 `build` 하나이고 그건 이미 `next/parallel.md` 가 든다. 구조 복잡성·디버깅 포인트·비용이
같이 오르므로 **0~2단계를 내보내고 실측한 뒤에 판단한다.**

## 다른 두 초안과의 관계

| 문서 | 이 문서에 의존하나 | 무엇을 주고받나 |
|:--|:--|:--|
| `92` 스킬 제안 | **일부** | 원격 심볼 겹침 판정이 G5 의 고객이다. **배선 절반은 무관하니 먼저 해도 된다** |
| `91` 회사형 | **아니다** | 원칙만 가져가고 코드는 안 가져간다 |

**`91` 은 이 문서를 기다릴 이유가 없다.** `91` 이 이식하겠다고 적은 여섯(강제력 3등급 · 진행자≠판정자 ·
되돌릴 수 없는 것은 사람 · 정본은 데이터 · 상태는 계산 · 근거 등급)은 **전부 flow 0.5 에 이미 있다.**
이 전환이 만드는 것은 flow **내부**의 계산기이고, `91` 이 필요한 것은 다른 스택(LangGraph·Postgres)에
옮길 **원칙**이다. `91` 머리말이 적은 *"90 다음이 이것"* 은 의존이 아니라 순서 선호였다 —
그리고 이 문서의 착수가 조건부(근거가 나오면)이므로, 의존이라고 읽으면 근거가 안 나올 때
`91` 의 자리가 정의되지 않는다. **두 트랙은 독립이다.**

주고받는 것이 하나 있다 — **가변 상태와 append-only 로그의 구분**이다(「이미 버린 안을 되살리지
않는 형태」 절). 그 구분 없이는 이 문서의 금지가 `91` 을 불가능하게 만든다.
