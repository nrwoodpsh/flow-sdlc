# flow v2 — 구조

v1(0.8.0) 진단은 `00.diagnosis/`에 있다. 이 문서는 그 진단이 가리킨 처방이다.

## 왜 다시 짓나

세 층이 각각 다른 증상을 냈는데 원인이 하나였다.

| 층 | 증상 | v1 근거 |
|:--|:--|:--|
| 커맨드 | 게이트를 4곳이 약속하고 실제로 거는 곳은 `/flow:run` 하나 | `diag-A` 4절 |
| 스킬 | `/flow:design` 한 번에 1,107줄이 실리고 실사용은 100여 줄 | `diag-B` 4절 |
| 인프라 | 차단 목록 하나 늘리는 비용이 9곳 → 미탐 9건이 남았다 | `diag-C` 4절 |

**정본이 산문이라 기계가 못 읽는다.** 그래서 복제가 생기고, 복제를 맞추는 비용이 변경을 막고, 안 고쳐진 채 낡는다.

## 축 — 정본은 데이터, 산문은 생성물

정본을 JSON으로 내린다. 훅·검사기는 그걸 읽고, 문서 표는 그걸로 생성한다. **손으로 두 곳을 맞추는 관계를 남기지 않는다.**

```
flow.topology.json          ← 파이프라인 위상·게이트 조건의 정본
  ├─ 각 커맨드의 진입 조건   (읽는다 — 게이트가 여기서 걸린다)
  ├─ next.md 체인표          (생성)
  └─ plugin.json description (생성)

guard-rules.json            ← 차단 목록의 정본
  ├─ guard-danger.sh         (읽는다)
  ├─ hooks.test.sh           (읽는다 — 케이스를 여기서 만든다)
  └─ README·CLAUDE.md 차단표 (생성)
```

생성물은 커밋한다. 플러그인 설치자가 빌드를 돌릴 수 없기 때문이다. 대신 **`lint`가 생성물이 정본과 맞는지 대조한다** — 손으로 고치면 실패한다.

## 커맨드 — 14개에서 11개로

v1에서 접은 자리는 넷이고 근거는 전부 `diag-A` 2·3절에 있다.

| v2 커맨드 | 무엇 | v1에서 |
|:--|:--|:--|
| `/flow:setup` | 프로젝트 초기 세팅 | 그대로 |
| `/flow:next` | **지금 뭘 할 차례인지 답하고, 원하면 이어서 돌린다** | `ask` + `run` 합침 |
| `/flow:prd` | 요구 발급 — 시스템·도메인 | 그대로 |
| `/flow:design` | 설계 — 시스템·도메인에서 기능까지 | `design` + `spec` 합침 |
| `/flow:build` | 구현 + 단위 검증 | `build` + `verify unit` 합침 |
| `/flow:verify` | 브랜치·프로젝트 검증 + 요구 커버리지 감사 | `verify`에서 unit 제외 |
| `/flow:review` | 리뷰 — 코드·문서 | 그대로 |
| `/flow:sync` | 문서 수렴 | 그대로 |
| `/flow:commit` | 커밋 | 그대로 |
| `/flow:spike` | 버릴 코드로 리스크 검증 | 그대로 |
| `/flow:publish` | 외부 발행 | 그대로 |

빠진 것 — `spec`(design에 흡수) · `theme`(스킬로) · `ask`·`run`(`next`로 합침).

**`ask`와 `run`이 한 커맨드인 이유**: 둘 다 위상을 읽어 다음을 정하는 층이다. v1에서 갈라진 것은 하나는 "묻고 멈춤", 하나는 "묻고 이어감"이라서인데 그건 인자 하나 차이다. 위상이 데이터가 되면 둘 다 얇아진다.

### 게이트는 오버레이가 아니라 진입 조건이다

v1 최대 결함이 여기였다 — 게이트가 `/flow:run`에만 있어서 커맨드를 하나씩 부르는 기본 경로엔 안 걸렸다.

v2는 각 커맨드가 자기 진입 조건을 `flow.topology.json`에서 읽어 **스스로 판정한다.** `next`로 돌리든 하나씩 부르든 같은 게이트를 지난다. `next`는 순서대로 부르는 얇은 층만 남는다.

## 스킬 — 얇은 SKILL.md + references/

SKILL.md는 **판정과 인덱스**만 싣는다. 긴 규약은 `references/*.md`로 내리고 필요할 때만 읽는다.

```
traceability/
  SKILL.md            ~40줄   판정 기준 + 무엇이 어디 있나
  references/
    id-system.md              ID 체계·이름
    conflict.md               동시 발급 충돌
    unit-state.md             유닛·task 상태 계산
```

`/flow:design`이 싣는 양이 332줄에서 40줄이 된다.

**분할 기준은 소비자다.** 한 조각을 두 커맨드가 항상 같이 쓰면 나누지 않는다 — v1의 `tdd-verify`/`test-spec` 분리가 로드를 못 줄인 이유가 그것이다(`diag-B` 3-e).

### 스킬 목록 재획정

v1 16개에서 근거 있는 정리만 한다.

| 조치 | 대상 | 근거 |
|:--|:--|:--|
| 합침 | `tdd-verify` + `test-spec` → `testing` | 두 커맨드가 항상 같이 싣는다 (`diag-B` 3-e) |
| 합침 | `code-audit` → `code-review`의 조각 | 같은 체크리스트다 (`diag-B` 부수 관찰) |
| 옮김 | `doc-template`의 절 등급 표 → `doc-verify` | 등급을 쓰는 쪽이 거기다 (`diag-B` 2절) |
| 옮김 | 다이어그램 표기 → 그림 그리는 커맨드가 읽는 조각으로 | 정본이 안 쓰는 쪽에 있었다 (`diag-B` 3-b) |
| 새로 | `theme-apply`가 커맨드를 흡수 | `theme` 커맨드는 위임만 했다 (`diag-A` 2절) |

### description 등급을 기계로 강제한다

v1은 자율 7개 중 6개가 오발동 억제 신호를 달아 등급이 뒤집혔다(`diag-B` 3-a). v2는 **등급을 frontmatter 필드로 두고** 검사기가 문형을 대조한다. 규칙 파일이 정본인 구조를 버린다.

## 에이전트 — 5개에서 4개로

`verifier`가 테스트 실행과 남의 발견 반증을 겸해 경계가 겹쳤다(`diag-A` 3절).

| 에이전트 | 무엇 | 도구 |
|:--|:--|:--|
| `explorer` | 넓게 읽고 결론만 | Read·Grep·Glob |
| `builder` | 구현 — **쓰기 권한은 여기 하나** | 전체 |
| `verifier` | **실행** — 테스트를 돌려 exit code로 판정 | Read·Grep·Glob·Bash |
| `gatekeeper` | **대조·반증** — 남의 주장을 의심한다 | Read·Grep·Glob |

경계가 도구 권한과 일치한다.

## 가드 — 목록을 데이터로, 등급을 나눈다

`guard-rules.json`이 정본이고 셸이 그걸 읽는다. 늘리는 비용이 **한 줄**이 된다.

v1 실측 미탐 9건을 반영하되, 등급을 가른다.

| 등급 | 무엇 | 왜 |
|:--|:--|:--|
| `block` | 되돌릴 수 없는 것 — `push --force` · `reset --hard` · `branch -D` · `worktree remove --force` · `gc --prune` | v1 기준 |
| `block` | **방어를 끄는 것** — `commit --no-verify` · `-c core.hooksPath=` | 새로 추가. AI가 스스로 층을 끄는 길이었다 (`diag-C` 3절) |
| `block` | 외부 상태를 만드는 것 — `gh pr/issue/repo create` · `gh workflow run` | 새로 추가 |
| `ask` | 판단이 갈리는 것 — `commit --amend` · `stash pop` · `tag -d` | 무조건 막으면 정상 작업이 걸린다 |

**`/flow:commit`이 `--no-verify`를 붙이던 경로를 없앤다.** v1은 커맨드 자신이 드리프트 훅을 끄고 있었다.

### 방어 층은 경로별로 적는다

v1 README는 "드리프트 4겹"이라 적었지만 실제로는 사람 경로만 4겹이고 AI 경로는 옵트인 CI 1겹이었다(`diag-C` 3절). v2는 **표에 경로를 나눠 적는다** — 층 수를 세지 않는다.

## 검사기 — 폐기 판정이 있는 구조

v1 `lint-docs.py` 407줄 중 검사 하나는 사문화된 채 화이트리스트 22개를 유지하고 있었고 통과 숫자로는 구별되지 않았다(`diag-C` 2절).

v2는 **각 검사에 픽스처를 붙인다.** 어기는 입력을 넣어 실패하는 것까지 확인해야 검사가 등록된다.

```
scripts/
  lint.py               검사 본체
  lint.test.py          검사마다 통과 케이스 1 + 위반 케이스 1
```

위반 케이스가 통과하면 그 검사는 **사문화로 표시되고 테스트가 실패한다.** CLAUDE.md의 *"훅은 되돌려서 실패하는지도 확인한다"* 를 기계로 옮긴 것이다.

## 남기는 것 — 진단이 값어치를 확인한 것

새로 짜지 않고 그대로 이식한다. 재작성하면 그 사고를 다시 낸다.

| 무엇 | 왜 |
|:--|:--|
| `guard-danger.sh`의 인용 인식 스캐너 | `"it\'s a fix"`가 가드를 통째로 껐던 사고가 테스트에 박혀 있다 |
| `drift-hook.sh`의 `set -f` | 글로브가 디스크 파일로 확장돼 하위 파일을 놓친 사고 |
| 훅↔CI 나란히 판정 | 같은 규칙의 두 구현이 어긋나는 것을 별도 실패로 분리 |
| 표 렌더 검사 4종 | 눈에 안 보이는데 문서를 깨뜨린다 |
| `bump-version.sh`의 이중 대조 | 두 매니페스트가 어긋나면 업데이트가 전달되지 않는다 |
| 요구 ID 추적 축 | 이 플러그인의 유일한 발명이다. 버리면 남는 게 없다 |
| 도구 권한이 경계 | 말이 아니라 frontmatter가 막는다 |
| 자기 검증 금지 | LLM 자기확인 편향에 대한 실질적 방어 |
| `critical`은 룰 기반만 차단 | 오탐으로 파이프라인이 멈추는 것을 막는다 |
| 레거시 면제 게이트 | 실전에서만 나오는 규칙이다 |
| `paths` frontmatter로 조건부 로드 | 매 턴 비용을 피한다. v2의 기본으로 |

## 안 하는 것

- **빌드 단계를 두지 않는다.** 생성물을 커밋하고 검사기가 대조한다. 플러그인 설치자에게 빌드를 요구할 수 없다.
- **차단을 allow-list로 뒤집지 않는다.** 과차단은 사람이 훅을 꺼 버리게 만든다. deny-list를 유지하되 늘리는 비용을 없앤다.
- **커맨드를 7개까지 줄이지 않는다.** 국면만 남기면 오버레이가 갈 곳이 없다.
