# flow v2 — 구조

v1(0.8.0) 진단은 `00.diagnosis/`에 있다. 이 문서는 그 진단이 가리킨 처방이고, **1차 설계가 반증 리뷰에서 깨진 부분을 고친 판**이다(`00.diagnosis/review-v2-design.md`).

## 왜 다시 짓나

세 층이 각각 다른 증상을 냈는데 원인이 하나였다.

| 층 | 증상 | 근거 |
|:--|:--|:--|
| 커맨드 | 게이트를 4곳이 약속하고 실제로 거는 곳은 `/flow:run` 하나 | `diag-A` 4절 |
| 스킬 | `/flow:design` 한 번에 1,107줄이 실리고 실사용은 100여 줄 | `diag-B` 4절 |
| 인프라 | 차단 목록 하나 늘리는 비용이 9곳 → 미탐 9건이 남았다 | `diag-C` 4절 |

**정본이 산문이라 기계가 못 읽는다.** 그래서 복제가 생기고, 복제를 맞추는 비용이 변경을 막고, 안 고쳐진 채 낡는다.

## 강제력이 먼저다 — 약속과 기계를 가른다

1차 설계는 "각 커맨드가 자기 진입 조건을 읽어 스스로 판정한다"로 갔다. **리뷰가 이걸 깼고 맞다** — 그건 v1과 같은 프롬프트 순응인데, 진행하려는 쪽이 자기 조건을 판정하니 v1이 갖고 있던 판정 독립성(작업자와 게이트 분리)만 잃는다.

v2는 게이트를 **강제력의 종류로** 가른다. 커맨드는 조건을 **선언만** 하고, 판정은 다른 것이 한다.

| 등급 | 무엇이 판정하나 | 무엇을 판정할 수 있나 |
|:--|:--|:--|
| **기계** | `PreToolUse` 훅이 `flow.topology.json`을 읽는다 | 파일 존재·경로·형식·태그 유무 — **참/거짓이 결정되는 것만** |
| **분리 판정** | `gatekeeper` 에이전트 — 진행하는 쪽이 아니다 | 내용 충족 여부. 룰로 못 접는 것 |
| **약속** | 커맨드 본문 | 위 둘로 안 되는 것. **약속이라고 표에 적는다** |

세 등급을 표로 적는 것이 요점이다. v1은 4겹을 자랑했지만 AI 경로에서는 1겹이었다(`diag-C` 3절). **층 수를 세지 않고 각 층이 어느 경로에서 기계인지 적는다.**

기계 게이트의 실제 형태: 소스 파일에 `Write`/`Edit`가 들어올 때 `PreToolUse` 훅이 해당 유닛의 task 문서와 요구 태그를 확인하고, 없으면 차단한다. 커맨드를 하나씩 부르든 `next`로 돌리든 같은 훅을 지난다.

### 이 기계의 한계를 표에 적는다

`PreToolUse`의 matcher는 **도구 이름**이다. 그래서 다음은 이 훅이 아예 안 돈다.

| 무엇 | 어떻게 다루나 |
|:--|:--|
| `Bash` 경유 쓰기 — `cat >` · `sed -i` · `tee` · `python -c` | `Bash` matcher 쪽 가드가 **소스 경로 리다이렉션**을 본다. 인용 스캐너를 재사용한다 |
| MCP 파일 도구 | **못 막는다.** 한계로 적는다 |

v1은 이 종류의 한계를 `guard-danger.sh` 머리말에 적어 뒀다. **v2도 적는다** — "보장"이라 쓰지 않는다. 기계인 것은 `Write`/`Edit` 경로이고, `Bash`는 가드가 닿는 범위까지, MCP는 밖이다.

### 면제가 없으면 과차단이 되고, 과차단이면 사람이 훅을 끈다

task 문서 없는 쓰기를 전부 막으면 정상 작업이 걸린다. 면제를 규칙으로 둔다.

| 무엇 | 왜 |
|:--|:--|
| `spike/` 아래 | 버릴 코드다. task가 없는 것이 정상이다 |
| 레거시 면제 유닛 | v1이 실전에서 얻은 규칙을 그대로 쓴다 |
| 유닛이 하나도 없을 때 | flow 도입 직후다. v1 `drift-hook.sh`의 "유닛 없으면 검사를 안 켠다"와 같은 판정 |

면제 목록도 `flow.topology.json`이 갖는다. 훅과 문서가 같은 것을 읽는다.

## 축 — 정본은 데이터, 산문은 생성물

정본을 JSON으로 내린다. 훅·검사기는 그걸 읽고, 문서 표는 그걸로 생성한다.

```
flow.topology.json          ← 위상·게이트 조건·커맨드↔조각 연결의 정본
  ├─ PreToolUse 훅           (읽는다 — 기계 게이트가 여기서 걸린다)
  ├─ 각 커맨드의 ## 연결 절   (생성)
  ├─ next.md 체인표          (생성)
  └─ plugin.json description (생성)

guard-rules.json            ← 차단 목록 중 단순 규칙의 정본
  ├─ guard-danger.sh         (읽는다)
  ├─ hooks.test.sh           (읽는다 — 케이스를 여기서 만든다)
  └─ README·CLAUDE.md 차단표 (생성)
```

### 이 관계도 동기화 관계다 — 어디서 강제하는지 적는다

리뷰 지적이 맞다. `정본 JSON → 생성물`은 손 동기화를 없앤 게 아니라 **검출기가 지키는 관계**로 바꾼 것이다. 검출기 실행이 약속이면 v1의 병이 데이터 층에서 반복된다.

그래서 강제 지점을 정한다.

| 어디 | 무엇 | 종류 |
|:--|:--|:--|
| 이 리포의 CI (GitHub Actions) | `lint.py` + `lint.test.py` + `hooks.test.sh` | **기계 — 우회 불가** |
| 이 리포의 pre-commit | 같은 것 (빠른 것만) | 기계 — `--no-verify`로 우회 가능하므로 CI가 정본 |
| `lint.py`의 생성물 대조 | 생성물이 정본과 어긋나면 실패 | 기계 |

**CI는 `.example`가 아니다.** v1은 드리프트 CI를 옵트인 예시로 뒀고 그게 AI 경로가 1겹이던 이유다. 이 리포에서는 필수로 돈다.

생성물은 커밋한다 — 플러그인 설치자에게 빌드를 요구할 수 없다. 대신 손으로 고치면 CI가 잡는다.

**사용자 프로젝트 쪽은 우리가 강제할 수 없다.** 위 표는 이 리포의 이야기다. 설치된 프로젝트에서는 이렇게 갈린다.

| 어디 | 종류 |
|:--|:--|
| 우리가 심는 git 훅 (`drift-hook.sh`) | 기계 — 단, `--no-verify`로 우회 가능 |
| 우리가 주는 CI 워크플로 | **옵트인** — 켜는 것은 프로젝트의 선택이다 |
| 커맨드 본문의 검사 지시 | 약속 |

**옵트인을 기계라고 적지 않는다.** `/flow:setup`이 CI를 켜라고 권하고, 안 켠 프로젝트에는 그 층이 없다는 것을 표로 보여 준다.

### guard 데이터화는 단순 규칙까지다

리뷰 지적대로 v1 규칙의 상당수는 flat 목록이 아니라 예외 로직이다 — `merge --abort`는 허용하고 `--continue`는 차단, `restore`는 `--staged` 없이만 차단, `gh api`는 `-X GET`만 통과.

**예외 로직을 데이터로 내리지 않는다.** 그건 매칭 엔진 재작성이고, 설계가 "재작성하면 그 사고를 다시 낸다"고 적은 그 대상이다.

| 무엇 | 어디 |
|:--|:--|
| 단순 차단 목록 (명령 이름 열거) | `guard-rules.json` — 늘리는 비용이 한 줄 |
| 예외 로직이 붙은 규칙 | 셸에 남긴다. 인용 스캐너와 함께 이식 |
| 인용·heredoc 토크나이저 | v1 그대로 이식. **재작성 금지** |

즉 "늘리는 비용 한 줄"은 단순 규칙에 한한다. 그렇게 적는다.

**갈라진 대가는 정본이 두 곳이 되는 것이다.** 문서 차단표를 JSON에서만 생성하면 셸에 남은 규칙(`merge`·`rebase`·`restore`·`gh api` 계열)은 표에 안 실리거나 손으로 적어야 한다 — v1이 앓던 산문 사본 관계가 축소판으로 남는다.

그래서 **셸 규칙의 머리말을 고정 형식으로 둔다.** 생성기가 그 주석 블록을 긁어 표에 넣고, 검사기가 셸 본문과 머리말이 어긋나면 실패시킨다. 문서 표에는 `JSON 정본`과 `셸 정본`을 절로 나눠 적는다.

### 커맨드 본문도 조각으로 가른다

리뷰가 `design`+`spec` 접기에서 짚은 위험이 실재한다 — 두 커맨드가 183+166줄이라 합치면 v1 최대(`run` 297줄)를 넘고, **기능 스펙을 반복 호출할 때마다 시스템 설계 절차가 같이 실린다.**

그래서 스킬에 쓰는 패턴을 커맨드에도 적용한다.

```
commands/design.md          얇게 — 레벨 판정 + 어느 조각을 읽나
procedures/design/
  system.md                 시스템·도메인 레벨 절차 (도메인당 1회)
  feature.md                기능 레벨 절차 (기능마다 반복)
```

**조각은 `commands/` 밖에 둔다.** `commands/` 하위 디렉터리는 커맨드 로더의 스캔 표면이라, 조각을 거기 두면 커맨드로 오인 등록되거나 `design.md`와 이름이 충돌할 여지가 생긴다. `design.md`가 `${CLAUDE_PLUGIN_ROOT}/procedures/…` 경로로 읽는다 — 스킬 `references/`와 같은 방식이다.

**조건**: 이렇게 해서 `design.md` 본체가 얇아지지 않으면 접기를 되돌린다. 접는 것이 목적이 아니다.

같은 이유로 `/flow:verify`의 두 일(테스트 실행 / 요구 커버리지 감사)도 조각을 가른다. 도구·에이전트·병렬 전략이 다르다는 진단 권고를 인자 하나로 눌러 덮지 않는다.

### `next`가 흡수하지 않는 것

v1 `ask`에는 라우팅이 아닌 기능 셋이 얹혀 있었다(`diag-A` 2절). 그중 둘은 **안전 규칙**이라 없애면 회귀다.

| v1 | 무엇 | v2에서 어디 |
|:--|:--|:--|
| `ask` 1-A | 운영 장애 — 완화 우선, **완화를 우리가 실행하지 않는다** | `ops-doc` 스킬이 정본. `next`가 그 상황을 만나면 싣는다 |
| `ask` 1-D | SOP 실행 — **`사람만` 단계는 실행하지 않는다** | 같음 |
| `ask` 1-B | 재개 지점 | `next`에 자연 흡수 |

v1 `run`의 나머지도 갈 곳을 적는다.

| v1 `run` | v2에서 어디 |
|:--|:--|
| 실패 시 되돌아갈 범위 계산 (추적 축의 일부) | `traceability`의 조각 |
| 재시도 3회 · 정지·재개 처리 | `next` 본문 |
| 체인 위상 | `flow.topology.json` (생성 표) |

## 스킬 — 얇은 SKILL.md + references/

SKILL.md는 **판정과 인덱스**만 싣는다. 긴 규약은 `references/*.md`로 내리고 필요할 때만 읽는다.

```
traceability/
  SKILL.md            ~40줄   무엇을 언제 읽나 + 판정 기준
  references/
    id-system.md              ID 체계·이름
    conflict.md               동시 발급 충돌
    unit-state.md             유닛·task 상태 계산
    revert-scope.md           실패 시 되돌아갈 범위
```

`/flow:design`이 싣는 양이 332줄에서 40줄이 된다.

### 지연 로드의 뒷면 — 규약 미적재를 방어한다

리뷰가 v1엔 없던 실패 모드를 짚었다. v1은 비쌌지만 규약이 **항상 있었다.** v2는 SKILL.md가 읽기를 지시하지 않으면 규약이 **아예 없는 상태**로 작업이 지나간다.

방어를 둘 둔다. **둘 다 기계가 아니다 — 그렇게 적는다.**

1. **SKILL.md의 40줄은 판정표다.** "어떤 상황이면 어느 조각을 반드시 읽는다"가 본문의 대부분이고, 규약 내용은 조각에만 있다. 판정을 못 하게 만들지 않는다.
2. **산출물에 읽은 조각을 적는다.** 검사기가 "이 상황인데 이 조각 기록이 없다"를 대조한다.

**2번이 잡는 것은 잊음까지다.** 기록은 자기 보고라 안 읽고 "읽음"이라 적는 경로를 검사기가 구별할 수 없다. 상황 판정을 기계가 할 수 있으면 애초에 훅 등급으로 강제하면 되고, 못 하면 검사기도 상황을 모른다. 그래서 이건 **리마인더이고 방어가 아니다.** 지연 로드를 택한 대가로 남는 위험이다.

**분할 기준은 소비자다.** 한 조각을 두 커맨드가 항상 같이 쓰면 나누지 않는다 — v1의 `tdd-verify`/`test-spec` 분리가 로드를 못 줄인 이유가 그것이다(`diag-B` 3-e).

### 스킬 목록 재획정

| 조치 | 대상 | 근거 |
|:--|:--|:--|
| 합침 | `tdd-verify` + `test-spec` → `testing` | 두 커맨드가 항상 같이 싣는다 (`diag-B` 3-e) |
| 합침 | `code-audit` → `code-review`의 조각 | 같은 체크리스트다 (`diag-B` 부수 관찰) |
| 옮김 | `doc-template`의 절 등급 표 → `doc-verify` | 등급을 쓰는 쪽이 거기다 (`diag-B` 2절) |
| 옮김 | 다이어그램 표기 → 그림 그리는 커맨드가 읽는 조각으로 | 정본이 안 쓰는 쪽에 있었다 (`diag-B` 3-b) |
| 흡수 | `theme` 커맨드 → `theme-apply` 스킬 | 커맨드는 위임만 했다 (`diag-A` 2절) |
| 정본 | `ops-doc`에 운영 장애·SOP 안전 규칙 | `ask`에서 옮겨온다 |

### 커맨드↔스킬 연결도 정본을 둔다

v1 최다 실측 결함이 여기였다 — `## 연결` 절이 본문과 15+23건 어긋났고 검사기는 세 줄의 존재만 봤다(`diag-A` 2절).

`flow.topology.json`이 **어느 커맨드가 어느 스킬의 어느 조각을 싣나**를 갖는다. `## 연결` 절은 그것의 생성물이고, 스킬 `description`의 사용처 문장도 같은 데이터로 검사한다. 매 턴 실리는 거짓말(`diag-B` 3-g)이 구조적으로 불가능해진다.

### description 등급

v1은 자율 7개 중 6개가 오발동 억제 신호를 달아 등급이 뒤집혔다(`diag-B` 3-a). v2는 등급을 데이터로 두고 검사기가 문형을 대조한다.

**구현 전 확인할 것**: SKILL.md frontmatter에 비표준 필드를 두는 것이 Claude Code에서 경고 없이 허용되는지. 안 되면 `flow.topology.json` 쪽에 둔다.

## 에이전트 — 5개 유지

1차 설계가 `reviewer`를 무언급으로 지웠다. **리뷰 지적이 맞다** — 그러면 "critical은 룰 기반만 차단"을 수행할 주체가 없어진다. 복원한다.

| 에이전트 | 무엇 | 도구 |
|:--|:--|:--|
| `explorer` | 넓게 읽고 결론만 | Read·Grep·Glob |
| `builder` | 구현 — **쓰기 권한은 여기 하나** | 전체 |
| `verifier` | **실행** — 테스트를 돌려 exit code로 판정 | Read·Grep·Glob·Bash |
| `reviewer` | **격리 리뷰** — OCR·정적분석 도구를 돌려 룰 기반 발견을 만든다 | Read·Grep·Glob·Bash |
| `gatekeeper` | **대조·반증** — 남의 주장을 의심한다. 진입 게이트의 내용 판정 | Read·Grep·Glob |

`verifier`와 `reviewer`가 둘 다 Bash를 쓰지만 나누는 이유는 산출이 다르기 때문이다 — 하나는 통과/실패, 하나는 severity 붙은 발견 목록이다. `gatekeeper`에 Bash가 없는 것은 의도다. 도구를 돌리는 쪽과 판정하는 쪽을 가른다.

## 가드 — 목록을 데이터로, 등급을 나눈다

v1 실측 미탐 9건을 반영하되 등급을 가른다.

| 등급 | 무엇 | 왜 |
|:--|:--|:--|
| `block` | 되돌릴 수 없는 것 — `push --force` · `reset --hard` · `branch -D` · `worktree remove --force` · `gc --prune` | v1 기준 |
| `block` | **방어를 끄는 것** — `commit --no-verify` · `-c core.hooksPath=` | 새로 추가. AI가 스스로 층을 끄는 길이었다 (`diag-C` 3절) |
| `block` | 외부 상태를 만드는 것 — `gh pr/issue/repo create` · `gh workflow run` | 새로 추가 |
| `ask` | 판단이 갈리는 것 — `commit --amend` · `stash pop` · `tag -d` | 무조건 막으면 정상 작업이 걸린다 |

**`/flow:commit`이 `--no-verify`를 붙이던 경로를 없앤다.** v1은 커맨드 자신이 드리프트 훅을 끄고 있었다.

## 검사기 — 폐기 판정이 있는 구조

v1 `lint-docs.py` 407줄 중 검사 하나는 사문화된 채 화이트리스트 22개를 유지하고 있었고 통과 숫자로는 구별되지 않았다(`diag-C` 2절).

```
scripts/
  lint.py               검사 본체 — --list 로 검사 목록을 노출한다
  lint.test.py          검사마다 통과 케이스 1 + 위반 케이스 1
```

- 위반 케이스가 통과하면 그 검사는 **사문화로 표시되고 테스트가 실패한다.**
- 픽스처 없는 검사가 `--list`에 있으면 테스트가 실패한다. **검사를 더하고 테스트를 안 붙이는 길을 막는다.**
- 대상 0건일 때 "전부 통과"라고 말하지 않는다. 대상 수를 출력한다.
- **검사기 자체의 고장과 문서 위반 발견을 exit code로 가른다.** 무력화된 검사는 스택 트레이스가 아니라 그 검사 `id`를 지목한 실패로 나와야 한다.

반드시 넣을 검사 셋을 여기 적는다 — 리뷰가 이 셋을 요구했다.

| 검사 | 무엇을 막나 |
|:--|:--|
| 생성물 ↔ 정본 대조 | 생성물을 손으로 고치는 것 |
| `gatekeeper` 위임 지시 유무 | v1 결함의 원형 — 게이트를 약속만 하고 아무도 부르지 않는 것 |
| 커맨드↔조각 연결 ↔ `topology` 대조 | `## 연결` 절이 본문과 어긋나는 것 (v1 최다 실측 결함) |
| 셸 가드 머리말 ↔ 셸 본문 대조 | 갈라진 정본 중 셸 쪽이 낡는 것 |

CLAUDE.md의 *"훅은 되돌려서 실패하는지도 확인한다"* 를 기계로 옮긴 것이다. **훅 테스트에도 같은 원칙을 적용한다** — `guard-rules.json`에서 항목을 지우면 케이스가 실패해야 한다.

새로 짜지 않고 그대로 이식한다. 재작성하면 그 사고를 다시 낸다.

| 무엇 | 왜 |

## 안 하는 것

- **빌드 단계를 두지 않는다.** 생성물을 커밋하고 CI가 대조한다. 플러그인 설치자에게 빌드를 요구할 수 없다.
- **차단을 allow-list로 뒤집지 않는다.** 과차단은 사람이 훅을 꺼 버리게 만든다. deny-list를 유지하되 늘리는 비용을 없앤다.
- **예외 로직을 데이터로 내리지 않는다.** 매칭 엔진 재작성이 된다.
- **커맨드를 7개까지 줄이지 않는다.** 국면만 남기면 오버레이가 갈 곳이 없다.
- **얇아지지 않으면 접지 않는다.** `design`+`spec`은 조각 분리로 얇아지는 것이 조건이다.
