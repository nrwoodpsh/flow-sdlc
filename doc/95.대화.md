## 확정된 것 — 라운드 순

### R1 — 시스템 구분은 3+1이다

Q(Claude): 쓴 것을 3가지 시스템으로 가르면?
A(사용자, 정정으로 확정):

- **Pre-Design 시스템** — 요구 수집·분석 → 요구정의서 → 화면설계서(Notion·Figma). 다음 시스템으로 넘기는 방식은 미정(Notion? Figma? 지식그래프?)
- **Developer 시스템** — 기술 검토 → task 분할 → 구현 → 검증 → 리뷰(설계 의도대로 구현됐나)
- **Operator 시스템** — 운영 문제 기록(구현이 남긴 로그를 테이블로 스케줄링) · 사람 최종 점검 후 배포 버튼
- **Knowledge 시스템**(횡단) — 모든 정보를 온톨로지로 저장, 도메인 지식 포함. 위 세 시스템이 활용

판정: 생애주기(설계 전/개발/운영) + 횡단(지식) 구분이 기능 구분보다 낫다 —
시스템 경계가 조직의 사람 경계와 일치해서 "누가 여나"가 자연스럽게 정해진다.

### R2 — 동기는 이해의 아픔이다

Q(Claude): 이 그림을 그리게 한 아픔은 ①통제(AI 불신) ②지식(맥락 흩어짐) ③실행(생산성) 중 어디?
A(사용자): **②** — AI 산출물이 많아 이해하고 따라가기 힘들다. 그래서 사람 개입의 경계를 그었다.

판정: 경계는 증상 완화(따라갈 것을 줄임), Knowledge 시스템이 원인 치료다.
아픔이 ②인 이상 Knowledge 시스템은 장식이 아니라 **존재 이유**다.

### R3 — Knowledge의 쓰기 권한

Q(Claude): 온톨로지에 누가 쓰나 — (a) 사람이 직접 편집 (b) 산출물에서 자동 생성?
A(사용자): 도메인 지식은 **사람과의 협업**으로, 운영 지식은 **기계가 주**가 되어 넣는다.

확정 규칙 — 지식 종류별로 정본 방향을 고정한다:

| 지식 | 성질 | 정본 | 상대는 |
|:--|:--|:--|:--|
| 도메인 지식 (요율·규정·용어) | 선언 — 세상에서 온다 | **사람** | 기계는 제안만 |
| 운영 지식 (배포 이력·장애·패턴) | 관측 — 시스템에서 난다 | **기계** | 사람은 해석만 |

경계 원칙("누가 여나")을 시스템 사이만이 아니라 지식 안쪽에도 적용한 것 — 설계가 일관된다.

### R4 — 킬러 질의 정정: 병은 이해 부채다

Q(Claude 가설): Developer의 킬러 질의는 역방향 추적(이 코드를 고치면 뭐가 영향받나)?
A(사용자, **정정**): 아니다. 병은 **정보 생성량이 사람의 흡수량을 절대적으로 앞지르는 것** —
설계·구조를 확실히 이해하지 못한 채 진행하면 개발 단계에서 헤맨다.

판정: 이해 부채(comprehension debt)는 경계 파이프라인 전체의 붕괴 모드다.
사람의 결정 지점 6곳은 사람의 이해를 전제하는데, 이해 없는 컨펌은 고무도장이 된다.
킬러 질의는 기계용이 아니라 **사람용**이다:
*"내가 지금 컨펌할 이것 — 뭘 하고, 왜 그렇게 결정됐고, 전체 어디에 놓이나 — 한 장으로."*

### R5 — 헤맴의 정체: 셋 다, 그래서 지도 하나

Q(Claude): 헤맬 때 몰랐던 것은 (a)구조 (b)결정 (c)상태 중 무엇?
A(사용자): **전부.**

판정: 닻이 아예 없다는 진단이다. 셋은 세 문서가 아니라 한 지도의 세 레이어다(내비게이션 구조):

| 레이어 | 내비로 치면 | 변하는 속도 | 사람의 몫 |
|:--|:--|:--|:--|
| 구조 | 지도 | 느리다 — 설계 때만 | **기억한다** (한 번 이해하면 오래 간다) |
| 결정 | 왜 이 길인가 | 쌓이기만 한다 | 조회한다 — ADR |
| 상태 | 현재 위치 점 | 매일 변한다 | 조회한다 — **기계가 계산·갱신** |

이해 부채의 원인: 셋이 같은 속도의 문서 더미로 섞여 도착해 사람이 셋 다 기억하려다 무너진다.
가르면 사람이 기억할 것은 구조뿐이고, 결정·상태는 조회다.
Knowledge 시스템의 사람용 출력 = 온톨로지에서 뽑는 **투영(projection)**, "You are here" 한 장.

### R5 보충 — 생산과 제공은 다르다

사용자 반문: 구조·결정·상태는 전부 Developer 시스템의 역할 아닌가?
답: **만드는 것**은 Developer가 맞다 — 일하면서 흘리는 부산물이다. 그런데 그 부산물의
양이 곧 이해 부채의 원인(R4)이다. **모아서 사람이 소화할 형태로 내주는 것**이 Knowledge의 몫.
내비 비유 — Developer는 운전(위치를 만든다), Knowledge는 내비 화면(어디·왜·얼마나를 보여준다).
※ 이 반문 자체가 R4의 병을 실증했다 — "한 장"이라는 말을 앞질러 써서 사용자가 놓쳤다.
용어를 만들면 즉시 풀어 말할 것.

### R6 — "한 장"은 둘 다: 같은 투영의 두 배달 시점

Q(Claude): 현황 한 장을 언제 보나 — (a) 승인 요청에 첨부 (b) 상시 화면 (c) 둘 다?
A(사용자): **(c) 둘 다.**

판정: 다른 물건이 아니라 같은 투영의 두 시점이다.
승인 첨부(푸시) = 결정용, 그 결정 관련 조각만(줌 인) / 상시 화면(풀) = 복귀용 닻, 전체 지도(줌 아웃).

**여기까지로 Knowledge 시스템의 출력 사양이 확정됐다:
쓰기 규칙(R3) + 사람용 투영 한 장 + 줌 두 단계(R6).**

### R7 — ID 발급: 사람 규율이 아니라 도구+경계가 한다 (구조도 수정)

Q(Claude): Pre-Design 산출물의 ID(SYS-*·SCR-N)는 실무에서 누가 붙이나 —
(a) 기획자가 양식 따라 직접 (b) 주입 시 기계가 부여·사람 검수 (c) 도구가 자동 발급?
A(사용자): **(b)+(c).**

판정: **HTML 구조도의 전제(a — "사람이 ID 발급, 양식이 강제")를 사용자 스스로 기각했다.**
a안은 시스템 전체에서 유일하게 사람 규율에 기대는 조각이었다 — b+c가 "말이 아니라
기계가 막는다"는 자기 철학과 더 일관된다.

확정 규칙 — **정본 ID는 경계에서 찍는다**: Notion 행 ID·Figma 프레임 이름은 원천 키,
경계 1에서 기계가 우리 체계(SYS-*·SCR-*)로 정규화·도장하고 원천 키 매핑을 보관한다.
도구가 바뀌어도 정본 ID는 산다. 사람의 검수 대상은 내용이지 ID가 아니다.
이 답으로 미결 둘이 닫혔다 — 외부 양식 소유(도구가 소유, 경계가 정규화) ·
주입 방식(도구 연동이 ID를 나른다).

### R8 — 역주입: 자동 개입, 단 정확 조인만

Q(Claude): 같은 장애가 두 번 나면 누가 알아차리나 — (a) 조회로만 (b) 다음 요구로
(c) 개발 체크에 자동 개입?
A(사용자): **(c).**

판정과 조건 둘:

- (c)는 R7 위에서만 성립한다 — 장애 로그→모듈→task→요구가 ID로 이어져야 자동 개입이 가능하다.
- (c)의 붕괴 모드는 오탐이다 — 무관한 이력이 끼어들면 개발자가 무시하고 (a)로 퇴화한다.
  처방은 판별식 그대로: **정확 조인(같은 모듈 ID·에러 시그니처)만 자동, 유사도 판단은 AI 제안으로 격하.**
- 기제는 이미 실측됐다 — 훅의 additionalContext 주입(F2 재실측에서 끝까지 작동 확인).

### R9 — 6하 파싱: 문법 역할 → 시스템 개체 (사용자 발제, 표 확정)

Q(사용자 발제): 6하 원칙으로 프롬프트·요구를 파싱 — 주어=액터, 명사=화면, 동사=기능.
분석·설계·요구·구현·리뷰에서 쓰면 어떨까?
A(Claude 가설 표 제시 → 사용자 **확정**):

| 6하 | 문법 | 시스템 개체 |
|:--|:--|:--|
| 누가 | 주어 | 액터 — 권한의 근거 |
| 무엇을 | 명사 | **화면 또는 데이터 또는 외부시스템** (화면 하나로 몰지 않는다 — 배치·API는 화면이 없다) |
| 어떻게 | 동사 | 기능 — SYS-*·task의 단위 |
| 언제 | 부사절 | 트리거·조건 — 이벤트·배치 주기 |
| 어디서 | 부사구 | 채널·시스템 경계 — 웹/모바일/외부연동 |
| 왜 | 목적절 | 요구의 근거 — 도메인 지식·ADR로 가는 링크 |

판정 — 계보가 검증돼 있다(Abbott 텍스트 분석 1983 · 유스케이스 1992 · User Story).
독창은 명사=화면 대응(한국 SI의 화면설계서 등뼈를 문법에 박은 것). 시스템에 꽂히는 지점 셋:

- **R7의 빈칸을 채운다** — "주입 시 기계가 ID 부여"의 방법이 이것이다. 6하 파싱 = ID 추출기
  (주어→액터, 명사→SCR-*, 동사→SYS-*).
- **빠진 주어 = 빠진 결정** — 한국어 요구서는 주어를 생략한다. 파싱 실패 지점이 곧
  역추출 검토(경계 1)가 사람에게 돌려보낼 모순 목록이다. 파서의 실패가 리뷰 소견이 된다.
- **온톨로지 스키마의 씨앗** — 노드 타입(액터·화면·기능·데이터)과 엣지(액터가-기능을,
  기능이-화면에서)가 문법에서 나온다. "스키마는 질의에서 역산"(R8까지)과 다른 방향에서
  출발해 같은 지점에서 만났다.

파싱의 격은 판별식을 따른다 — 추출은 AI(제안), 확정은 사람, 추출된 ID의 연결 대조는 코드.

## 검증 종합 — 8라운드의 결론

**확정된 시스템 한 장:**

| 시스템 | 주인 | 확정된 것 |
|:--|:--|:--|
| Pre-Design | 사람+도구 | ID는 사람 규율이 아니라 도구 원천 키 + 경계 정규화(R7) |
| Developer | AI 수행·툴 판정·사람 컨펌 | 승인마다 "한 장"(투영) 첨부 — 이해한 상태에서 컨펌(R6) |
| Operator | 기계 기록·사람 배포 버튼 | 운영 지식은 기계 정본, 자동 적재(R3) |
| Knowledge (횡단) | 이중 정본(R3) | 출력 = 사람용 투영 한 장 · 줌 2단계(R6) · 역주입 = 정확 조인 자동 개입(R8) |

**가치 명제(최종)**: 이 시스템의 차별점은 AI 생산성이 아니라 **"이해 부채를 지도로 갚는다"**이다.
시장의 AI 코딩 도구가 생산(더 빨리 만들기)에 몰려 있을 때, 이 구상은 이해(사람이 따라가기)에
정면으로 선다 — 동기(R2)와 킬러 질의(R4)가 전부 그 축이다.

**실무 적용(최종)**: 가치 있음. 순서는 보고서 로드맵 유지 — 경계 파이프라인 지금 ·
결정적 계산기 다음 · 그래프는 운영에서 추출. ID 경계 발급(R7)이 전 체인의 첫 관문.

### R15 — 명명 확정: bridge / flow / know-flow

최종 시스템(회사 orchestration + 사람·기계 경계)의 이름을 문답으로 확정했다:

| 층 | 이름 | 비고 |
|:--|:--|:--|
| 최종 시스템·리포 | **bridge** | 함교(사람이 지휘, 기계가 항행) + 다리(경계를 건너는 산출물) 이중 뜻 |
| 플러그인·프리픽스 | **flow** 유지 | flow-sdlc 패턴 그대로(리포 이름 ≠ 플러그인 이름) — 커맨드 재학습 없음 |
| 지식 시스템 | **know-flow** | bridge 안의 Knowledge 층 |

계보: setting-ai → flow-sdlc → bridge. 축약 프리픽스(brdg 등)는 검토 후 기각 —
프리픽스는 flow 를 계승한다. **주의**: 플러그인 이름이 곧 프리픽스라 flow-sdlc 의 flow 와
bridge 의 flow 는 공존 불가 — bridge 의 플러그인은 flow 의 다음 판(계승)으로 낸다.

- `@import`는 절약이 아니다 — 세션 시작 시 전부 확장된다. 일반 링크는 절약되지만 읽는 보장이 없다.
  안 읽힌 규칙은 없는 규칙 — 매 턴 지켜질 것을 링크 뒤에 숨기지 않는다.
- `paths` 없는 rules 파일은 상시 로드다 — rules에 넣어서가 아니라 paths를 걸어서 절약된다.

**두 자원을 혼동하지 않는다:**

- 컨텍스트 윈도우(1M) — **에이전트 인스턴스당 각자.** 서브에이전트는 부모 대화를 공유하지 않고
  새 윈도우를 받으며 CLAUDE.md 계층이 복제되어 들어간다(Explore·Plan 제외).
- 사용량 한도 — **계정 단위 공유.** 모든 에이전트의 소비가 합산 차감된다. 캐시 반복분은 원가의 약 10%.
- 그래서 CLAUDE.md 다이어트는 에이전트 수만큼 곱해서 절약된다. 진짜 아끼는 것은 돈보다
  윈도우 공간과 모델 주의력이다.

**멀티에이전트 격리 — 쓰기 에이전트가 2개 이상 동시일 때만 격리한다:**

읽기 전용(탐색·검증·리뷰)은 격리 불필요. 동시 쓰기는 git worktree(`.git` 공유, 작업 폴더만 분리 —
로컬 머지 즉시). 런타임 충돌(포트·DB)이면 컨테이너로 올라간다. 격리는 공짜가 아니다.

**Knowledge 시스템과의 접점**: 그래프 질의가 컨텍스트 조립을 대체하는 것이 이 계층 구조의
종착점이다 — 단 질의층이 생겨도 계층 규율은 유지한다(R8 판정과 같은 문서).

## 문답 진행 규칙 — 다음 세션용

- **한 번에 질문 하나.** 가설을 놓고 맞는지 물어라 — 사용자의 정정이 가장 정보량이 많다 (R4가 증거).
- **확정된 것은 재론하지 않는다.** 위 라운드 목록이 그 경계다.
- **결론을 서두르지 않는다.** 목적은 구현이 아니라 아이디어 검증이다 — 사용자가 명시했다.
- 라운드가 끝나면 이 파일에 덧붙인다 — 확정이면 `확정된 것`으로, 미결이면 `열린 질문`으로.
- **답변은 고정 템플릿 5칸을 따른다** (R10에서 사용자가 확정):

| 칸 | 내용 | 생략 |
|:--|:--|:--|
| 판정 | 결론 한 줄 — 된다/안 된다/조건부 | 항상 넣음 |
| 계보 | 이미 증명된 것인가, 어디서 | 없으면 생략 |
| 연결 | 지금까지의 확정(R#)과 어떻게 맞물리나 | 없으면 생략 |
| 흠 | 정직한 약점 | 못 찾았으면 "못 찾았다"고 명시 — 이 칸만 침묵 금지 |
| 다음 질문 | 가설을 놓고 정정 요청 | 문답 중일 때만 |

  억지로 칸을 채우지 않는다 — 없는 흠을 짓고 무관한 계보를 끌어오는 것이 오탐이고,
  오탐은 템플릿을 사문화시킨다(R8 붕괴 모드와 동일).

### R12 — 실전 시연 피드백: 칸 이름은 일상어, 출력은 목록으로

Q(사용자): 시연을 보니 ① 용어가 어렵다(계보? 흠?) · 줄바꿈 없이 빽빽해 보기 힘들다
