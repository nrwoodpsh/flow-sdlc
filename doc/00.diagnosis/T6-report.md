# T6 — 역추출 규약을 조각으로 세운다 (D8 · 능력 8)

낸 것은 조각 둘과 지도 갱신, 그리고 **배선 패치 명세**다. 배선은 내 소유 밖이라 손대지 않았다.

| 파일 | 줄 | 무엇 |
|:--|--:|:--|
| `plugins/flow/skills/traceability/references/reverse-extract.md` | 75 | 코드에서 요구를 뽑는 규약 |
| `plugins/flow/skills/traceability/references/reverse-check.md` | 67 | 역추출 요구를 코드에 대보는 층 |
| `doc/02.skills-map.md` | +14 | 조각 등재 · 분할 근거 · `prd`·`review` 배선 행 |

## 조각을 왜 둘로 갈랐나

**소비자가 다르다.** `prd` 는 뽑기와 대조를 둘 다 싣지만 `review`(문서) 는 **대조만** 싣는다 —
문서를 채점하는 쪽은 *어디서부터 코드를 읽나* 가 필요 없다. `01.architecture.md`·`02.skills-map.md` 의
분할 규칙(*"한 조각을 어떤 커맨드는 싣고 어떤 커맨드는 안 싣는다"*)의 왼쪽 칸에 걸린다.

안 갈랐다면 `review` 가 진입점 읽는 순서·요구 판별표까지 실었다. 갈라서 그 자리에서 실리는 것이 67줄이다.

## 왜 `traceability` 아래인가 — 새 스킬을 안 세운 근거

| 왜 | |
|:--|:--|
| 산출이 이 스킬의 것이다 | 역추출의 산출은 요구 ID 와 `상태: 확인 필요` 다. 그 정본이 `coverage.md`·`id-system.md` 로 이미 여기 있다. 남의 스킬에 두면 그 규약을 옮겨 적게 되고, **W2 가 잡은 역추출 3중 사본이 정확히 그렇게 생겼다** |
| 로드 단위가 안 늘어난다 | `prd`·`review` 가 `traceability` 를 이미 무조건 싣는다. 새 스킬은 `SKILL.md` 라우터 한 장 + `skills` 등록 + `skill-description-*` 두 검사의 양방향 대조를 늘리고, 실제로 읽히는 양은 그대로다 |
| 이름까지 지목돼 있었다 | W2 `재설계 후보` 의 `traceability/reverse-extract` |

`code-graph` 는 뺐다 — 그쪽은 **변경 국면 전제**로 쓰여 있고(W2 마지막 절: 분석 시점에는 변경 파일이 없다)
소비자가 `build`·`review`·`commit` 이라, 역추출을 거기 두면 `prd` 가 그래프 질의 규약을 함께 싣는다.

## 역추출 규약이 정한 것

**어디서부터 읽나** — 바깥에서 안으로 4회차(진입점 → 서비스·도메인 → 데이터 → 설정).
근거는 하나다: *요구는 밖에서 관측되는 동작이다.* 안쪽부터 읽으면 구현 세부가 요구로 올라온다.
레벨은 **같은 진입점에서 무엇을 집나**를 가른다(`sys` 횡단 구현 · `domain` 경계·용어 · `func` 모듈 동작).

**무엇을 요구로 보나** — 판정 질문 하나(*"이 동작이 없어지면 밖에서 무엇이 달라지나"*)와 6행 표.
**하드코딩된 숫자를 요구로 올리는 것**이 이 표의 핵이다 — 타임아웃·한도·재시도가 레거시 업무 규칙의 실체이고,
그게 안 뽑히면 뒤 국면의 경계값 테스트에 기대값 출처가 없다(`testing/case-source` 가 요구를 출처로 요구한다).
버그는 **요구가 아니다** — 코드가 하는 일과 이름·주석·테스트가 어긋나면 **둘 다 적고 확정하지 않는다.**

**확인과 추정을 어떻게 가르나** — 여기가 새로 세운 축이다. **근거 등급(`확인`/`추정`/`의도 불명`)은
`상태` 와 다른 축**이다. `확인 필요` 는 *사람이 확정 안 했다* 이고 근거 등급은 *우리가 얼마나 봤나* 다.
v1·v2 는 둘을 `확인 필요` 하나로 뭉쳐서, 전수를 다 읽은 요구와 이름만 보고 짐작한 요구가 표에서 구별되지
않았다. 가르면 **무엇을 더 읽어야 하는지가 남고**, `reverse-check` 의 표본 선정 기준이 생긴다
(`추정` 은 표본이 아니라 전수 대조 대상이다).

**ID** — 새로 만들지 않았다. 형식·발급 순서는 `id-system.md`, 착지처는 `level.md` 를 이름으로 가리킨다.
더한 것은 역추출 고유의 셋뿐이다: ① 근거를 **요구 칸 끝**에 붙인다 ② `func` 은 유닛을 안 만든다
③ **회차를 시작할 때 이미 적힌 근거 위치를 먼저 훑는다** — 회차를 나눠 읽으면 같은 동작을 두 번 뽑아
한 동작에 ID 가 둘 생긴다. **근거 위치가 그 대조 키다.**

## 검증 층 — 만들었다. 그리고 못 하는 것을 적었다

D8 의 셋째 항목(*"역추출 요구가 코드와 맞나를 보는 층이 없다"*)에 3층을 세웠다.
**한 층만 실행으로 판정되고 나머지는 그렇지 않다고 조각이 직접 적는다.**

| 층 | 무엇으로 판정하나 | 등급 |
|:--|:--|:--|
| 앵커 — 근거 `{파일}:{심볼}` 이 실재하나 | **실행 결과**(검색이 0건을 낸다) | 실행으로 확인 — `contract-gate` 와 같은 급 |
| 표본 — 그 코드가 적힌 동작을 하나 | `verifier` 가 격리 판정 | 판정 독립성(능력 2)만 확보. 사람이 읽는다 |
| 검수 — 그것이 의도였나 | 사람 | 원래 사람의 일 |

**표본을 역방향으로 읽게 한 것**이 이 층의 유일한 방법론적 장치다. 요구 문장을 먼저 읽고 코드를 보면
확증 쪽으로 읽힌다 — 코드부터 읽어 문장을 새로 쓰고 나서 나란히 놓는다.

**한계로 적은 것 — 조각 안에 표로 있다.**

| 못 하는 것 | 왜 |
|:--|:--|
| **누락** (코드에 있는데 안 뽑힌 것) | 전수 확인은 코드를 처음부터 다시 읽는 비용이다. 이 층은 뽑힌 것만 본다. `coverage` 의 gap 은 반대 방향이라 대신 못 한다 |
| 런타임에 갈리는 동작 | 설정·외부 응답으로 분기가 갈리면 코드에 답이 없다 — 운영 값을 못 보면 `추정` 이다 |
| 표본 밖 | 몇 건 중 몇 건인지 숫자로 적게 하는 것까지다 |
| **기계 강제** | 훅은 문서 내용을 안 본다. 조각 머리에 *"기계가 강제하지 않는다 — 약속이다"* 로 적었다 |

**기계 게이트를 만들자는 유혹을 접었다.** 요구 표의 근거 앵커를 훅이 grep 하는 검사는 만들 수 있어 보이지만,
그건 **사용자 프로젝트의 문서 형식을 훅이 파싱한다**는 뜻이고 `drift-check/rule.md` 가 이미 그 한계를
적어 둔 자리(`00.ref/02.db-schema` 를 못 잡는다)와 같은 종류다. 표 형식을 우리가 못 정하는 문서에
기계를 걸면 fail-open 이 된다 — D1 이 그 형태다.

### 역추출한다 *(`legacy`)*
