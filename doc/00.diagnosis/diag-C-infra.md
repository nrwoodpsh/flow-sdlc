## 3) 고칠 것

**guard-danger.sh 의 방어 축이 명령 이름 열거다 — deny-list라 늘 뒤진다.**
실측 미탐(전부 `통과`):

| 명령 | 무엇이 되돌려지지 않나 |
|:--|:--|
| `gh workflow run deploy.yml` | **배포가 돈다.** 목록에 없는 `gh` 서브커맨드 |
| `gh pr create` · `gh issue create` · `gh repo create` | GitHub에 외부 상태가 남는다 |
| `git branch -D feature/x` | 미머지 커밋이 사라진다 |
| `git worktree remove --force` | 미커밋 변경이 사라진다 |
| `git commit --amend` | 이력을 다시 쓴다(`rebase`는 막는데 이건 안 막는다) |
| `git commit --no-verify` | **drift 훅 층을 끈다** |
| `git -c core.hooksPath=/dev/null commit` | 같음 — 훅 자체를 무력화 |
| `git tag -d` · `git gc --prune=now` · `git stash pop` | 참조·객체·스태시 |

머리말 `26-33`이 "못 막음"으로 적은 것은 셸 우회(`eval`·변수 쪼갬·스크립트 파일)뿐이다. **열거에서 빠진 명령은 한계로도 적혀 있지 않다** — 문서가 실제 방어보다 넓게 읽힌다.

**드리프트 방어가 AI 경로에서는 기계 장치가 아니다.**

CI만 기계인데 `.example`로 옵트인이다. **사람이 Sourcetree로 커밋할 때는 4겹이 맞고, AI 경로에서는 1겹(옵트인)이다.** 이 구분이 어디에도 적혀 있지 않다.

## 4) 이 층의 가장 큰 구조적 결함

**"기계가 막는 것"의 목록이 셸 `case` 문 안에 손으로 열거되어 있고, 그 사본이 문서 5곳에 산문으로 복제되어 있다.**

정본은 `guard-danger.sh` 머리말 `7-25`(CLAUDE.md가 여기를 가리킨다). 사본 — `README.md:71-78` · `guide/getting-started.md:278-298` · `project-template/CLAUDE.md:45` · 같은 파일 `53`(표) · `CLAUDE.md:27`. `plugin-authoring.md:85`는 **"훅 차단 케이스 추가" 시 함께 고칠 곳을 9군데로** 적어 둔다.

세 가지가 동시에 따라온다.

1. **목록에 없는 명령은 조용히 통과한다** — 실측 9건. 그중 둘(`--no-verify`·`-c core.hooksPath=`)은 다른 방어층을 AI가 스스로 끄는 길이다.
2. **목록을 하나 늘리는 비용이 9곳 수정 + 테스트 케이스**다. 그중 하나는 **매 턴 실리는** `project-template/CLAUDE.md`다.
3. **그래서 아무도 안 늘린다.** 146 케이스가 전부 통과하는 상태에서 미탐 9건이 남아 있는 것이 그 결과다.

v2에서 반드시 달라져야 할 것: **차단 목록을 데이터 하나로 두고, 훅·테스트·사용자 문서가 그것을 읽거나 그것으로부터 생성되게 한다.** 지금은 셸 코드·셸 주석·산문 5곳이 각각 손으로 동기화되는 관계다. 그리고 방어 층 수를 자랑하지 말고(4겹) **각 층이 AI 경로에서 실제로 기계인지 표에 명시**해야 한다 — 지금 표는 사람 경로의 그림이다.

부수적으로 같은 병이 검사기에도 있다. `lint-docs.py`는 407줄에 검사 20종을 담고 있는데, 그중 하나(검사 4의 절반)는 **사문화된 채로 화이트리스트 22개를 유지하고 있고 통과 숫자로는 구별되지 않는다.** 검사 추가만 있고 폐기 판정이 없는 구조다.
