# 실측 커버리지와 결함 목록

**원칙은 전 기능 실측이다.** 여기 적힌 것은 전부 **실행 결과**이고, 근거는 회차 로그와
세션 트랜스크립트(`~/.claude/projects/*/*.jsonl`)의 `tool_use` 레코드다.

> **측정 방법을 한 번 틀렸다.** `claude -p` 출력에는 **도구 호출 흔적이 없다** — 최종 답변 텍스트만 나온다.
> 그것만 보고 *"에이전트가 안 불렸다"* 고 판단할 뻔했다. 실제 근거는 트랜스크립트다.
> 아래 에이전트·조각 수치는 전부 트랜스크립트에서 세었다.

## 어떻게 돌렸나

설치하지 않고 `claude --plugin-dir <v2>/plugins/flow -p "/flow:…"` 로 돌렸다.
`flow@setting-ai`(사용 중)와 `flow@inline` 이 공존하는 것을 `claude plugin list` 로 확인했다.
대상은 유튜브 채널 요약 시스템을 레거시 형태로 만든 것(`/tmp/yt-digest` → 사본 `trial-a/b/c`).

## 훅 — 런타임 발화가 확정됐다

정적 검사가 못 보던 자리다. **셋 중 둘이 실제 차단을 실증했다.**

| 훅 | 실측 |
|:--|:--|
| `gate-source-write.sh` | ✅ **런타임 34회 발화**(트랜스크립트) · 셸 직접 8케이스 — File Map 안은 통과, **밖은 전부 차단** |

| `check-drift-hook.sh` | ❌ **미실측**(SessionStart 경고) |

```
git commit --no-verify           ⛔ 차단   ← v1 이 스스로 붙이던 그 플래그다
git -c core.hooksPath= commit    ⛔ 차단
git checkout -- <경로>            ⛔ 차단
gh pr create                     ⛔ 차단
git push --dry-run               통과(정상) — git 자신의 "No configured push destination"
git status --short               통과·정상 실행
```

**v1 결함이 실제로 닫혔다.** v1 은 `/flow:commit` 이 `--no-verify` 를 붙여 드리프트 훅을 껐다.
v2 는 **가드가 그 플래그를 막아** 커맨드가 쓰려 해도 못 쓴다. 그래서 `commit` 이 우회하지 않고 멈췄다.

## 갱신 — `review` 회차와 B 리포트 반영

**`review` 는 조각을 제대로 읽었다.** `code-review/{checklist,layers,severity}` ·
`testing/{run,case-source,integration}` **6개 적재**. `reviewer` 가 실제로 불려 Bash 로 도구를 돌렸고
(계약 tsc · 소스 tsc · `npm test` 19 passed · 셔플 전부 Exit 0), `gatekeeper` 반증으로 **2건이 기각**됐다.
`npm run build` 가 Exit 127(`tsc` 없음)인 것도 잡아 보고했다.

> **그래서 F2 는 계통 결함이 아니라 커맨드별 편차다.** `review` 6개 · `sync` 4/8 · `build` 1/7 · `commit` 0/3.
> *"조각을 못 읽는다"* 가 아니라 **어떤 커맨드는 읽고 어떤 커맨드는 안 읽는다** 가 정확한 서술이다.
> 수정도 계통 장치가 아니라 **안 읽는 커맨드의 본문**을 봐야 한다.

**에이전트는 5개 중 4개가 실측됐다** — `verifier`·`gatekeeper`·`builder`·`reviewer`.
`explorer` 만 전 회차 **0회**다(F3).

| 훅 | 발화 | 모델·stdout 에 닿나 |

`main` 이라 `feat/collect-quota` 를 만들어 커밋했다. **v1 결함이 닫혔다.**

## F2 재현 시험 — 명령형 지시가 효과가 있다 (실측)

설계 완료·구현 전 상태의 사본 둘을 만들어 `build` 를 **독립적으로 두 번** 돌렸다.
본문에는 새로 넣은 `먼저 규약을 읽는다` 절이 있다.

| | 조각 | 절차 | 선언 7개 중 |
|:--|--:|--:|:--|
| 고치기 전 (yt-digest) | **0** | **0** | **0/7** |
| rb1 | 9 | 2 | **7/7** + 조건부 2(`code-graph/query`·`impact-analysis/regression-surface`) |
| rb2 | 8 | 2 | **7/7** + 조건부 1(`doc-template/task-doc`) |

**0 → 7/7 이 두 번 재현됐다.** 절차 조각도 둘 다 2/2 읽었다.
조건부도 상황에 맞게 갈렸다 — `channel.ts` 가 `[Mod]` 라 *기존 코드를 고칠 때만* 조건이 발동했다.

에이전트도 정상이었다 — `builder`·`verifier`·`gatekeeper`, rb1 은 구현↔검증 루프가 두 번 돌았다.

**그래서 판정은 이렇다.**

- **개입은 효과가 있다.** 조각을 절차 중간의 괄호로 가리키는 것(인용)과 절을 세워 명령형으로
  적는 것(지시)은 **행동이 다르다.** n=2 로 재현됐다.
- **다만 필요조건은 아니다.** `design` 은 그 절이 없는데도 7개를 읽었다 — 왜인지는 여전히 모른다.
  즉 **충분조건이지 필요조건이 아니다.**
- **그래서 나머지 커맨드도 같은 처방이 필요하다.** 지금 그 절이 있는 것은 `build`·`commit`·`design`
  셋뿐이고, `setup`·`spike`·`publish`·`review`·`sync`·`verify`·`prd`·`next` 는 없다.
  없는 것이 반드시 실패한다는 뜻은 아니지만, **보장이 없다.**

## F2 재확인 — 지시서로는 **보장할 수 없다**

읽기 절을 11개 커맨드 전부에 세운 뒤 `sync` 를 돌렸다. 결과가 앞의 낙관을 깼다.

| 회차 | 선언 | 적재 | 읽기 절 |
|:--|--:|--:|:--|
| `build` 고치기 전 | 7 | **0** | 없음 |
| `build` rb1 | 7 | **7** | **있음** |
| `build` rb2 | 7 | **7** | **있음** |
| `sync` 고치기 전 | 8 | 4 | 없음 |
| **`sync` 고친 뒤** | 8 | **0** | **있음** |

`sync` 는 조기 종료가 아니었다 — 작업 트리 diff 가 로그 삭제뿐인 것을 알아보고 **HEAD 커밋의
소스 변경을 대상으로 잡아** 분류·갱신을 다 했다. 그러면서 선언 8개를 하나도 안 읽고,
**선언에 없는 `doc-verify/scoring` 을 대신 읽었다.**

**그래서 판정은 이렇다.**

- **읽기 절은 확률을 올린다.** `build` 에서 0 → 7/7 이 두 번 재현됐다. 인용보다 지시가 낫다는 것은 유지된다.
- **그러나 보장이 아니다.** 같은 처방을 받은 `sync` 가 오히려 4 → 0 이 됐다.
- **지시서로 조각 적재를 보장할 수 없다** — 이것이 실측 결론이고, `01.architecture.md` 가
  이 위험을 **방어 칸이 아니라 위험 칸**에 둔 판단이 옳았다는 증거다.
- 검사기(`fragment-read-instructed`)가 지키는 것은 **지시가 있나**까지다. **읽었나는 못 본다** —
  그건 런타임 행동이고 정적 검사의 밖이다. 검사 이름이 그렇게 되어 있다.

**F2 는 "닫힘" 이 아니다.** 개선했고, 남은 위험의 범위를 좁혀 적었다.

```
커버리지: gap 1건 · 검증됨 4 · 현행(미검증) 1건 · 상위 미연결 5건
```

- **`현행(미검증)` 이 gap 과 따로 세어졌다.** `coverage` 조각이 *"안 가르면 요구 전부가 gap 으로 나와
  리포트가 쓸모없어진다"* 고 적은 그 분리가 지켜졌다.
- **자기 결론을 정본에 맞춰 뒤집었다** — *"`부분 검증` 은 정본 4버킷에 없다"* 며 gap 으로 재분류했다.
- **경계 판단이 정확했다** — *"요구가 없다는 사실 자체는 gap 이 아니다(gap 은 요구 축에 정의된다)"* 로
  빌드·배포 요구 0건을 결함 축으로 돌렸다.

### F2 의 실해가 예상보다 작다 — 층이 받았다

`build` 가 조각을 안 읽어 `5.verify` 에 진행 필수 3절(`판정`·`완료 기준 매핑`·`미검증`)을 빠뜨렸는데,
**`verify project` 가 그것을 차단으로 잡았다.** 한 층의 미적재가 최종 결과까지 통과하지 못했다.

**F2 는 여전히 위험이다**(지시서로 보장 못 한다). 그러나 **층이 쌓여 있어 단일 실패로 끝나지 않는다** —
설계가 노린 구조가 실제로 작동했다. 위험의 심각도를 **높음 → 중간**으로 내린다.

### F2 최종 실측표

| 커맨드 | 선언 | 적재 | 읽기 절 |
|:--|--:|--:|:--|
| `build` (rb1·rb2) | 7 | **7 · 7** | 있음 |
| `review doc` | 10 | **9**(조건부 제외 10/10) | 있음 |
| `sync` | 8 | **0** | 있음 |
| `prd func` | 12 | **0** | 있음 |

**같은 처방인데 갈린다.** 지시서 문구가 아닌 다른 무엇이 갈림을 만들고, 그것을 규명하지 못했다.
`prd func` 는 새 ID 가 0건이라 발급 규약이 불필요했을 수 있다 — **그러나 그것을 구별할 방법이 없다.**
그 구별 불가가 F2 의 본질이다.

## 능력 12 — 계획 절반은 실측됐다

미완료 task 둘의 소유가 완전히 갈린 상태(`quota.ts` ↔ `channel.ts`)에 `orchestration`
한도를 채우고(`maxWorkers: 2` · `worker: sonnet` / `judge: opus`) `/flow:next` 에 병렬을 요청했다.

**조각 넷을 다 읽었다** — `ownership` · `parallel` · `collect` · **`regression-surface`**(선행 조건).

| 무엇 | 결과 |
|:--|:--|
| 한도 확인 | `maxWorkers: 2` 읽음 · **판정자가 진행자보다 높은지 확인해 통과라 적었다** — 내가 넣은 규칙이 발동했다 |
| 소유 겹침 | **비었다**고 정확히 계산 |
| 배정 | 후보 2 → **배정 1 · 직렬로 미룸 1** |
| 지시서 | 새 파일 없이 task 문서로. 경계도 적었다 — *"`channel.ts` 는 W1 소유가 아니다"* |

**후보가 둘이고 소유가 안 겹치는데 배정을 1로 줄였다.** 순서 의존 셋을 찾았고 그중 하나는
**내가 예상하지 못한 것**이다.

> **`npm test` 가 리포 전체를 돈다.** `vitest run` 에 설정 파일이 없어 `*.test.ts` 를 전부 수집한다.
> 두 워커가 동시에 돌리면 **서로의 작성 중 테스트가 상대 판정에 섞인다** — `File Map` 밖에서 생기는
> 겹침이라 소유 계산이 못 잡는다.

`ownership.md` 가 *"`File Map` 밖에서 생기는 파일은 겹쳐도 알 수 없다"* 로 적어 둔 한계의
**구체적 사례**다. 흔한 경우라 조각에 이름을 붙여 적었다. *"의심스러우면 직렬"* 규칙도 지켜졌다.

**나머지 절반은 배포해야 실측된다** — 워커를 실제로 띄우는 것은 **설계상 환경의 일**이고,
거둬들이기는 워커가 파일을 써야 셀 것이 생기며, *죽어도 이어가기* 는 런이 죽어야 검증된다.
구조적 한계이지 미완이 아니다.
