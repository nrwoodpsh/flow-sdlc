## 1 · study — 설명을 노트 한 장으로 남긴다

### 원안이 왜 안 되나

*"구현에 대한 모든 단계에 적용"* 을 모드로 만들면 `design`·`build`·`verify` 본문마다 분기가 붙는다.
**커맨드 본문을 얇게 유지하는 것이 이 설계의 축이다** — `procedures/` 를 뗀 이유가 그것이다.

그리고 모드는 `loads` 를 가르는 축이다(`review` 의 코드/문서는 조각 목록 자체가 다르다).
study 는 조각을 바꾸지 않는다 — **산출물을 하나 더 내는 것**이라 모드가 아니다.

### 바꾼 형태

설명 자체는 작업 중 대화로 한다(지금도 된다). 바꾸는 것은 하나 — **끝나면 파일로 남긴다.**

```json
// workflow.config.json
"study": { "enabled": true, "language": "java" }
```

- **자리** — `sync` 가 유닛을 마무리할 때 `doc/00.ref/05.explainer/` 에 설명 노트 1장.
- **슬롯·템플릿은 이미 있다** — `03.templates/10.explainer/explainer-template.md`, 작성 규칙은 `ops-doc/authoring` 의 「설명 노트」.
  `ops-doc` 이 스스로 적어 뒀다: *"부르는 곳이 없다 — 파이프라인이 만들지 않는다."* **이 제안이 그 호출자다.**
- **`build`·`design` 출구가 아니다** — 셋이 각각 내면 같은 유닛에 겹치는 설명 노트가 셋 생긴다.

### 범위는 사용자가 지목한다 — 유닛 전체가 아니다

사용자 원문이 이 범위를 정하고 있다: *"구현 계획을 보고, **내가 모르는 부분을** 이 옵션을 주면"*.

| | 결과 |
|:--|:--|
| ✗ 유닛 전체를 대조 | 이미 아는 것까지 섞여 길어진다 → 안 읽힌다 |
| ✓ **사용자가 지목한 것만** | 짧고 끝까지 읽힌다 |

`design`·`build` 를 시작할 때 사용자가 지목하고, `sync` 가 **그것만** 노트로 남긴다.

### 템플릿에 필수 칸 하나를 더한다

**`다른 점` 칸이 이 제안의 안전장치다.**

```markdown
## 대조 — {선택 언어}

| 이 프로젝트 | {언어} 대응 | **다른 점** |
|:--|:--|:--|
| `Promise` | `CompletableFuture` | **스레드가 없다.** Java 는 스레드풀, 여기는 이벤트 루프 하나 |
| `interface` | ~~`interface`~~ | **런타임에 없다.** 컴파일 뒤 사라진다 — `instanceof` 불가 |
```

- **비면 감점한다.** 빌 일이 없다 — 비유는 늘 어긋나는 데가 있다.
- **이름이 같은 자리가 가장 위험하다** (위 표 둘째 줄). 같아 보여서 확인 없이 넘어간다.
- 왜 필수인가: *"A 는 B 와 같다"* 는 **LLM 이 그럴듯하게 틀리는 자리**고, 이 노트에는 기계 판정자가 없다.
  코드는 컴파일러가 잡고 계약은 `contract-gate` 가 잡는데 **대조 설명은 아무도 안 잡는다.**
  `doc-verify` 는 템플릿 충족만 본다 — *"비유가 맞나"* 는 채점 대상이 아니다.
- **목적이 학습이면 정확성은 덜 중요해지지 않고 더 중요해진다.** 틀린 대조는 효과가 0 이 아니라
  **마이너스**다 — 잘못 이해한 것을 문서로 굳힌다.

### 배선상 주의 — 조각으로 만들지 않는다

**`sync` 는 F2 실측에서 조각 읽기가 0/8 이었다** (큰 프로젝트). study 지시를 조각에 넣으면 안 읽힐 쪽에 건다.
**커맨드 본문 또는 `procedures/sync/` 에 둔다** — 본문은 슬래시 커맨드라 항상 실린다.

### 판정자가 사용자다 — 그건 결함이 아니다

**셋 중 이것만 판정자가 사람이다.** 다른 둘과 종류가 다르다.

| 제안 | 판정 | 확인 방법 |
|:--|:--|:--|
| 원격 대조 · 결정 축 | 기계 · `gatekeeper` | 숫자 |
| **study** | **사용자** | *"읽으니 알겠다"* |

한때 이 문서는 「효과를 측정할 수 없다」와 「수요가 확인되지 않았다」를 위험으로 적었다. **둘 다 근거가 아니다** —

- **측정 가능성은 게이트에 대는 기준이다.** 통과·차단을 기계가 갈라야 하니 셀 수 있어야 한다.
  이 노트는 게이트가 아니고 사람이 읽는 물건이다. 셀 수 없다는 것을 값이 없다는 뜻으로 옮기면 비약이다.
- **`05.explainer/` 가 비어 있던 것은 부르는 커맨드가 없었기 때문이다.** 부를 수 없는 것을 아무도
  안 썼다는 사실에서 수요 없음을 끌어낼 수 없다. **요청 자체가 수요다.**

### 남은 위험 — 하나뿐이다

- **대조가 틀릴 위험.** 위 「필수 칸」이 상당히 막지만 완전히는 못 막는다. 기계 판정자가 없다.
- (위험이 아니라 제작 조건) **조각에 두지 않는다** — `sync` 조각 읽기율 0/8 이라 커맨드 본문에 둔다.

## 2 · 결정 축 누락 검사 — 카탈로그가 아니다

### 원안이 왜 안 되나

`00.concept.md` 의 「무엇이 아닌가」와 부딪힌다 — **코드 생성기 아님** · **스택 특화는 프로젝트에 위임**.
그리고 목록은 지식을 더하지 않는다. 나열된 패턴은 이미 아는 것이고, 목록이 더하는 것은 **고르고 싶은 마음**이다.
이 리포는 반대 방향을 골랐다 — 권한 도구에 `ponytail`(**과설계 삭제 목록**)이 `[필수]` 로 올라 있다.

### 그런데 사용자가 준 목록은 카탈로그가 아니었다

> 동시 접근(Mutex·spinlock) · DB 개념(ER·정규화) · Kafka 사용 케이스 · MSA 패턴(API Gateway·Circuit Breaker)
> · Event-Driven · OOP 컨셉 · API 통신 방식

**이것은 패턴이 아니라 설계 결정 축이다.** 그래서 판정이 바뀐다.

| 반박 | 재판정 |
|:--|:--|
| 스택 특화라 경계 위반 | **틀렸다.** Mutex·정규화·pub-sub 은 스택 무관 개념이다. `Spring @Transactional` 이면 위반이지만 이건 아니다 |
| 지식을 더하지 않는다 | **절반만 맞다.** 지식은 안 더하는데 **누락은 잡는다.** 그건 다른 일이다 |
| 고르고 싶어진다 | **남는다.** 목록 크기에 비례한다 |

**값이 어디 있는지가 뒤집힌다** — 고르게 하는 데 없고 **빠뜨린 축을 잡는 데** 있다.
그리고 그건 flow 의 사업 정의(*"순서와 판정을 든다"*)에 정확히 들어맞는다.

### 바꾼 형태 — 패턴 이름이 아니라 판정 질문

`design` 이 이 표를 채운다. **`해당?` 이 ✅ 인데 `결정` 이 비면 그것이 발견이다.**

| 축 | 판정 질문 | 해당? | 결정 | 남길 곳 |
|:--|:--|:--:|:--|:--|
| 동시 접근 | 같은 자원을 둘 이상이 쓰나 | ✅ | 캐시 갱신에 락 하나 (`Mutex`) | `2.task` |
| 실패 전파 | 외부 호출이 있나 — 실패하면 어디까지 가나 | ✅ | 재시도 2회 후 빈 값 | `3.contract` |
| 데이터 일관성 | 쓰기가 둘 이상 저장소에 걸치나 | ❌ | 저장소 하나뿐 | — |
| 비동기 경계 | 응답을 기다리지 않아도 되는 일이 있나 | ❌ | 실시간 응답만 | — |

- **패턴 이름은 `결정` 칸 안의 예시로만 들어간다.** 목록이 이름을 고르게 하지 않는다.
- 해당하면 무엇을 쓸지는 판단이고 근거는 ADR 이다. **`해당?` 에는 반드시 답한다.**

### 축 목록은 플러그인이 들고 다니지 않는다

**축은 프로젝트마다 다르다.** 단일 프로세스 대시보드에 Kafka·MSA 축을 묻는 것은 소음이고,
소음이 섞이면 표를 형식적으로 채우게 된다.

```
setup 이 스택 답변으로 걸러 프로젝트에 심는다
  대시보드      동시 접근 · 실패 전파 · 화면 상태            (3~4)
  MSA 백엔드    + 데이터 일관성 · 비동기 경계 · 서비스 경계  (7~8)
```

**이것은 `code-style.md` 의 `paths` 가 TypeScript 프로젝트에 15개 언어를 남겨 둔 결함과 같은 병이다** —
전부 들고 다니면 해당 없는 항목이 대부분이 되고 표 전체가 무시된다.

### 남은 위험

- **조각을 크게 만들면 안 읽힌다.** 8분류 × 패턴 10개 = 설명 80개는 F2 를 악화시킨다.
  **축 8줄 + 질문 1개씩** 이 상한이다.
- **새 드리프트 면이 생긴다.** `setup` 이 프로젝트에 심는 축 목록은 생성물이고,
  플러그인의 축 정의가 바뀌면 이미 심은 프로젝트와 어긋난다. `CLAUDE.md` 의
  「정본을 손으로 두 곳 맞추지 않는다」가 여기에도 걸린다.
- **형식적 채움** — `해당?` 을 전부 ❌ 로 채우면 검사가 사문화된다. 등급 판정에 걸어야 한다.

## 3 · 원격 대조 — fetch 가 아니라 판정 기준이 본체

### 가져오는 것은 이미 된다

가드 통과를 확인했다(2026-08-18 실측).

```
git fetch origin                   통과
git ls-remote origin               통과
git log origin/main..HEAD          통과
git diff origin/main...HEAD        통과
```

### 원격 개념이 아예 없지는 않았다

`traceability/conflict.md` 가 이미 원격을 본다.

> **발급 전** — **원격 기본 브랜치의 그 파일을 기준으로 최대 번호를 본다.** 로컬만 보면 남이 이미 쓴 번호를 다시 쓴다

`sync` 가 이 조각을 싣는다. **다만 대상이 ID 번호 하나뿐**이고 파일·심볼 충돌로는 넓혀져 있지 않다.

### 새로 만들 것은 셋

| # | 무엇 | 왜 fetch 만으로 안 되나 |
|:--|:--|:--|
| ① | **판정 기준** | 파일 단위면 오탐이 쏟아진다(`index.ts`·`types.ts` 는 늘 겹친다). **심볼 단위**여야 하고 그러면 `code-graph` 가 필요하다 |
| ② | **배선** | **`review 코드` 의 `loads` 에 `impact-analysis` 가 없다.** `regression-surface` 는 `build` 의 conditional 에만 걸려 리뷰 시점에 뛰지 않는다 |
| ③ | **적을 자리** | `regression-surface` 의 「안 본 범위」 표. `repo 밖 — 사람 확인` 과 같은 형식으로 **`남이 최근에 고침 — 사람 확인`** |

### 리포트가 이렇게 바뀐다

```
지금     AuthFilter.ts:42 — validateToken 반환형이 바뀝니다. 호출부 3곳 영향.

뒤       AuthFilter.ts:42 — validateToken 반환형이 바뀝니다. 호출부 3곳 영향.
         ⚠ 이 함수를 원격 main 에서 3일 전에 다른 사람이 고쳤습니다 (a3f9c21)
           → 머지하면 부딪힙니다. 그 커밋을 먼저 보세요.
```

**코드를 읽어서는 알 수 없는 정보다.** 원격 히스토리에만 있다 — 파생 불가라 적을 값어치가 있는 종류다.

### 자리가 유리하다

F2 실측에서 **`review 코드` 는 조각 10/10 을 읽었다** — 측정된 커맨드 중 가장 높다(`build` 7/7 · `sync` 0/8 · `prd 기능` 0/12).
**셋 중 가장 잘 도는 자리에 붙는다.**

### 남은 위험

- **혼자 쓰면 값이 거의 없다.** 원격 main 에 남의 커밋이 없으면 대조할 것이 없다 — **팀 전제**다.
  (혼자여도 `origin/main..HEAD` 는 되돌림 범위의 경계를 준다. 그건 `traceability/revert-scope` 의 일이다.)
- **오탐이 한 번 쏟아지면 끝난다.** 심볼 단위 판정이 안 되면 넣지 않는 것이 낫다.

## 효과 판정 — 판정자가 누구냐로 먼저 가른다

**셋을 한 자에 대지 않는다.** 두 개는 기계·`gatekeeper` 가 판정하고 하나는 사용자가 판정한다.
**측정 가능성은 앞의 둘에만 대는 기준이다** — 게이트는 통과·차단을 갈라야 하니 셀 수 있어야 하고,
사람이 읽는 노트는 그렇지 않다. 이 구분을 안 하면 종류가 다른 것을 같은 자로 재게 된다.

| # | 붙는 자리 | 판정자 | 어떻게 확인하나 | 판정 |
|:--|:--|:--|:--|:--|
| **3** | `review 코드` | 기계 + `gatekeeper` | 경고 건수 · 그중 진짜였던 비율 | **효과 있다** (팀 전제 · 심볼 단위 판정이 조건) |
| **2** | `design` | `gatekeeper` | `해당? ✅ + 결정 빈칸` 잡힌 횟수 | **효과 있다** (형태 조건부 — 축 8줄 상한) |
| **1** | `sync` | **사용자** | 읽고 *"알겠다"* 가 되나 | **효과 있다** (`다른 점` 칸이 조건) |

**셋 다 효과가 있다. 조건이 다르다.**

- **3의 조건은 정확도** — 심볼 단위가 안 되면 오탐이 쏟아지고 그러면 아무도 안 본다.
- **2의 조건은 크기** — 축이 늘어나면 조각이 커지고 커지면 안 읽힌다(F2).
- **1의 조건은 옳음** — 기계 판정자가 없어 `다른 점` 칸이 유일한 방어다.

**그리고 자리마다 지켜지는 정도가 다르다.** 읽으라는 지시와 채워 내라는 지시가 다르게 지켜진다 —
`setup` 의 정직 요약(산출물 형태) 7/7, `sync` 의 조각(참조 형태) 0/8.
**2·1 은 산출물 형태라 유리하다.** 단 1의 지시를 조각에 두면 0/8 쪽에 걸리므로 커맨드 본문에 둔다.
