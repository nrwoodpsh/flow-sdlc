## 결정 — 린터를 쓴다. `setup` 이 세운다 (20260819 사용자 결정)

하드 차단"* 이라고 정해 뒀는데, **그 자격을 가진 도구가 하나도 없다.** 실측 리포트가 스스로 적었다:

린터는 검출도 **판정도** 결정론이라 그 자격을 갖고, 설치가 `npm i -D` 한 줄이다.

### 요구 — 제시가 아니라 자동 구축이다

지금 `setup.md:196` 은 *"골라 제시하고 **고른 것만** 설치한다"* 다. **그것이 ①의 결함이다.**
린터는 그 방식이면 안 된다 — **스택을 받으면 그 자리에서 층이 서야 한다.**

**4단계를 빼면 ①이 그대로 재현된다** — 패키지는 깔렸는데 설정이 없어 안 돌고, `/flow:review` 를
처음 돌릴 때까지 아무도 모른다. **초안은 최소로 하고 *"규칙 조정은 프로젝트 몫"* 을 요약에 적는다.**

### TypeScript 는 ESLint 다 — Biome 이 아니다

**타입 정보를 보는지가 갈림길이다.** 이번에 놓친 `N1`(가드 없는 `JSON.parse`)은
`no-unsafe-assignment`·`no-unsafe-member-access` 가 잡는데, **둘 다 타입 계산기를 요구한다.**
Biome 은 빠른 대신 타입을 사실상 안 보므로 이 발견을 못 잡는다.

| 안 본 룰 항목 | 걸린 발견 | 린터가 잡나 |
|:--|:--|:--|
| Null Checks | **N1** — `merge.ts:31`·`:115` | ✅ `no-unsafe-assignment`·`no-unsafe-member-access` |
| Async in Loops | `runner.ts` | ✅ `no-await-in-loop` |

**넷 중 둘을 확실히, 하나를 절반 잡는다.** `F1` 이 룰 기반으로 승격되는 것은 아니다 —
과장하지 않는다. 승격되는 것은 `N1` 이다.

## ⓪ · `flow.tools.json` — 도구를 데이터로 만든다

```jsonc
{
  "ocr": {
    "kind": "cli",                                  // cli | plugin | slash
    "layer": "패턴",
    "required": true,
    "install": { "by": "auto",                       // ← 마커가 필드가 된다
                 "cmd": { "*": "npm i -g @alibaba-group/open-code-review" } },
    "invoke": "ocr delegate rule <파일…>",            // ← ④
    "runBy": "reviewer",                             // ← ⑦
    "verify": { "cmd": "ocr delegate preview",
                "expect": "파일 목록이 비지 않는다" },  // ← ⑥ · exit 0 이 아니다
    "withoutIt": "룰 검출이 빠지고 LLM 판단만 남아 오탐이 는다"
  },
  "claude-security": {
    "kind": "plugin",
    "runBy": "main",                                 // 플러그인은 reviewer 밖이다
    "install": { "by": "user", "cmd": { "*": "/plugin install claude-security@…" } }
  }
}
```

**7건이 4작업으로 접힌다.**

| 원 제안 | 어디로 |
|:--|:--|
| ④ 호출 방법 · ⑦ 실행 주체 | `invoke` · `runBy` **필드** + 생성 + 검사 |
| ① 묻고·설치하고·확인 · ② `review.layers` | `verify` 를 `setup` 이 돌려 config 에 적는다 |
| ③ SessionStart 알림 | 훅이 `review.layers` 를 읽는다 |
| ⑤ 설치 절차 · ⑥ 검증 방법 | `install.cmd`(플랫폼별) · `verify.expect` **필드 값** |

### 값의 중심 — ⑥·⑦ 이 산문 수정에서 기계 검사로 바뀐다

| 신설 lint | 무엇을 잡나 |
|:--|:--|
| `tool-runner-consistent` | `kind: plugin\|slash` 인데 `runBy: reviewer` 면 실패 ← **⑦** |
| `tool-verify-present` | `required: true` 인데 `verify` 가 없으면 실패 ← **⑥** |
| `tool-canon-parity` | 카탈로그·`layers.md` 표 ↔ canon 대조 (`generated-up-to-date` 계열) |

**⑦ 은 순수 정합성 문제다** — *"플러그인인데 Bash 로 돌리라고 적혀 있다"*. 데이터로 두면 사람이 안 봐도
잡히고, 산문으로 고치면 도구가 하나 늘 때 또 어긋난다.

### 목적을 먼저 못 박는다 — 파일을 넘는 것이다

> **"A 파일의 1번 함수를 수정했을 때, 다른 파일의 무엇과 연결돼 있나 · 값이 파일들을 넘어 어디로 흐르나"**

이것이 `범위` 층의 목적이다. **함수 안 흐름이 아니다.** 이 기준으로 도구가 갈린다.

| 질문 | dep-cruiser | Semgrep OSS | LSP | **joern** | CodeQL |
|:--|:--:|:--:|:--:|:--:|:--:|
| 파일 A 가 파일 B 를 임포트하나 | ✅ | ❌ | 부분 | ✅ | ✅ |
| **이 함수를 부르는 곳** (파일 넘어, 1홉) | ❌ | ❌ | ✅ | ✅ | ✅ |
| **N홉 호출 체인** (파일 넘어) | ❌ | ❌ | ❌ | ✅ | ✅ |
| **값이 파일을 넘어 흐르나** | ❌ | ❌ | ❌ | ✅ | ✅ |

**joern 과 CodeQL 둘만 만족한다.** 실측이 이미 증명했다 — 2회차에서 joern 이
`runCollect` 호출부 0(파일 넘는 호출 그래프)과 `SYS-5`/`SYS-9` 무유출(파일 넘는 흐름)을 확정했다.
**모듈 임포트 그래프와 함수 호출 그래프를 섞지 않는다** — 한 파일에 함수 열 개가 있으면
임포트는 열 개를 뭉쳐 보여준다.

### CodeQL 을 제거하는 이유 — 라이선스다

기술만 보면 JS/TS 에서 CodeQL 이 joern 보다 성숙하다. **막는 것은 라이선스다.**

| 무엇 | 라이선스 |
|:--|:--|
| 쿼리 소스 (`github/codeql` 의 `.ql`) | **MIT** — 자유 |
| **CLI · 엔진** (그 쿼리를 실제로 돌리는 것) | **GitHub CodeQL 이용약관 — 오픈소스 아니다** |

```
✅ 무료      공개 리포(OSI 라이선스) · 학술 연구 · GitHub Actions(공개 리포)
⚠️ 제약      사설·상용 코드  →  GitHub Advanced Security 필요
❌ 금지      CodeQL 로 경쟁 제품·서비스를 만드는 것
```

**쿼리가 MIT 여도 엔진이 막히면 못 돌린다.** joern 은 **Apache 2.0** 이라 조건이 없다.

**동작 방식도 다르다** — CodeQL 은 **빌드를 가로채** 컴파일러가 본 것을 관계형 DB 로 만들고
`QL`(Datalog 계열)로 질의한다. 정확하지만 **빌드가 돌아야 한다.** joern 은 **소스만 파싱**해
CPG(그래프)를 만들고 Scala DSL 로 순회한다 — 빌드가 불필요한 대신 **프론트엔드 품질에 의존한다**
(이번 astgen 사고가 그 약점이다).

> **약관은 계약 문서고 조항이 바뀐다.** 공개 리포로 전환하거나 GHAS 를 구독하게 되면
> `github/codeql-cli-binaries` 의 `LICENSE.md` 와 GitHub 의 CodeQL Terms 를 **직접 읽고** 다시 판단한다.

### Semgrep 을 제거하는 이유 — 지금 필요가 없다

Semgrep 은 **코드 모양을 찾는 도구**다. `grep` 이 글자를 찾는 것과 다르다.

```
grep      "JSON.parse"        주석·문자열 안도 걸린다
semgrep   JSON.parse($X)      실제 호출만 · "try 밖에 있는 것만" 같은 조건을 붙인다
```

**용도는 하나다 — 우리만의 규약을 짧게 쓰는 것.** ESLint 커스텀 규칙은 JS 플러그인을 짜야 하는데
Semgrep 은 YAML 몇 줄이다. 그런데 세 근거가 지금 다 0 이다.

| 근거 후보 | 지금 |
|:--|:--|
| 프로젝트 고유 규약을 기계로 내린다 | **그 규약이 문서에 없다** |
| 흔한 실수를 잡는다 | **ESLint** 가 한다 (겹친다) |
| 여러 언어를 규칙 하나로 | **TypeScript 단일 언어다** |

**없는 필요를 위해 도구를 깔지 않는다** — 「근거 없는 선제 구축」이다.
**다시 볼 조건**: 고유 규약이 문서에 생기거나, 언어가 둘 이상이 될 때.

### LSP — joern 의 폴백이다. joern 보다 먼저 깐다

**LSP 는 도구 이름이 아니라 규약이다**(Language Server Protocol). IDE 가 언어 서버와 말하는 규격이고,
언어마다 서버가 다르다 — TypeScript `tsserver` · Java `jdtls` · Python `pyright` · Go `gopls`.

붙이면 **grep 이 아니라 타입·정의·참조로 코드를 읽는다.**

| | LSP 없이 | LSP 있으면 |
|:--|:--|:--|
| "이 함수 쓰는 곳" | `grep` — 주석·문자열·동명이인까지 걸린다 | **정확한 참조만** (타입으로 판정) |
| "이 변수 타입" | 읽어서 추측 | 서버에 물어본다 |
| 컴파일 에러 | `tsc` 를 돌려야 안다 | 즉시 안다 |

**발견을 내는 도구가 아니다 — 탐색을 정확하게 하는 것이다.** 그래서 `review` 뿐 아니라 `build` 에서도 값을 낸다.

**joern 과 겹치지 않는다.** 축소 모드가 `LSP + grep` 인 것이 그 관계다.

| | **LSP** | **joern** |
|:--|:--|:--|
| 부르는 곳 (파일 넘어, **1홉**) | ✅ 정확하다 | ✅ |
| **N홉 호출 체인** | ❌ 한 번에 못 준다 | ✅ |
| **값이 파일을 넘어 흐르나** | ❌ **불가능** | ✅ |
| 코드 안 문자열 (`@Qualifier("...")`) | ❌ | ✅ |
| 준비 비용 | **0** — 켜 두면 상시 | CPG 를 먼저 빌드 |

**`[필수]` 로 두는 이유 셋:**

1. **joern 의 폴백이다.** joern 설치가 아프고 실패할 수 있는데(astgen), 지금은 **폴백조차 없다.**
   1회차 리포트: *"`code-graph` 미설치(**축소 모드도 못 돌렸다**). joern 도 없다.
   호출 그래프·교차 파일 영향을 하나도 계산하지 못했다."* — 폴백이 폴백 없이 무너졌다.
2. `build`·`review` 에서 코드를 읽는 정확도가 오른다.
3. **CLI 경로면 `[자동]` 이 진짜다** — `npm i -g typescript-language-server typescript`.

**설치 두 갈래** — 카탈로그(`presets/tools/README.md` 30~52줄)가 이미 정리해 뒀다.

```
플러그인 (권장)   /plugin install typescript-lsp@claude-plugins-official   → [사용자 설치]
CLI (대체)        npm i -g typescript-language-server typescript           → [자동]
```

**`setup` 자동 구축에서는 CLI 경로를 쓴다** — 플러그인은 슬래시 명령이라 우리가 못 친다.
`[필수]` 를 사용자 손에 맡기면 안 깔린다는 것이 ①의 결함이다.

**설치 순서** — **LSP 를 joern 보다 먼저 깐다.** joern 이 실패해도 축소 모드로 굴러가야 한다.

### 딸린 신규 — CPG 검증기

`joern-parse` 가 **파싱 실패에도 `exit 0`** 이라 빈 CPG 로 *"검증 완료"* 보고가 났다.
**독립 계산기로 대조한다** — `ts-morph` 로 `src/` 의 파일·함수 수를 세서 CPG 의 수와 맞춘다.

```
독립 계산기   20 파일 · 342 함수
joern CPG     0 파일          ⛔ 어긋난다 — CPG 가 비었다
```

**대체가 아니라 대조다.** 몇십 줄이고, *"훅을 고쳤으면 되돌려서 실패하는지도 확인한다"* 와 같은 사상이다.
**taint 를 직접 구현하지는 않는다** — 별칭·포인터 분석이 필요하고, 틀린 taint 는 없는 것보다 나쁘다
(*"무경로 확정"* 이 거짓이 되면 그 위 판정이 전부 근거를 잃는다).

## 자를 것 · 갈라낼 것

### `joern` — `[필수]` 는 유지하고 `[자동]` 마커만 내린다

**설치는 아팠지만 층은 값을 냈다.** 2회차 리포트가 이렇게 적었다 —
*"이번 회차의 값은 새 결함보다 **근거의 승격**"*.

| 무엇 | 1회차 (joern 없음) | 2회차 (joern 있음) |
|:--|:--|:--|
| `F1` 의 교차 파일 영향 | 미측정 | **0 — 임포트 그래프에 호출부 없음** |
| `N1` | 없었다 | **발견** (그래프 + 코드) |
| `SYS-5`/`SYS-9` 유출 · SQL 인젝션 | 눈으로 읽은 주장 | **그래프 실측으로 무경로 확정** |

**"안 봤다" 를 "문제없다" 로 적지 않으려면 이 층이 필요하다.** 축소 모드(`LSP+grep, 1~2홉`)는
데이터 흐름을 아예 안 보므로 위 셋 중 어느 것도 확정하지 못한다. **`[필수]` 를 유지한다.**

**고칠 것은 마커와 설치 경로다.**

```
brew 포뮬러에 JS/TS astgen 없음 (swift·go 만 들어 있다)
astgen 버전 요구 3.47.0  vs  upstream 최신 3.42.0 → 404
joern 이 astgen 을 PATH 가 아니라 cwd 상대경로로 찾는다 (ASTGEN_BIN 을 설정해도)
빌드는 libexec/jssrc2cpg.sh <절대경로>/src --output <cpg> 로 돌았다
```

| 지금 | 바꿀 안 |
|:--|:--|
| `[필수]` `[자동]` | **`[필수]` `[사용자 설치]`** — `sudo`·수동 astgen 이 필요하면 **`[자동]` 은 거짓이다** |

- **`install.cmd` 를 언어별로 가른다** — macOS+brew 는 **JS/TS 에 쓸 수 없다.**
  TypeScript 프로젝트에는 공식 설치 스크립트나 Docker 이미지를 안내한다.
- **astgen 버전 불일치를 알려진 문제로 적는다** — 카탈로그에 없으면 다음 사람이 같은 시간을 버린다.
- upstream 을 우리가 고칠 수 없다. **아프다는 사실을 적는 것이 우리 몫이다.**

### `ocr` — 하위 명령이 원인이 아니었다 (20260819 실측)

피드백은 *"`delegate rule` 이 아니라 `rules check` 가 세부 룰셋을 준다. `delegate` 는 5개
카테고리로만 줘서 Duplicate Code·Null Checks·Async 항목이 애초에 안 보였다"* 로 적었다.
**직접 돌려 확인했다 — 사실이 아니다.** `ocr v1.9.6`:

```
ocr rules check   src/lib/collect/merge.ts | sed -n '/^#### Obvious/,$p'   → 41줄
ocr delegate rule src/lib/collect/merge.ts | sed -n '/^#### Obvious/,$p'   → 40줄
diff → 41d40  "────────" 구분선 한 줄. 그것뿐이다
```

**둘 다 6개 카테고리를 전부 준다** — `Obvious Typos` · `Dead Code` ·
**`Code Quality Checks`**(Duplicate Code · Null Checks · `any` 금지 · `==` 금지) ·
`React Best Practices` · **`Async Handling Standards`**(Error Handling · Async in Loops) ·
`Code Security Checks`. 세부 항목까지 같다.

**`ocr` 진단이 네 번 바뀌었고 네 번 다 도구를 탓했다.**

| 회차 | 진단 | 사실 |
|:--|:--|:--|
| 1 | 도구가 설정 안 됨 | ❌ 정상이었다 |
| 2 | `scan` 이 아니라 `delegate` | ⚠️ 맞지만 원인 아님 |
| 3 | `ocr` 은 룰 엔진이 아니다 | ❌ 룰셋은 실재한다 |
| 4 | `delegate` 가 5개만 준다 | ❌ **6개 다 준다 (실측)** |

**네 번 다 원인은 적용이었다.** ④의 제안(호출 방법을 리뷰가 읽는 문서에)은 여전히 유효하다 —
`scan` 과 `delegate` 를 가르는 것은 필요하다. 그러나 **반쪽 적용의 원인은 아니다.**
원인은 아래 ⑥-B 하나이고, 해법도 하나다.

### ⑥-B 는 도구 문제가 아니다 — canon 으로 안 닫힌다

피드백 자신이 적었다: *"룰셋을 받아놓고 기계로 판정 가능한 항목만 골라 대체하고 나머지를 안 봤다.
층이 죽은 이유가 도구가 아니라 **적용 성실도**였다."*

**F2 계열이다** — 지시가 있는데 안 지킨 것. `flow.tools.json` 이 못 잡는다.
`92` 의 실측이 답을 준다 — **참조 형태 0/8 · 산출물 형태 7/7.**

```
✗ "룰을 전부 적용하라"                          ← 참조. 안 지켜진다
✓ 리포트에 룰 항목 단위로 적용/미적용을 적는다    ← 산출물. 반쪽 적용이 드러난다
```

`6.review/NN` 템플릿에 **적용한 룰 항목 표**를 필수 칸으로 넣는 것이 유일한 방어다.
`안 본 범위` 표와 같은 사상이다. **이것은 A~E 와 별개 작업이다.**

## `/flow:review` 를 목적 두 개로 가른다 (20260819 사용자 결정)

**리뷰의 목적이 둘이다.**

```
① 코드 상 이상한 부분이나 사이드 이펙트가 있는가
② 우리의 설계 의도대로 정상 개발이 되었는가
```

**지금 리포트는 ①만 답하고 ②는 흩어져 있다.** 목적이 둘이면 리포트도 둘로 답해야 한다.

### 목적별로 도구가 갈린다 — 외부 도구는 ②를 못 한다

| 도구 | ① 이상 | ① 사이드 이펙트 | ② 설계 정합 |
|:--|:--:|:--:|:--:|
| **ESLint** | ✅ **결정론 판정** | — | — |
| **joern + LSP** | — | ✅ **전담** | — |
| **ponytail** | ✅ 과설계 | — | — |
| **OCR** (위임) | ⚠️ 체크리스트 (판정은 LLM) | ❌ **diff 안만 본다** | ❌ **전혀** |
| *claude-security* `[선택]` | ✅ 취약점 | — | — |
| *codex* `[선택]` | — | — | ⚠️ 설계 **자체**를 의심 |
| **`contract-gate`** | — | — | ✅ 계약 정합 |
| **`traceability/coverage`** | — | — | ✅ 요구 커버리지 |
| **`drift-check`** | — | — | ✅ File Map ↔ 실제 변경 |
| **`gatekeeper`** | — | — | ✅ 판정 분리 |

**목적 ②는 flow 고유다. 외부 도구 여섯을 다 깔아도 안 채워진다** — OCR 룰은 우리 `3.contract` 도,
요구 태그도, File Map 도, 설계도도 모른다. **그것이 flow 가 하는 일이고 도구가 대신 못 하는 자리다.**

### OCR 의 값은 룰이 아니라 커버리지다

```
ocr delegate preview --format json
→ total 126 · reviewable 49 · excluded 77 (unsupported_ext 65 · default_path 12)
```

**안 본 파일에서는 이상한 것도 설계 위반도 못 찾는다 — ① · ② 둘 다의 전제다.**
지금은 `git diff` 를 눈으로 골라 본다. 빠뜨려도 아무도 모른다.
이 숫자가 있으면 *"49/49 봤다"* 가 **검증 가능한 주장**이 된다.

**룰 그룹이 리뷰 단위를 준다** — `delegate rule` 이 파일을 룰 그룹으로 묶어 준다
(실측: `**/*.{ts,js,tsx,jsx}` 그룹 · `**/package.json` 그룹 · `default` 그룹).
**그룹마다 `reviewer` 하나를 붙이면** ocr 의 번들링 전략을 위임 모드로 근사한다.

**`--background-file` 은 통과 저장소다** — `delegate preview` 의 JSON 에 `background` 키가 실리고
`delegate rule` 에는 안 실린다(실측: diff 0). ocr 이 그것으로 아무것도 하지 않는다.
얻는 것은 *"무엇을 볼 파일 + 무슨 맥락으로"* 가 **한 물건**이 되는 것뿐이다.
**2000자 권고가 있다** — task 문서 전문(6676자)을 넘기면 경고가 난다. 요구 태그 + 계약 요지로 요약한다.

### 순서 원칙 넷

```
① 싼 것 먼저          결정론이 잡을 것에 비싼 LLM 토큰을 쓰지 않는다
② 범위를 좁힌 뒤       OCR 이 확정한 파일 목록에만 비싼 층을 돌린다
③ 외부 전송은 맨 끝    거절되면 나머지는 이미 돌아 있어야 한다
④ 판정은 끝에 한 번    gatekeeper
```

### 절차 — `[선택]` 둘의 삽입 지점까지

```
① 코드 이상 · 사이드 이펙트
   0  대상 확정       ocr delegate preview --format json   [OCR]      reviewer
   1  룰 그룹 확보     ocr delegate rule <reviewable 전부>   [OCR]      reviewer
   2  결정론          eslint · tsc                          [ESLint]   reviewer   ← 하드 차단 자격
   3  사이드 이펙트    joern / LSP+grep 폴백                 [joern]    reviewer
   4  체크리스트       룰 그룹마다 reviewer · ponytail         [ponytail] **메인**(슬래시)
   5  취약점          claude-security                       [선택]     **메인**(Workflow)
② 설계 의도 정합
   6  계약 정합       contract-gate                          결정론     reviewer
   7  요구 커버리지    traceability/coverage
   8  File Map 대조   drift-check
   9  설계 의심       codex                                  [선택]     **메인** · 외부 전송 확인
판정
  10  반증           gatekeeper (critical·high)
```

**`claude-security` 가 ①의 마지막인 이유** — 목적 ①(취약점)이고 **비싸다.** ESLint·joern 이 이미 잡은
것에 토큰을 쓰지 않는다. 그리고 **자체 반박을 근거로 삼지 않는다** — 실측에서 그 산출의
`coverage.adversarialCasualties` 와 `votes.json` 이 서로 어긋났다. **`gatekeeper` 가 다시 본다**
(*"진행하는 쪽이 판정하지 않는다"*).

**`codex` 가 ②의 마지막인 이유** — *"이 설계가 맞나"* 는 **구현이 설계를 따랐는지 확정한 뒤** 묻는
질문이다. 순서를 뒤집으면 *"설계가 틀렸다"* 가 *"구현이 안 따랐다"* 를 가린다.
그리고 **코드가 외부로 나가므로 맨 마지막**이다 — 사용자가 거절해도 0~8 은 이미 돌아 있다.

## 구현할 것 — `review` 재구성

| id | 무엇 | 완료 판정 | 판정자 |
|:--|:--|:--|:--|
| **R1** | `procedures/review/code.md` 를 **① / ②** 두 절로 가른다 | 두 절 제목이 목적 문장 그대로다. `lint` 신설 `review-two-purposes` — 리포트 템플릿에 두 절이 없으면 실패 | 검사기 |
| **R2** | 0단계에 `ocr delegate preview --format json` 을 박고 **커버리지 숫자를 리포트 필수 칸**으로 | 픽스처 — `reviewable_count` 를 안 적은 리포트가 채점에서 감점된다 | 검사기 |
| **R3** | 룰 그룹마다 `reviewer` 하나 (독립 컨텍스트) | `delegate rule` 의 그룹 수와 리포트의 `룰 적용` 행 수가 같다 | 검사기 |
| **R4** | **룰 항목별 적용/미적용 표**를 `6.review` 템플릿 필수 칸으로 | 빈 칸이면 감점. **반쪽 적용의 유일한 방어다** | 검사기 |
| **R5** | 층마다 `runBy` 명시 (`reviewer`/`main`) — 피드백 ⑦ | `tool-runner-consistent` (`kind: plugin\|slash` + `runBy: reviewer` → 실패) | 검사기 |
| **R6** | `review 코드` 의 `loads` 에 **`impact-analysis` 추가** | 지금 없다 — `regression-surface` 가 리뷰 시점에 안 뛴다 | 검사기 |
| **R7** | `[선택]` 둘의 **삽입 지점**을 절차에 적고, `codex` 는 **외부 전송 확인**을 절차 단계로 | 절차에 확인 단계가 없으면 `lint` 실패 | 검사기 |

바꾼다. 실측에서 네 회차 동안 그 주장이 검증 불가였고, 그래서 반쪽 적용이 네 번 안 잡혔다.
