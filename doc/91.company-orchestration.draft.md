# 회사형 오케스트레이션 — 다음 세대 구상 검토 (초안)

> **정본이 아니다.** flow 다음 제품의 설계 입력이다. 여기 적힌 것은 아무것도 강제하지 않는다.
> **착수 순서가 정해져 있다** (2026-08-12 사용자 결정): flow 0.5 실전 테스트 →
> 그래프 전환(`90.graph-migration.draft.md`, 근거가 나오면) → **그 다음이 이것이다.**
> 번호가 `91` 인 것은 정본 라인(`00`~`05`)에서 떼어 두려는 것이다.

## 한 문장

**사람 CEO 의 결정 하나가 AI 부서장·워커의 실행 열 배를 움직이는 회사 운영 체계.**

"사람 없이 도는 회사"가 아니다 — 그 목표는 아래 숫자가 기각한다.

## 구상 (사용자 원안)

| 층 | 누가 | 무엇 |
|:--|:--|:--|
| CEO | 사람 | 의사결정 — 승인 · 거절 · 보류 · 재검토 |
| 부서장 | AI 에이전트 | 기획 · 마케팅 · CS · 플랫폼 · SI · SM — 각자 워커를 거느린다 |
| 워커 | AI 서브에이전트 | 부서마다 구성이 다르다 |

- 상태 관리는 LangGraph(또는 유사) · 산출물은 Notion(사람·AI 공용) · 보고는 메일, 모바일 선호
- Slack — CEO·부서장 방 + 부서 단위 방(CEO 마스터 참여)
- 업무 지시는 이벤트 버스(Kafka) 로 — topic 이 지시서다. 누락 없이 순차 진행
- 중앙 기억(RDB·Vector·Graph) + 검색 신뢰 방안 · 감시와 감사 체계

## 평가 — 방향은 업계와 같고, 자율 범위는 숫자가 정한다

**방향은 주류다.** 오케스트레이터가 컨텍스트를 소유하고 워커는 압축 요약만 반환하며 승인
지점을 명시적 게이트로 두는 패턴이 2026년 업계 합의다. flow 가 실측으로 도달한 결론과 같다.

**자율 범위는 냉정한 숫자가 정한다** (2026-08-12 조사, 근거는 문서 끝).

| 숫자 | 뜻 |
|:--|:--|
| 장기 실무 완수율 **30.3%** (TheAgentCompany — 시뮬레이션 회사 175개 업무) | 부서를 통째로 맡기는 것은 시기상조다 |
| 산출물 품질 전문가 대비 **74%** (GDPval) | 단일 산출물은 이미 쓸 만하다 — 갭은 오케스트레이션과 소통이다 |
| 매니저 에이전트 3층 구조 = **학계 공식 미해결 과제** (DAI 2025) | GPT-5 급 매니저도 워크플로우 관리에 실패했다 |
| 멀티에이전트 실패 최다 원인 = **검증 부실** (MAST, 1,600 트레이스) | "검증자가 있다 ≠ 품질" — 표면 검사는 검증이 아니다 |
| 실증된 계층 = **2층 + 사람 게이트** 까지 | 부서장 아래 자율 서브계층을 더 쌓을 근거가 없다 |

그래서 원안에서 하나를 좁힌다 — **부서장은 관리자가 아니라 라우터·수렴자다.** 목표 분해와
워커 배정은 하되, 워커 산출의 품질 판정은 부서장이 아니라 **분리된 판정자**(감사 에이전트 +
기계 게이트)가 한다. 부서장이 판정까지 하면 MAST 의 최다 실패를 그대로 들여오는 것이다.

## flow 에서 이식하는 DNA

flow 는 이 회사의 "플랫폼/SI 부서장이 쓰는 부서 도구"가 되고, 원칙은 회사 층으로 올라간다.

| flow 에서 검증한 것 | 회사 층에서 |
|:--|:--|
| 강제력 3등급 — 기계 · 분리 판정 · 약속 | 부서장 보고의 각 항목에 등급을 적는다. 약속을 기계라 적지 않는다 |
| 진행하는 쪽이 판정하지 않는다 | 부서장은 자기 부서 산출을 승인하지 못한다 |
| 되돌릴 수 없는 것은 사람 | 결제 · 외부 발송 · 계약 · 채용류 결정 = 사람 승인 |
| 정본은 데이터, 산문은 생성물 | **정본은 DB, Notion 은 사람용 투영** |
| 저장된 상태는 낡는다 — 파일에서 계산 | **이벤트 로그가 정본, 상태는 로그에서 재생** |
| 근거 등급 `확인`/`추정` | 모든 기억·검색 결과에 출처 4필드 강제 |

## 설계 — 구성 요소와 선택 근거

### 오케스트레이션 · 상태

**LangGraph** — 원안의 선택이 맞다. `interrupt()`(승인 대기) + 체크포인터(Postgres, 끊겨도
재개)가 정확히 필요한 두 기능이고 엔터프라이즈 배치 1위 평가다. 부서장 = supervisor 그래프,
워커 = 그 하위 노드. **장기 실행 내구성이 문제로 실측되면** Temporal 을 백본으로 결합한다
(OpenAI SDK 공식 통합 GA) — 그 전에는 안 넣는다.

### 업무 지시 — 이벤트 버스

원안의 가장 좋은 결정이다. 지시서가 topic 이면 유실 없음 · 순서 보장 · 재생 가능이고,
**메시지 로그가 그대로 감사 기록이 된다.** 단 규모를 가른다.

| 규모 | 선택 | 왜 |
|:--|:--|:--|
| 0~1단계 (부서 1~2) | **Postgres 큐** (SKIP LOCKED) | 이미 있는 DB 다. 운영비 0 |
| 부서 3+ · 재생 필요 | **Redpanda** | 단일 바이너리 · Schema Registry 내장 · Kafka API 호환 |
| 그 뒤 | Kafka (관리형) | 필요가 실측된 뒤에 |

**지시서 스키마가 이 시스템의 `guard-rules.json` 이다** — JSON Schema 로 정본을 두고,
스키마에 안 맞는 지시는 버스에 못 들어간다(기계 게이트). 지시서 필수 필드:
`요청 부서 · 대상 부서 · 무엇을 · 완료 판정 · 마감 · 위험 등급 · 근거(출처 링크)`.

### 산출물 — 정본은 DB, Notion 은 투영

Notion 은 기계 정본 실격이다 — 실측 근거: **API 3 req/s** 제한, **리비전 API 부재**(그 시점의
정본을 기계가 재구성 못 한다), 2025-09 API 파괴적 개편 전례. 그래서:

- **정본**: Postgres(산출물 메타 + 이벤트 로그) + 오브젝트 스토리지(본문)
- **Notion**: 단방향 발행 투영 — 사람이 읽는 뷰. **사람이 Notion 을 고치면 드리프트다** —
  flow 의 drift-check 를 일반화한 검사가 투영과 정본을 대조한다
- 메일 보고도 같은 정본에서 생성한다 — 보고서를 손으로 쓰는 순간 정본이 둘이 된다

### 사람 승인 루프

- **LangGraph `interrupt()` + Slack Block Kit 버튼** — 승인/거절 2버튼까지는 검증된 길이고,
  원안의 4상태(승인·거절·보류·재검토)는 얇은 커스텀이다(참고 구현: HumanLayer 의
  다채널 라우팅 + 에스컬레이션 + 타임아웃, LangChain Agent Inbox)
- 이메일 폴백 + Slack 모바일 푸시가 현재의 모바일 승인 실태다 — 별도 앱을 만들지 않는다
- **승인 매트릭스가 핵심 설계물이다.** CEO 가 전부 승인하면 CEO 가 병목이다:

| 위험 등급 | 예 | 누가 |
|:--|:--|:--|
| 낮음 — 되돌릴 수 있고 내부용 | 초안 · 분석 · 내부 문서 | **자동** (사후 샘플 감사) |
| 중간 — 되돌릴 수 있고 외부 노출 | 게시 예약 · 고객 답변 초안 | 부서 담당 사람 또는 CEO 위임 규칙 |
| 높음 — 되돌릴 수 없거나 돈 | 발송 · 결제 · 계약 · 삭제 | **사람. 예외 없음** (flow 의 guard 등급 그대로) |

### 기억 · 검색 신뢰

- 시작은 **pgvector** (Postgres 이미 있으니) — 풀 GraphRAG 는 건너뛴다(인덱싱 비용
  10~40배, 2026 컨센서스는 "특정 워크로드만 정당화"). 시간축 추론이 실측으로 필요해지면
  **Graphiti**(오픈소스, bi-temporal)만 얹는다
- **신뢰 = 출처 강제.** 모든 기억·검색 결과에 4필드 스키마를 강제한다:
  `{출처(이벤트 ID 또는 URL), 시각, 작성 에이전트, 모델 버전}`.
  **출처 없는 검색 결과는 판정 근거로 쓸 수 없다** — flow 의 근거 등급을 기계로 올린 것.
  규제 방향과도 일치한다(EU AI Act Art.50, 2026-08-02 발효 — AI 생성물 기계가독 표시 의무)
- 평가는 RAGAS 류(Faithfulness)를 CI 처럼 주기 실행

### 감시 · 감사

- 계측: **OTel GenAI semantic conventions**(전부 Development 상태라 **버전 핀**) +
  **Langfuse 셀프호스트**(오픈소스 · 프레임워크 무관 · 락인 없음)
- **append-only 감사 로그가 먼저다** — 감사 에이전트는 그 위에서만 성립한다.
  이벤트 버스 선택이 이걸 공짜로 준다
- 감사 에이전트 = flow gatekeeper 의 일반화 — 트랜스크립트를 샘플 추출해
  지시 준수·출처 유무·등급 위반을 본다. **자기 부서를 감사하지 않는다**
- 비용 대시보드 + 부서별 토큰 예산 + 킬 스위치(외부 발송 일괄 차단)

## 단계표 — 각 단계에 완료 판정이 있다

**완료 판정이 기계가 아닌 작업은 착수하지 않는다** — flow 규율 그대로.

| 단계 | 무엇 | 완료 판정 |
|:--|:--|:--|
| **0 — 한 부서 관통** | 부서 하나(산출물이 글인 CS 또는 마케팅) + 워커 2 로 지시→작업→정본 저장→Notion 투영→Slack 승인→기록의 한 사이클. Postgres 큐 · pgvector · LangGraph interrupt | 실제 업무 1건이 사람 승인을 거쳐 완료되고, 전 단계가 이벤트 로그에서 재생된다 |
| **1 — 신뢰 축** | 지시서 JSON Schema 정본 + 스키마 검증 게이트 · 출처 4필드 강제 · Notion↔정본 드리프트 검사 | 스키마 위반 지시가 버스에서 거부된다 · 출처 없는 검색이 판정에 못 쓰인다(테스트로 증명) · Notion 수정이 드리프트로 검출된다 |
| **2 — 승인 매트릭스 + 부서 2~3** | 위험 등급 3단 자동/담당/사람 라우팅 · 부서 간 handoff(CEO 방) · 4상태 버튼 | 높음 등급이 자동 승인되는 경로가 없음을 되돌림 테스트로 증명 · 부서 간 지시가 스키마를 통과해 왕복 |
| **3 — 감시·감사** | OTel(버전 핀)+Langfuse · append-only 감사 로그 · 감사 에이전트 샘플 감사 · 비용 예산 | 감사 에이전트가 심어 둔 위반(출처 누락·등급 위반)을 잡는다 — 못 잡으면 실패 |
| **4 — 조건부 확장** | Redpanda/Kafka 전환 · Temporal 백본 · 부서 6 · Graphiti | **착수 조건: 0~3 의 실측에서 병목이 그 자리로 확인될 때만** |

## 하지 않는 것

| 무엇 | 왜 |
|:--|:--|
| 부서 6개 동시 구축 | 근거 없는 선제 구축이다. 부서 하나가 0단계다 |
| 부서장 아래 자율 서브계층(3층 자율) | 실증된 것은 2층 + 사람 게이트까지다. 매니저 에이전트는 미해결 과제다 |
| 부서장이 자기 부서 산출을 판정 | 멀티에이전트 실패 최다 원인이 검증 부실이다 |
| Notion 을 기계 정본으로 | 3 req/s · 리비전 API 부재 · 파괴적 개편 전례 |
| Kafka 를 1일차에 | 운영비가 실측 전에 든다. Postgres 큐 → Redpanda → Kafka 순 |
| 풀 GraphRAG | 인덱싱 비용 10~40배, 대부분 벡터 + 메타데이터 필터로 충분 |
| 사람 없는 외부 발송·결제 | 되돌릴 수 없는 것은 사람이다. flow guard 등급 그대로 |
| 모바일 승인 앱 신규 개발 | Slack 모바일 푸시 + 이메일 폴백이 현재 실태다 |
